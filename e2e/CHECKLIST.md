# agent-inbox — чек-лист живой верификации

Единственный источник правды о том, что в продукте **реально работает**, а что нет. Живёт на диске,
поэтому любая сессия продолжает с места, а не с нуля.

## Как этим пользоваться

**Запуск цикла:**

```
/loop продолжай e2e-верификацию agent-inbox по e2e/CHECKLIST.md: возьми первый пункт со статусом ⬜ или ❌, прогони его команду, при красном — починить и перепрогнать, обновить статус и строку «Факт» в этом файле, закоммитить. Не спрашивай разрешения, не пиши отчёты между пунктами.
```

**Статусы:** ⬜ не прогонялся · 🟢 прогнан, зелёный · ❌ прогнан, красный · 🚧 в работе · ⛔ заблокирован (нужен оператор)

**Правила ведения (обязательные):**

1. Статус ставится ТОЛЬКО после реального прогона команды. Не «по коду видно», не «должно работать».
2. В строку «Факт» пишется вывод прогона (счёт тестов / точка отказа), а не пересказ.
3. Один пункт = один коммит. Нельзя закрывать пункт, не закоммитив.
4. ❌ обязан нести конкретную точку отказа (файл/узел/ассерт), иначе это не диагноз.

## Когда ОСТАНОВИТЬСЯ (жёсткие условия, чтобы не крутиться бесконечно)

Останавливаюсь и пишу оператору, если верно ЛЮБОЕ:

- **Всё зелёное** в разделах A–C (это финиш; D — необязательный хвост).
- **Один пункт красный 3 попытки подряд** — дальше это не отладка, а угадывание. Ставлю ⛔ с описанием, что пробовал, и иду к следующему пункту.
- **Нужно решение оператора** (удалить данные, тронуть чужой процесс, поменять контракт, постить в реальный MR сверх разрешённого) → ⛔ и вопрос.
- **Нет внешнего доступа** (нет `GITLAB_PERSONAL_TOKEN`, GitLab недостижим, opencode не поднимается) → ⛔, потому что живая проверка невозможна в принципе.
- **Нельзя починить, не сломав зелёное** → ⛔ с объяснением конфликта.

Запрещено: закрывать пункт без прогона; ослаблять ассерт, чтобы позеленело; помечать 🟢 при `skip`.

### A3 — реальный root cause найден и исправлен (было ⛔, теперь 🟢)

Две ложные гипотезы по пути (websearch/webfetch, затем медленная модель) были опровергнуты
прогонами — оставлено в истории журнала прогонов ниже, не переписываю задним числом.

**Настоящая причина:** `@opencode-ai/sdk`'s `createOpencodeClient` пытается отключить таймаут запроса
через `req.timeout = false` — это НЕ реальное поле Fetch API и ни на что не влияет. Настоящий таймаут
(`headersTimeout`/`bodyTimeout`, undici-дефолт 300000мс) живёт на диспетчере уровнем ниже и никогда не
отключался. Любой ход агента дольше 5 минут убивался этим скрытым лимитом с голым `fetch failed` —
ДО того как наш собственный `_withTimeout` (`promptTimeout`, 3-10 мин по политике узла) успевал сработать.
Два несогласованных таймаута, младший побеждал молча.

**Фикс:** [opencode.real.ts](../services/agent-inbox/modules/inbox-opencode/opencode.real.ts) —
`OpenCodeRealOpts.dispatcher` (опциональный undici `Agent`); когда передан, оборачивает `fetch` с этим
диспетчером вместо SDK-дефолта. [bootstrap.ts](../services/agent-inbox/serve/bootstrap.ts) передаёт во все
3 места создания `OpenCodeReal` общий `new UndiciAgent({headersTimeout:0, bodyTimeout:0})` — единственный
источник таймаута теперь `_withTimeout`, не два конкурирующих. Опция сделана optional (не по умолчанию в
конструкторе), т.к. явный `dispatcher` в фиче-запросе `fetch()` полностью обходит
`setGlobalDispatcher`/`MockAgent` — а на нём стоит весь network-black-box тест-тир; это была моя
собственная регрессия при первой попытке фикса, поймана прогоном юнит-тестов (4 красных в
`opencode.real.blackbox.test.ts`) и исправлена тем же диффом.

Модель `node_enrich` также сделана конфигурируемой (`AGENT_INBOX_ENRICH_MODEL`, дефолт
`llm-proxy/deepseek-v4-flash` — обогащение не требует ревью-качества) и websearch/webfetch —
конфигурируемый (`AGENT_INBOX_ENRICH_NETWORK`), с динамическим промптом и гейтом на секцию
`## Веб-исследование`, когда включено — но ни то ни другое не было настоящей причиной сбоя.

**Итог:** `t3-t4-live-review.spec.ts` — 2 passed (11.7m), 2026-07-28, полный живой проход
prepare→enrich→lenses→synthesize→ask, без единого `fetch failed`.
