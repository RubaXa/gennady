# Module: plugins/anystack

## 1. Module Vision

`StackPlugin`-заглушка для репозиториев, у которых плагина нет: собственных гейтов не приносит, а весь список гейтов автор пишет в `stack.anystack.extraGates`. Термины (Gate, Scope, Capability, ENV_FAIL, VIOLATION, Run replica) — [stack.spec.md §2](../../../specs/stack/stack.spec.md).

**Parent scope:** [`stack`](../../../specs/stack/stack.spec.md) · **Локальность:** [`plugins`](../../../specs/plugins/plugins.spec.md) · **E2E-механизм:** [`stack/e2e`](../../../specs/stack/e2e/e2e.spec.md)

Зачем это нужно: экзотический стек (или монорепа с самодельным `make`-пайплайном) сегодня упирается в `NO_STACK_DETECTED` — `verify` отказывается работать, пока кто-нибудь не напишет плагин. Но всё, что репозиторию реально нужно от gennady, — это **исполнитель гейтов**: реплика прогона, вердикты, `envFail`-правила, таймауты, отчёт, JSON для оркестратора. Заглушка отдаёт это всё, не изобретая детекции. Цена: `id` плагина остаётся обязательным — это пространство имён гейтов (`anystack:build`) и ключ конфиг-секции.

Золотой пример:

```yaml
stack:
  anystack:
    extraGates:
      - id: build
        argv: [make, build]
      - id: test
        argv: [make, test]
        timeout: 20m
```

`stack.use` не нужен: плагин определяется в любом репозитории. Он остаётся полезен, когда нужно **исключить** остальные стеки — `use: [anystack]` в npm-репозитории отключит гейты node.

## 2. Capability Support

| Capability | Поддержка       | Комментарий                                                               |
| ---------- | --------------- | ------------------------------------------------------------------------- |
| `detect`   | ✅ всегда       | Возвращает detection для любого корня — но только когда выбран (§3)       |
| `verify`   | ✅ обязательный | `planGates` возвращает пустой список; гейты добавляет конфиг              |
| `fix`      | ➖ не объявляет | Фиксер задаётся полем `fixer` у своего гейта (stack.spec §4.4)            |
| `gateIds`  | ✅ пустой       | Словарь гейтов пуст: `extraGates` не проверяются по нему (config.spec §3) |

## 3. Detection

**Плагин определяется в любом репозитории** — и это осознанный выбор в пользу мультистековости: `anystack` не заменяет реальный стек, а сосуществует с ним. `anystack + node` — нормальный прогон: гейты из конфига исполняются рядом с npm-гейтами, и ничего не нужно объявлять в `stack.use`.

Что из этого следует и чем за это заплачено:

- **`NO_STACK_DETECTED` перестаёт достигаться по умолчанию.** Репозиторий, который не опознал ни один реальный плагин, теперь получает активный `anystack` без гейтов, то есть `ZERO_GATES` и код 1 вместо кода 5. Прогон, ничего не исполнивший, по-прежнему не успех, но **сообщение обязано нести подсказку**, которую раньше давал код 5, — иначе диагностика деградирует. Она перенесена в `ZERO_GATES` (stack.spec §8).
- **Код 5 остаётся достижимым через `use`**: `use: [golang]` в репозитории без `go.mod` даёт пустой набор активных плагинов. То есть «стек не найден» продолжает существовать там, где автор назвал ожидаемый стек явно.
- **Плагин обязан молчать, когда ему нечего запускать.** Он активен везде, поэтому его `summary` и `scope` в отчёте были бы шумом в каждом репозитории. Отчёт опускает стек, который не запланировал ни одного гейта, — правило общее, не про `anystack`: стек без гейтов не сообщает читателю ничего.
- `detect` не читает диск и не запускает процессов: возвращать нечего, кроме факта, что гейты придут из конфига.

## 4. Scope Resolution

`resolveScope` возвращает запрошенный режим как есть с примечанием, что скоуп ничего не сужает. Причина: гейт из конфига — это фиксированный `argv`, и что он прочитает, решает только его собственная команда. Флаги `--all`/`--only`/позиционные цели продолжают работать как фильтры **гейтов** (это уровень `verify`), но не превращаются в аргументы команды.

## 5. Gates

**Gitignored-пути — рабочая зона гейтов.** Гейты исполняются в реальном дереве (stack.spec D-STACK-017), поэтому кэши сборки, сгенерированные проекты и прочие ignored-артефакты доступны гейту как есть — без деклараций и симлинков. Guard их не откатывает: они локальны по определению. Фикстура `any-ignored-workspace` закрепляет, что гейт видит ignored-путь; `any-dirty-tree` — что незакоммиченное состояние отвергается до исполнения (`DIRTY_TREE`, exit 4).

Собственных гейтов нет — `planGates` возвращает `[]`. Всё остальное приходит из `applyStackConfig` (stack.spec §4.6, FR-STACK-05) и получает полный паритет с built-in-гейтами (FR-STACK-15): `timeout`, `env`, `cwd`, `requires`, `fixer`, `envFail`, `outputMeansFailure`, `driftMeansFailure`.

**Выбран, но гейтов нет.** Прогон завершается `ZERO_GATES` и кодом 1: прогон, который ничего не исполнил, не является успехом. Синтетического «гейта-заглушки» здесь нет намеренно — гейт означает проверку, а отсутствие конфигурации проверкой не является.

## 7. Inter-Module Dependencies

- **Depends on:** [`stack`](../../../specs/stack/stack.spec.md) (`StackPlugin`, реестр, раннер), [`config`](../../../specs/config/config.spec.md) (`extraGates` и их валидация)
- **Sibling:** [`plugins/golang`](../../golang/specs/golang.spec.md), [`plugins/node`](../../node/specs/node.spec.md) — независимые зоны ответственности
- **Amends:** ничего — поведение «anystack распознаёт всё» уже вписано в `stack.spec` §3 (exit 5 недостижим без `use`/`--stack`) и §8.4 (`ZERO_GATES` несёт подсказку). Никакого признака `optIn` нет: плагин определяется всегда, opt-out — через `stack.use`

## 8. Handoff to Task Scaffolding

**Structural changes:** `StackId` пополняется `'anystack'`; `plugins/index.ts` регистрирует плагин; отчёт опускает стек без гейтов; `ZERO_GATES` получает подсказку.

**Поведение на границах** (как реализовано в `verify.cmd.ts` / `stack-registry.ts`):

- **`--stack=anystack` в репозитории без единого маркера** — работает: флаг действует как разовый `stack.use`, а `anystack` детектится в любом корне, поэтому exit 5 с ним недостижим. Без `extraGates` это `ZERO_GATES` и exit 1, с гейтами — обычный прогон.
- **`--only anystack:test` в мультистековом репозитории** — `--only` фильтрует гейты плана: гейты остальных стеков выпадают, а стек, у которого не осталось ни одного гейта, опускается из плана, отчёта и JSON. Селектор, не совпавший ни с одним гейтом плана, — `BAD_INVOCATION`, exit 4.
- **`use: [golang]` без `go.mod`** — валидно для строгой валидации конфига (FR-STACK-12 ловит только id, неизвестные реестру), но `detect` у `golang` вернёт null, активных плагинов не останется, и это `NO_STACK_DETECTED`, exit 5 (см. §3). `anystack` в такой `use`-список не входит, поэтому не спасает.

**Open risks:**

- **Подсказка в `ZERO_GATES` общая, а не про `anystack`.** Она называет `stack.<id>.extraGates`, потому что раннер не должен знать про конкретный плагин. Для автора, который ещё не написал гейты, этого достаточно; более адресный текст потребовал бы либо синтетического гейта (§5 — отклонено), либо доступа `detect` к конфигу.
- **Отчёт может стать пустым.** Если единственный активный стек — `anystack` без гейтов, в отчёте не останется ни строки про стеки: только `ZERO_GATES` с подсказкой. Правило одно на все поверхности — человеческий отчёт, `--plan` и `--json`, — поэтому «какие стеки определились» в этом случае не видно нигде. Это осознанный компромисс: стек, ничего не проверивший, не является частью прогона.
