# Правила качества успеха (итеративный план)

Что значит «результат нас устраивает»: он (1) соответствует поставленной цели, (2) **воспроизводим**,
(3) отвечает нашим стандартам, (4) отвечает enterprise-зрелости (логирование, обработка ошибок и т.п.).

Два принципа, без которых правило не считается внедрённым:

1. **Судим объективно, не по самооценке воркера.** Корректность реализации проверяется независимыми
   golden-тестами и механическими гейтами, а не тестами, которые воркер написал сам под свой же код.
2. **Воспроизводимость в ОБЕ стороны.** Для каждого правила: положительный исход (конформный артефакт
   проходит) и отрицательный исход (неконформный артефакт **падает**) должны быть **воспроизводимы и
   зафиксированы**. Отрицательный результат — это не провал работы, а зафиксированная «вариация, как
   оно идёт неправильно», которую правило обязано ловить.

Правило внедрено ⇔ есть механизм проверки + тест, что механизм **проходит на хорошем** и **падает на
плохом** (оба воспроизводимо).

## Backlog правил (все нужны; порядок — инкрементальный)

| #   | Правило                                                    | Артефакт    | Объективная проверка                              | Итерация         |
| --- | ---------------------------------------------------------- | ----------- | ------------------------------------------------- | ---------------- |
| R1  | Структурная целостность                                    | спека/тикет | `sdd-check --all` clean                           | **1**            |
| R3  | Механические код-гейты                                     | код         | type-check + lint clean, `testcov --min`          | **1**            |
| R6  | Устойчивость: типизированные ошибки, называющие аргумент   | код         | golden negative-тесты + мелкий lint               | **2**            |
| R2  | Независимые golden-тесты корректности                      | код         | эталонный тест-сет фикстуры по реализации воркера | **3**            |
| R4  | Трассируемость бриф→спека→тест (нет висячих требований)    | спека       | маппинг-чек                                       | **4**            |
| R5  | Воспроизводимость исхода (положит. И отриц.) ≥ порога на N | флоу        | батч-замер clean-rate + фиксация failure-форм     | **5 (сквозное)** |

Отложено на потом (после ядра, добавляем без боли): структурное логирование/наблюдаемость,
интеграционные тесты (мультимодуль), security/секреты, perf/сложность, семантическое качество
декомпозиции (судья/человек), глубина research.

## Дисциплина каждой итерации

1. Реализовать/зафиксировать механизм правила.
2. **Позитивный тест**: конформный артефакт проходит (воспроизводимо).
3. **Негативный тест**: подготовленный неконформный артефакт падает именно на этом правиле
   (воспроизводимо) — зафиксировать форму нарушения.
4. Записать результат (что пробовали, что показал прогон — оба исхода).
5. Только после этого — следующая итерация; план корректируем по ходу.

## Статус

- **Итерация 1 (R1+R3) — стартуем.** Механизмы существуют (`sdd-check --all`, `sdd-verify`
  type-check/lint/testcov). Задача итерации: закрепить их как правила качества с доказательством в
  обе стороны — позитив (чистая фикстура/реализация проходит) и негатив (фикстура `broken-specs` уже
  даёт воспроизводимый негатив: `sdd-check` ловит дефект; для R3 — реализация, ломающая type-check/
  coverage, падает гейт).
- Итерации 2–5 — по мере закрытия предыдущей.

## Набор brownfield-evals (существующий код без спеки) — маленькие, ветко-изолирующие

Принцип: несколько небольших evals, каждый проверяет ОДНУ ветку решений (не монолит). Инфра-ориентир,
без установки зависимостей. Каждый — свой golden-критерий, both-way.

- **E-bf-recover** — есть рабочий bash/Makefile-проект БЕЗ спеки → `discover-from-code` восстанавливает
  спеку. Golden: спека появилась, `sdd-check` по ней clean, ссылается на реальные файлы кода.
- **E-bf-delta** — есть проект без спеки + change-request → правка кода НАПРЯМУЮ (дельта). Golden:
  новое поведение работает (эталонный тест), старое не сломано. (ветка: прямая модификация.)
- **E-bf-delta-to-spec** — дана дельта кода → превратить в обновление/создание спеки. Golden: спека
  существует и отражает изменение. (ветка: реверс дельта→спека.)
- **E-bf-via-spec** — проект + восстановленная спека + change-request → фича через SDD (spec→ticket→
  execute). Golden: поведение + связность спеки. (ветка: spec-first; тяжелее — full SDD.)

Порядок: сперва лёгкие ветки (E-bf-delta, E-bf-recover), затем E-bf-delta-to-spec, затем E-bf-via-spec.
