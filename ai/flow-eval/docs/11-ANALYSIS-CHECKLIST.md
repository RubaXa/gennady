# Чеклист анализа результатов и построения гипотез

Рабочий инструмент для двух задач: (1) **разобрать** прогон eval — что именно произошло и почему; (2)
**построить следующую гипотезу** — что менять, чтобы улучшить. Каждый пункт — проверяемый вопрос с
правилом, выведенным из прошлых экспериментов (цитаты — `journal/EXPERIMENTS-LOG.md`, далее «LOG»).

Порядок жёсткий: **сначала отсеять артефакты харнесса (Часть 1), потом мерить поведение флоу (Часть 2),
потом строить мутацию (Часть 3)**. Нарушение порядка = ложный вывод (мы так теряли часы).

---

## Часть 1 — Прежде чем делать ЛЮБОЙ вывод: артефакт или поведение?

Прогон, убитый/искажённый харнессом, НЕ говорит ничего о флоу. Проверить всё это до трактовки:

- [ ] **Причина остановки — из `worker.error`, не по догадке.** `wall-clock budget …ms exceeded` = бюджет-килл;
      `stuck` = сработал детектор; пусто + `status=completed` = агент сам закончил ход. Разные причины —
      разные выводы. (LOG H8a-diag: «worker-error» оказался бюджет-киллом, а не добровольной остановкой —
      целый вывод H8 пришлось отозвать.)
- [ ] **Не убит ли раньше времени тремя лимитами:** `stuckAfter` (дефолт 1 — слишком агрессивно для
      медленной модели), `maxObservations` (дефолт 6 × observeEveryMs может резать ДО wall-clock),
      `budgetMs`/`maxWallClockMs`. Для честного прогона: `stuck-after 3`, `observe 45s`, `maxObservations`
      такой, чтобы wall-clock связывал (≥ budget/observe). (LOG H8a-diag: `stuck=1`+`maxObs=6`+120s
      давали «0 tools» и «стоп после anchors» — чистые артефакты.)
- [ ] **span ≠ budget?** Если `(последний tool − первый)/бюджет` близко к 1 — почти наверняка килл, а не
      естественный конец. Но wall-clock считается от отправки промпта, не от первого тула — учитывай
      латентность старта.
- [ ] **Модель та самая?** Только `llm-proxy/deepseek-v4-flash` (см. `03-SETUP.md §0`). Другая модель /
      исчезнувшая из каталога модель (виснет) = прогон недействителен.
- [ ] **N≥1?** Один прогон — это шум, не сигнал. Мелкую разницу (токены/время в пределах ~20%, вердикт
      судьи) не считать сигналом без повтора N≥3. (LOG H1/H2/H3: «в пределах шума, N=2».)
- [ ] **Фикстура реалистична?** Не выдумана ли в фикстуре форма, которой нет в реальном корпусе (проверь
      grep'ом по `specs/`). Синтетика фабрикует ложные провалы, похожие на баг тула. (LOG H7.)
- [ ] **Правильный код находки?** Сверяй ИМЕННО код (`MIG_SECTION_UNMAPPED_TARGET` от `plan --verify` ≠
      `SDD_TRACKER_MISSING_ROW` от `sdd-check`). Комментарий/тест может врать про блокер. (LOG H7.)
- [ ] **Гейт не warn-слеп?** `sdd-check` даёт exit 0 при живых warn (`SDD_MISSING_TASK_ID`,
      `SDD_TRACKER_MISSING_ROW` на v1). Зелёный ≠ готово. (LOG H7/H8.)

## Часть 2 — Разбор поведения по осям (что улучшало / что ухудшало)

Для каждой оси: сигнал «плохо» в трассе → проверенное правило. Мерить по трассе (`.sdd-eval-trajectory.*.json`):
histogram тулов, порядок, тайминги, кол-во edit, чекпоинты.

### A. Понимание агентом что делать (vs реверс словаря)

- [ ] **Есть ли `rg`/`grep` по `REQUIRED_SECTIONS|SDD_[A-Z]`?** Это реверс v2-словаря — фатальный
      деградатор. Правило: явно запретить грепать, действовать на findings тулов. (LOG H6: baseline 43
      вызова, 0 edit, оба чекпоинта red.)
- [ ] **Понимает ли агент, где СТОП?** Дочитывает ли `sdd-check` до конца как «готово», не сделав
      `ids`/`move`? Считает ли backlog (`SDD_SPEC_SECTION_MISSING` для секций, которых не было в v1) за
      работу и чинит недостижимое? Правило: done-оракул = `sdd-state` FLOW_VERSION=v2, а остаток —
      backlog, не трогать. (LOG H8-diag: v2 достигнут @~260с, затем ~500с впустую на недостижимых секциях.)

### B. Упрощение флоу (меньше церемонии/шагов)

- [ ] **Есть ли router/skill-цепочка в преамбуле?** `root→scope→router` перед работой = фатально.
      Правило: для известной фазы идти прямо на её директиву, без цепочки. (LOG B4: router-chain сам по
      себе достаточен для провала; V2 без него — PASS, reason 68249→334.)
- [ ] **Названы ли ВСЕ шаги операционного костяка, а не половина?** Назвать половину (plan/anchors, но не
      ids/move) хуже, чем ничего: агент считает половину полным флоу. Правило: либо весь костяк, либо
      целиком доверить директиве. (LOG H8: промпт не называл ids/move → агент их не звал.)

### C. Сокращение работы тулов/шагов

- [ ] **Много ли лишних `bash`/повторных `sdd-check`/`plan --verify`?** Итерации по гейту — норма, но
      цикл без прогресса — нет.
- [ ] **Не «думает вслух» ли в headless?** Discovery/interview в headless — чистый расход (×4 total, ×50
      reason). Правило: в headless убрать интервью/размышления. (LOG B4 V4.)
- [ ] **Физический бюджет стоит?** Без него один прогон улетает в 58 мин/576k токенов. Правило: всегда
      `budgetMs`; ≤5 мин для простой миграции — целевой потолок-килл. (LOG H6.)
- [ ] Помни: **~93–95% токенов — это INPUT (чтение директив/контекста) + reasoning, ~5% — вывод.** Рычаг
      экономии — сократить ЧТЕНИЕ, не выхлоп. Формулировка промпта (терсер) — НЕ рычаг (в пределах шума).
      (LOG «Разбор токенов»; H3.)

### D. Подсказка фактом/траекторией (вместо прозы для декода)

- [ ] **Даёт ли тул готовый факт (pre-filled map), или агент его реконструирует?** Предзаполненный
      Section Map убрал реверс словаря — `specs-clean` green на всех ярусах. Правило: перенести факт в
      тул (карта/трасса), а не заставлять агента выводить его грепом. (LOG H6-ladder.)
- [ ] **Аксиома или шаг?** Пассивную аксиому, которую агент должен «вспомнить», превращать в активный STEP
      с `<ToolCall owner="this-step">`. (LOG H4/H5 — explicit steps в выигрышной V2/V10.)
- [ ] Осторожно: **механический эмиттер помогает, только если бьёт по гейту.** Meta-эмиттер оказался
      ортогонален `plan-verified` (разные коды) —но effect. Сначала проверь, что код находки и код гейта
      пересекаются. (LOG H7.)

### E. Злоупотребление ленивой подгрузкой шагов

- [ ] **Перечитывает ли директивы/спеки повторно?** Повторное чтение цепочки директив до первой правки =
      фатально (22 тула, artifact=none). Один разовый `SKILL.md` — терпимо. Чтение существующих `specs/`
      когда скоуп есть — законная стоимость, не абьюз. (LOG H5/B4 V5/S1.)

### F. Дисциплина правок (много edit vs один write)

- [ ] **Один `Write` или churn из мелких `edit`/re-read?** Выигрышный рецепт — один Write в целевой файл
      (msgs 5, reason 334) против baseline 20 msgs без единой записи. (LOG H5.)
- [ ] **Заполнение шаблона: read + один перезаписывающий `Write`, а НЕ куча точечных `edit`.** Когда
      агенту дан скаффолд/шаблон и его надо заполнить, плохой паттерн — серия мелких `edit` по одному
      полю/секции: лишние тулы, риск рассинхрона разметки/секций, медленно. Правило: **прочитать файл
      целиком и перезаписать одним `Write`** с полностью заполненным содержимым. Сигнал в трассе: ≥3
      `edit` подряд по одному и тому же файлу-шаблону. (Наблюдение оператора; согласуется с выигрышем
      «один Write» — LOG H5.)
- [ ] **Растёт число edit — это хорошо или брутфорс?** 0→13 edit — хороший знак ТОЛЬКО если не ценой
      576k/58мин. Мерить edit вместе с бюджетом. (LOG H6 H1.)

## Часть 3 — Построение следующей гипотезы

- [ ] **Одна мутация за прогон.** Смешал две — не атрибутируешь эффект. Отдельный worktree на вариант;
      общий `dist`/`--gennady-root`, если меняется только текст промпта. (LOG §Воспроизводимость; 07-EXPERIMENTS §2.)
- [ ] **Критерий победы объявлен и утверждён ДО прогона.** Для миграции primary = `flow-v2`
      (FLOW_VERSION=v2, end-state), а не `plan-verified` (внутренняя согласованность слоя — зеленеет и на
      непроведённой миграции). Мерить исход, не набор тулов. (LOG H8-diag; H6 «Критерий победителя».)
- [ ] **Мутируем на ЛУЧШЕМ прогоне, не на сломанном baseline.** (LOG H6.)
- [ ] **Механика первична, судья вторичен, само-оценка агента — никогда.** (07-EXPERIMENTS §4; 10-QUALITY-RULES.)
- [ ] **Оба исхода в журнал** (и «сработало», и «нет»), отвергнутые пути — в архив, чтобы не повторять.
      Отвергнутое заносить в ledger. (07-EXPERIMENTS §6.)
- [ ] **Правильная единица eval.** Тяжёлый реальный репо не влезет в бюджет простого прогона — бери
      минимальный фикстур под конкретную гипотезу. (LOG H6 «Ключевой вывод».)
- [ ] **Приоритет рычагов (из истории):** сначала убрать церемонию/router-chain и реверс словаря (ось A/B —
      дают ×12–×200 по reason); затем перенести факты в тул (ось D); затем done-оракул/стоп-условие (ось A);
      формулировку промпта НЕ трогать как рычаг (шум).
