# Результаты и состояние eval-ов

eval — это проверка: даём модели задачу и смотрим, пройдёт ли она шаг разработки сама, в одноразовой
песочнице. Ниже — какие проверки есть, в каком они состоянии и с какими числами (время, число действий
модели, израсходованные токены). Числа восстановлены из журнала OpenCode по реальным прогонам —
«типичный прогон» = медиана по всем прогонам этого eval.

## Учебные проверки

Гоняются на выдуманных задачах (фикстуры создаются с нуля).

| Проверка              | Что модель должна сделать                       | Прогонов | Действий | Время    |  Токенов | Состояние                            |
| --------------------- | ----------------------------------------------- | -------: | -------: | -------- | -------: | ------------------------------------ |
| `fibonacci-library`   | По короткому описанию написать спецификации     |       36 |       74 | ~15 мин  | ~191 000 | Проходит: спеки без ошибок структуры |
| `tic-tac-toe`         | По готовым спекам составить список задач        |        7 |       71 | ~17 мин  | ~233 000 | Проходит                             |
| `slugify-toolchain`   | Взять готовую задачу и выполнить: код + тесты   |        4 |      114 | ~7 мин   | ~180 000 | Проходит до конца, тесты зелёные     |
| `broken-specs-repair` | Найти и починить одну ошибку, внесённую в спеку |        4 |       15 | ~2 мин   |  ~44 000 | Проходит                             |
| `infra-log-summary`   | Написать bash-скрипт: сводка по логам           |        1 |       10 | ~2 мин   |  ~32 000 | Один прогон                          |
| `infra-rotate-logs`   | Написать bash-скрипт: ротация логов             |        1 |        8 | ~1.5 мин |  ~14 000 | Один прогон                          |
| `infra-makefile`      | Написать Makefile по описанию                   |        1 |        7 | ~1 мин   |  ~11 000 | Один прогон                          |

«Действий» — сколько раз модель вызвала инструмент (запуск команды, чтение файла, правка). «Токенов» —
сколько израсходовала за прогон.

**Полный проход насквозь** (написать спеки → составить задачи → выполнить) прогонялся на `fibonacci`
как цепочка: спеки ~15 мин / 191 000 токенов → задачи ~13 мин / 281 000 → выполнение ~12 мин / 256 000.
Проходит до конца — это главный положительный результат по учебным проверкам.

Кроме перечисленного, было ещё ~90 прогонов-вариантов (другие промпты и фикстуры) — это проверки
гипотез, а не отдельные eval-ы; они разобраны в [`EXPERIMENTS-LOG.md`](./EXPERIMENTS-LOG.md).

## Проверки на реальном проекте cloud-ios

Здесь числа сохранены по каждому прогону.

### Восстановление удалённого скрипта в iOS-проекте cloud-ios

В настоящем iOS-проекте cloud-ios есть рабочий скрипт `Tools/check-swiftlint-exceptions.sh` — он следит
за исключениями из правил линтера SwiftLint (какие нарушения стиля в коде официально разрешены). Для
проверки этот скрипт **удалили** и попросили модель воссоздать его заново из спецификации (тикет
`IB-script`). Смотрим, восстановит ли флоу рабочий файл по одному описанию.

Во всех прогонах модель **писала** скрипт, но задачу до конца не доводила (не закрывала тикет).

### Как читать эти 14 прогонов

Кроме автопроверок, каждый прогон оценивал ещё и **автоматический проверяющий на базе модели**. Он не
принял ни один из 14 прогонов cloud-ios. Поэтому числа выше показывают **не «успех», а как шёл процесс**:
сколько модель работала, сколько действий и токенов потратила. Польза этих прогонов — в том, что каждый
провал указал на конкретный дефект, который потом починили.

## Оговорки

- Числа восстановлены из журнала OpenCode по реальным прогонам; «типичный прогон» для учебных проверок —
  это медиана по всем прогонам этого eval (разброс между прогонами заметный).
- Для учебных проверок сохранены расход и время, но **не** итоговый вердикт каждого прогона отдельно —
  состояние («проходит») взято из сводного разбора в [`PROGRESS-REPORT.md`](./PROGRESS-REPORT.md).
- Для cloud-ios сохранён каждый прогон; итоговую оценку автоматического проверяющего не прошёл ни один.
