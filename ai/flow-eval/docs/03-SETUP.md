# Предпосылки перед прогоном

Что должно быть готово ДО первого `npm run sdd-flow-eval`. Устройство харнесса —
[`02-ARCHITECTURE.md`](./02-ARCHITECTURE.md); полная процедура запуска (env, порты, живой прогон) —
[`04-RUNNING.md`](./04-RUNNING.md). Здесь — только чек-лист «готово / не готово» и правило `~/Developer/`.

## 0. ЖЁСТКОЕ ПРАВИЛО МОДЕЛИ (нарушение = фатально)

- **Единственная модель прогона eval — `llm-proxy/deepseek-v4-flash`** (ds4-flash от `llm-proxy`).
  Любое отступление — другой провайдер (в частности `provod`), другая модель — **ФАТАЛЬНОЕ НАРУШЕНИЕ**.
  Сравнимость журнала и всех A/B держится на одной и той же модели; смена модели обнуляет результаты.
- **Если `llm-proxy/deepseek-v4-flash` недоступен** — сделать **не более 5 попыток**, затем
  **ОСТАНОВИТЬСЯ и сообщить оператору**. НЕ переключать модель, НЕ импровизировать, НЕ «подобрать замену».

## 1. Node/npm и сборка

Харнесс исполняется через `tsx` внутри репозитория gennady; отдельная установка не нужна, но песочница
получает **скопированный** `dist/**` (`materializeLocalCli` в `provision.ts`) — значит, свежая сборка
обязательна перед КАЖДЫМ прогоном после правок кода:

```bash
npm run build
```

Если менялись директивы/шаблоны (`ai/kit/templates/**`, `templates.ts`) — ещё и:

```bash
npm run build:directives
```

Без пересборки песочница получит старый код/директивы и результат будет недостоверным.

## 2. OpenCode HTTP-сервер

Харнесс не поднимает OpenCode сам — сервер должен уже слушать порт до запуска `sdd-flow-eval`.

| Что              | Значение                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------ |
| Команда          | `opencode serve --hostname 127.0.0.1 --port <PORT> --log-level WARN`                             |
| Порт             | ≥ 4097, не `4096` и не порт личного OpenCode Desktop оператора                                   |
| `--pure`         | НЕ использовать — серверу нужен `~/.config/opencode/opencode.json` с провайдером `llm-proxy/...` |
| Проверка живости | `curl --fail http://127.0.0.1:<PORT>/health`                                                     |

`--base-url` харнесса указывает именно на этот сервер. Полный алгоритм выбора порта, ожидания
готовности и остановки — в [RUNBOOK «Подготовка»](./04-RUNNING.md#подготовка).

## 3. LLM-proxy

Модель ходит не к провайдеру напрямую, а через LLM-proxy. До запуска убедиться, что окружение содержит
адрес и ключ, не печатая значения:

```bash
for name in LLM_PROXY_BASE_URL LLM_PROXY_API_KEY; do
  test -n "$(printenv "$name")" || { echo "$name is missing" >&2; exit 1; }
done
```

Если переменной нет — остановиться и сообщить оператору; значения нельзя выдумывать.

## 4. Правило `~/Developer/` для внешних репозиториев

Эвалы, которые работают на **своём внешнем репозитории** (round-trip/migration, см.
[08-EXTERNAL-REPO.md](./08-EXTERNAL-REPO.md)), ожидают, что этот репозиторий лежит
под `$HOME/Developer/<repo>` — как обычный клон или как git worktree.

**Почему именно так:** скрипты (`roundtrip-eval.sh`, `migration-eval.sh`) и вспомогательные инструменты
(`session-metrics.py`, `session-telemetry.py`) используют фиксированные абсолютные пути и предполагают
единое расположение для всех репозиториев на машине оператора. Репозиторий вне `~/Developer/` — это
верный путь к:

- рассинхрону между тем, что видит скрипт, и тем, где реально лежат тикеты/спеки;
- конфликту с уже настроенными путями (`REPO`, `GEN_ROOT`) в других запусках/скриптах;
- неочевидным сравнениям в non-regression-метриках (`session-metrics.py compare`), которые читают
  фиксированный путь фикстуры.

**Что произойдёт, если правило нарушено:** `roundtrip-eval.sh` и `migration-eval.sh` проверяют `REPO` в
самом начале каждой подкоманды через `ai/flow-eval/scripts/require-developer-repo.sh` и завершаются с
ненулевым кодом и понятным сообщением на русском, ЕЩЁ ДО того как что-либо создать или изменить.

**Как починить:**

```bash
# либо настоящий клон/worktree под ~/Developer/
git clone <url> ~/Developer/<repo>
# либо, если репозиторий уже существует в другом месте — симлинк
ln -s /актуальный/путь/к/<repo> ~/Developer/<repo>
```

После этого повторить прогон — путь снова подставляется автоматически (`REPO="${REPO:-$HOME/Developer/<repo>}"`
в скриптах).

## 4a. Гигиена внешней фикстуры (E-16)

`migration-eval.sh`/`roundtrip-eval.sh` держат свою рабочую копию (`$FX`/`$RT`) под
`$HOME/.gennady/eval/<repo>/**` — вне репозитория gennady и вне `~/Developer/` (это НЕ репозиторий, а
git worktree-фикстура). Перед тем как доверять такой фикстуре (перед E-06/E-07/E-08/E-10 или ручным
прогоном), проверь:

```bash
ai/flow-eval/scripts/check-fixture-hygiene.sh "$FX"   # или "$RT" / любой другой путь фикстуры
```

Exit 0 (тихо) значит: (а) `git status --porcelain` пуст — фикстура воспроизводима из своего base SHA
без ручных правок, оставшихся с прошлой сессии; (б) в дереве нет файлов класса секретов (`.netrc`,
`.npmrc`, `.env*`, `credentials*`, `id_rsa*`, `*.pem`, `*.p12`, `*.keystore`, `application_default_credentials.json`).
Ненулевой exit печатает, что именно не так. Both-way доказательство логики проверки — хермет
(без внешнего репозитория) тест `ai/flow-eval/scripts/__tests__/check-fixture-hygiene.test.ts`.

Скрипт не встроен как блокирующий шаг внутрь `reset_fixture()`/`prep()`: секретный файл может быть
частью самой истории внешнего репозитория на нужном base-коммите (найдено `Tools/Artifactory/.netrc` —
L-13), и жёсткая блокировка сломала бы прогон целиком независимо от новой драйф. Это диагностика для
оператора, не автоматический бар.

## 5. Чек-лист «готово к прогону»

```bash
git status --short          # рабочее дерево worktree чистое
npm run build                # свежий dist
npm run test:sdd-flow-eval   # фейк-бэкенд тесты харнесса зелёные
curl --fail http://127.0.0.1:<PORT>/health   # OpenCode сервер отвечает
```

Продолжать можно только если все четыре пункта выполнены. Дальше — [RUNBOOK «Живой прогон»](./04-RUNNING.md#живой-прогон).
