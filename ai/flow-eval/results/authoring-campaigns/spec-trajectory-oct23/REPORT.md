# Спецификации: свежий наблюдаемый baseline и следующие гипотезы

## Решение

**Сокращение production-инструкций пока не принимаем.** Здесь сняты 30 новых прогонов на текущем
main, а не переиспользованы старые 30 модульных экспериментов. Найдены конкретные точки лишнего
поиска и объединения инструментов, но экономия от изменений ещё не измерена. В первоначальной
[матрице](../../../docs/AUTHORING-HYPOTHESIS-MATRIX.md) было семь гипотез; после ревью добавлены
ещё четыре независимых предложения. Ни одно не объявлено проверенным или принятым.

Сначала устранить ошибки измерения и неоднозначность задачи infrastructure; затем сравнивать
каждую гипотезу с контролем на одинаковом оценщике. Исправление оценщика не является улучшением
траектории агента. Не переписываем старые RED в GREEN.

### Исправление воспроизводимости после ревью

Первоначальный PR ошибочно не отслеживал30 `cli.log`: общий ignore исключал их, хотя первичный
манифест требовал эти байты. Локальная hash-проверка поэтому не доказывала переносимость. Сохранены
те же исходные логи через узкое campaign-scoped исключение; их SHA/размеры совпадают с прежним
манифестом. Новый тест требует manifest-файлы в Git index и отдельно моделирует отсутствие одного
лога. Данные/манифест/оценки не перегенерированы. Дополнительное условие передачи на ревью — полный
offline-прогон на чистой выкладке из Git без копирования локальных raw/ignored-файлов.

Приоритеты и ограниченность внешних исследований уточнены в
[primary-source notes](../../../docs/AUTHORING-RESEARCH-NOTES.md). Строгая path-квалификация и
known-label проверки предшествуют заявлениям об улучшении траектории; результатов новых A/B ещё нет.

## Условия и проверяемость

- Чистый main `056870393ea2138a9470b7ef6188a01dc7885f81`, Flash-only
  `llm-proxy/deepseek-v4-flash`; OpenCode 1.17.15, Node 22.19.0, concurrency=3.
- Десять типов × три попытки. План и collector заморожены **до** первого вызова модели.
  Бюджеты автора/оценщика/рефлексии разделены. Все ошибки сохранены, пересэмплирования нет.
- Снимался изолированный template-to-artifact сценарий, не весь интерактивный SDD-flow.
  Ни шаблоны, ни директивы продукта во время baseline не менялись.
- Полные первичные JSON/документы/judge/reflection/CLI-логи: [raw/](./raw/).
  Порядок case→raw-number: [mapping.json](./mapping.json). SHA-256 первичных файлов:
  [primary-manifest.json](./primary-manifest.json); условия: [protocol.json](./protocol.json).
- Source journal был read-only, чтобы 30 отдельных CLI-процессов не загрязняли исходник.
  Предупреждение EACCES относится к необязательной записи stub в этот журнал, **не** к работе
  агента или сохранению результата. Эти первичные записи и отчёт заменяют stub журнала.
- Collector/exporter сохранены как инертные `.mjs.txt`: это историческая запись условий,
  не команда для запуска с уже удалёнными временными путями. Offline replay этих путей не читает.

## Исходное качество, без улучшений задним числом

Формат/факты: **26/30**; семантический оценщик: **21/30**; оба одновременно: **20/30**.
Это не 20 полностью принятых SDD-траекторий: отдельная строгая path-проверка остаётся **0/30**.
Один worker-error — запрещённый поиск реализации в установленном пакете, не отказ прокси.
Все 30 tool capture/source/model/cleanup bindings полные; классификация opaque Bash неполная.

## Что происходит в траекториях

Подробный порядок **каждого** вызова во всех 30 попытках — [TRAJECTORIES.md](./TRAJECTORIES.md).
Там есть инструмент, роль наблюдаемой операции (не угаданное намерение), путь/безопасная команда,
статус/exit, вызовы проверок, чтения директив и форматов, повторные чтения и неизвестные места.
Идентификаторы/тайминги/message grouping сохранены в [report.json](./report.json).
Тело shell-программы и потенциально секретные аргументы в проекции скрыты; первичные безопасные
траектории сохранены отдельно. Чтения через Bash не превращаем в выдуманные native Read.

- **Portal:** owner + portal-format + существующие scope/module/contract-факты, создание,
  whole-write, иногда readback. Повторное чтение после записи не доказывает лишнюю церемонию.
- **Product:** поиск runtime-backing/fold-объяснений по именам аксиом/диагностик.
  В r1 поиск в `node_modules/gennady/dist` остановлен evaluator boundary; r2/r3 дошли до документа,
  но positive/negative предусловия требований конфликтуют. Это сильнее, чем гипотеза «слишком
  длинный prompt»: полезных локальных инструкций может не хватать.
- **Library:** r1/r2 потеряли declared dependency относительно портала; дополнительное чтение
  root/portal не гарантировало правильный результат. Нужен контроль графа, не только меньше текста.
- **Infrastructure:** r1 принят, r2/r3 отклонены оценщиком. Причина out-of-scope ownership в r2
  спорна: зависимый tooling-provider не автоматически родитель всех требований потребителя,
  а task brief сам требует normalizer intent для выбранного вида. Нужна калибровка task/ownership
  fit, а не объявление всех таких отказов дефектом агента. Raw вердикты оставлены как есть.
- **Interface:** смысл принят 3/3, однако в r2 наблюдается Python shell-перезапись ID и финальный
  compound check. Это уже конкретная операция, а не только неизвестный side effect.
- **Modules:** наиболее дорогие чтения owner/entity/DbC/shape/grammar плюс проверки и поиски
  authoring-receipt. В nested-r1 выявлено противоречие области positive и negative требований;
  flat-r2 — отдельный ложный отказ оценщика, описанный ниже.
- **Indexes:** в некоторых попытках контекст расширяется до router, соседних форматов и
  task-ticket structure. Например module-index-r2 читает router и ticket structure при задаче
  только на index. Это наблюдаемая точка для исследования lazy lookup, не доказанное лишнее чтение.

Native Read — лишь часть загрузок: `sed`/`rg` внутри Bash тоже возвращают контекст.
Несколько Read могут идти в одном assistant message (portal-r1, вызовы 6–8). Поэтому уменьшить
число инструментов не означает автоматически уменьшить model/API round trips.
Рефлексия сохранена в 29/30 попытках; у worker-error её нет. Это self-report для гипотез,
не доказательство причин и не подмена внешней оценки. Приватные рассуждения не собирались.
Не все ссылки в ответах автора валидны: неизвестные cited call IDs есть в product-r2 (10),
product-r3 (1), project-index-r3 (1). Поэтому саморефлексию проверяем по реальной трассе,
не принимаем её объяснения или цитаты автоматически.

SDK `cost=0` **не означает бесплатно**. Денежный счёт и HTTP-retries внутри AI Proxy неизвестны.
SDK REST-счётчики включают polling/config/session, поэтому не выдаём их за inference API calls.
Все роли использовали Flash; fallback на Pro отсутствовал. Расход оценщика/рефлексии — цена
исследования, а не стоимость только production-authoring. Полные input/output/reasoning/cache
счётчики по ролям есть в JSON; численный reasoning counter — не текст рассуждений.

## Найденные ошибки измерения и исправления

1. У нового отчёта отсутствующие REST-измерения ошибочно становились нулём; исправлено в unknown.
2. Отчёт сверяет наблюдаемые `usage.models` всех доступных ролей, не только requested-model label.
3. **Flat-r2:** «спека ожидает операторского approval» не распознавалось как pending. Добавлен
   versioned `calibrated-v2` с регрессией на реальном документе и negative controls для отрицания
   ожидания/выдуманного granted approval. Явный historical `calibrated` остаётся неизменным;
   raw15/summary.json и таблица выше **не** перекрашены. Это исправление измерителя, не агента.
4. Path oracle fail-closed на opaque Bash. Полный capture не равен доказанному whole-write-only пути.
   Не ослабляли его ради зелёного результата. Для combined tool надо сначала версионировать
   эквивалентные механические факты в обеих сравниваемых ветках; нельзя требовать лишний Read
   только ради старого имени инструмента или принять exit-0 compound shell как готовый receipt.
5. Portal-r2 и infrastructure-r2 требуют known-label калибровки смыслового оценщика: в первом
   отрицательные ограничения явно приведены рядом с общей Vision, во втором запрет provider-scope
   не обязательно ограничивает требования потребителя. Raw FAIL не отменяем, но и не объявляем
   их доказанными agent-only дефектами на основании одного judge rationale.

Новый oracle означает новую matched A/B пару. Эти 30 траекторий — свежая наблюдаемая отправная
точка для анализа расходов, но не автоматически квалифицированный контроль для нового oracle.
Три повтора показывают разброс на данных задачах, не доказывают статистическую эквивалентность.

## Следующая последовательность, без разворота общего дизайна

1. Measurement prerequisites: отдельно проверить infrastructure task/ownership fit и применимость
   path proof. Новые criteria/version фиксировать до запусков, старые raw сохранять.
2. I1, затем I2 по одному: self-contained runtime/fold guidance вместо reverse lookup словаря.
   Учитывать добавленные локальные bytes вместе с фактическим расходом, не обещать заранее экономию.
3. T1/A1/S1 по отдельности: сокращение manifest-дублей, wording аксиомы, порядок существующей
   инструкции. Полный смысл/активация/история/approvals/валидаторы не удаляются.
4. B1/B2: create+context и выбранный batch-read — только после доказательства полного
   эквивалентного результата и совместимости с host Read-before-Write guard (это пока неизвестно).
5. Успех — меньше суммарного расхода при отсутствии деградации качества и роста tool/model calls
   **по каждому** затронутому case; общий средний выигрыш не скрывает проигранный case. После
   pilot нужны holdouts и full-flow интеграция; production-изменения идут отдельным ревью.

## Очистка и воспроизведение

[cleanup-final.json](./cleanup-final.json): все 30 временных рабочих каталогов и owned SDK sessions
очищены; собственный OpenCode server остановлен, временный source worktree/root удалены.
Остались ограниченные первичные доказательства и отчёты, не бесконечные sandbox/cache-копии.
Чужие сессии/серверы/checkouts и shared dependency store не очищались.

node --import tsx ai/flow-eval/scripts/authoring-baseline-report.ts \
  --input ai/flow-eval/results/authoring-campaigns/spec-trajectory-oct23/input.json

Offline replay проверяет SHA-256 первичных файлов, bindings, сохранность неудач и точное
воспроизведение JSON/Markdown-отчётов; не обращается к модели, прокси или удалённому tmp.
Визуального артефакта нет — это backend/CLI без UI.
