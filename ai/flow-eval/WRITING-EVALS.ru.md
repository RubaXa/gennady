# Как написать свой eval для SDD flow-harness

Гайд для разработчика, который хочет **добавить новый eval-сценарий** (проверить, проходит ли модель
какую-то фазу/ситуацию SDD как обычный разработчик). Предполагает, что ты уже прочитал
[`README.md`](./README.md) (что это и как устроено) и [`RUNBOOK.ru.md`](./RUNBOOK.ru.md) (как
запускать). Ничего из этого гайда не требует знания истории конкретной сессии.

---

## 0. Модель в одну фразу

Один **сценарий** = (какую фазу SDD проверяем) × (в какой стартовой **фикстуре** = подготовленный
git-репозиторий). Runner поднимает worker-сессию OpenCode, наблюдатель следит за прогрессом по
ограниченному хвосту, отдельный **judge** выносит вердикт. Твоя работа — описать сценарий и, если
нужно, подготовить фикстуру, в которой этот сценарий вообще **выполним**.

---

## 1. Форма сценария (`SddEvalScenario`)

Источник истины — `types.ts`. Сценарии живут в `scenarios.json` (или в своём JSON-файле).

| Поле         | Обяз. | Значения                                                                           | Смысл                                                                                                                                       |
| ------------ | ----- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`         | да    | строка                                                                             | Стабильный идентификатор (в отчётах и координации параллельных прогонов).                                                                   |
| `phase`      | да    | `spec-authoring` \| `scaffold` \| `execute`                                        | Какую фазу SDD проверяем. Runner никогда не сваливается в «просто кодинг».                                                                  |
| `mode`       | да    | `full-spec-to-approval-1` \| `actual-tickets-to-approval-2` \| `canonical-execute` | Режим внутри фазы (граница approval).                                                                                                       |
| `intent`     | да    | строка                                                                             | Задача, которую видит worker; **дословно** уходит и в judge.                                                                                |
| `fixture`    | нет   | `SddEvalFixtureId`                                                                 | Встроенная фикстура (провижнится в изолированный temp-каталог). Без неё нужен `directory`.                                                  |
| `directory`  | нет   | путь                                                                               | Рабочий каталог сессии, если не используешь встроенную фикстуру.                                                                            |
| `scale`      | нет\* | `product` \| `module` \| `function` \| `fix`                                       | \*Обязателен для `spec-authoring`: синтетически «подтверждённый оператором» масштаб, чтобы headless-worker не выдумывал и не переспрашивал. |
| `acceptance` | нет   | строка                                                                             | Точные критерии (числа, негативные кейсы) для judge — он их видит отдельно от `intent`. **Настоятельно рекомендуется.**                     |

Соответствие фаза↔mode (сейчас 1:1):

- `spec-authoring` → `full-spec-to-approval-1` (написать спеки, остановиться перед Approval #1)
- `scaffold` → `actual-tickets-to-approval-2` (создать задачи, остановиться перед Approval #2)
- `execute` → `canonical-execute` (реализовать утверждённую задачу, подтвердить receipt-проверками)
- `repair` → `fix-to-clean` (в воркспейсе спеки, которые падают `sdd-check`; довести проверку до clean, чиня каждую находку по её тексту)

`phase`, `mode`, `SddEvalFixtureId` — **закрытые union-типы** в `types.ts`. Новое значение любого из
них надо сначала добавить в тип, иначе TypeScript/сборка не пройдут.

## 2. Анатомия фикстуры (`provision.ts` → `FIXTURE_FILES`)

Фикстура — это `Record<путь, содержимое>`, которую `provisionScenarioDirectories()` материализует в
изолированный git-репозиторий (свой на каждый сценарий), коммитит одним baseline-коммитом и
привязывает к нему собранный SDD (`dist/**`, `ai/**`, снапшот CLI).

Обязательный каркас любой фикстуры:

| Файл                        | Что кладём                          | Зачем                                                          |
| --------------------------- | ----------------------------------- | -------------------------------------------------------------- |
| `.gitignore`                | `REAL_GITIGNORE`                    | `coverage/`, `node_modules/`, `dist/` вне коммита.             |
| `tsconfig.json`             | `REAL_TS_CONFIG`                    | ES2022/NodeNext/strict/noEmit.                                 |
| `package.json`              | скрипты + `devDependencies: { c8 }` | см. §3 (правила coverage-выполнимости).                        |
| `scripts/test.mjs`          | `REAL_TEST_RUNNER`                  | `node --test` по `src/**/*.test.ts` (glob **внутри** скрипта). |
| `scripts/test-coverage.mjs` | `REAL_COVERAGE_RUNNER`              | c8 + `node --test` → `coverage/coverage-final.json`.           |
| `inputs/brief.md`           | текст брифа                         | То, из чего worker авторит спеки.                              |
| `specs/README.md`           | портал-таблица скоупов              | Точка входа спек.                                              |

Опционально — **предзасеянные спеки** через генераторы (для фаз scaffold/execute, где спеки уже
должны существовать):

- `canonicalScope(scope, ACR, module, operation)` — скоуп-спека с якорями секций.
- `canonicalModule(scope, ACR, module, operation, sourceFile)` — модуль-спека.
- `canonicalTask(...)` / `canonicalModuleIndex(...)` — тикет и трекер-индекс с записями Approval #2.

Эталонные фикстуры отличаются глубиной засева:

- **`fibonacci-library`** — минимум (только портал + бриф) → для `spec-authoring`.
- **`tic-tac-toe`** — засеяны скоуп+модуль-спека → для `scaffold`.
- **`slugify-toolchain`** — засеяны спеки + тикеты (с Approval #2) → для `execute`.
- **`broken-specs`** — структурно полные спеки с одним намеренным дефектом (невалидный mermaid) → для `repair`: проверяет, чинит ли воркер по тексту ошибки валидатора (без инструкций «как писать» в промпте).

Выбирай глубину засева под фазу: фаза проверяет ШАГ, а всё «до» него должно быть готово в фикстуре.

## 3. Что делает фикстуру ВЫПОЛНИМОЙ (правила coverage — критично)

Самая частая причина, по которой свежая фикстура «не проходит не по вине модели» — **coverage-гейт
структурно невыполним**. Правила (проверены на практике, залочены `fixture-coverage.test.ts`):

1. **c8 должен провижниться в песочницу.** Это делает `materializeLocalCli(dir, root, /*includeCoverageProducer*/ true)` — сейчас включено для всех фикстур. Без c8 `npm run test:coverage` не создаёт `coverage-final.json`, и гейт недостижим оффлайн.
2. **`package.json` объявляет `c8` в `devDependencies`.**
3. **Скрипт `test:coverage` должен быть fingerprint-безопасным = БЕЗ glob-токенов.** Receipt фазы фингерпринтит каждый путь-токен в verification-скриптах и **отвергает glob** (`shared/common/repo-path.ts`). Поэтому inline-команда вида
   ```json
   "test:coverage": "c8 --include=src/**/*.ts … node --test src/*.test.ts"
   ```
   **ломает `sdd-verify`** (glob `src/**/*.ts` не разбирается при валидации receipt).
   **Решение:** прячь glob внутрь `scripts/test-coverage.mjs` (один точный файл-токен) и объявляй
   ```json
   "test:coverage": "node scripts/test-coverage.mjs"
   ```
   Тикетная проверка `gennady testcov <src>` при наличии готового `coverage-final.json` **не
   передетектирует** команду, которая его создала.

Правило для новой фикстуры: **всегда** `scripts/test-coverage.mjs` (glob внутри) + `test:coverage`
одним файлом + `c8` в devDeps. Никогда не inline-команда с glob.

## 4. Контракт judge

Judge — изолированная сессия, видит **только** ограниченное evidence (`SddEvalJudgeInput`):
`intent`, `acceptance`, `diff`, `events`, `tail`, `state{status,stuck,waiting,errors}`. Не видит:
промпт worker'а, полный транскрипт, внутренности runner'а.

Контракт вывода (`judge.ts` → `parseVerdict`):

- **Первая строка** — ровно `VERDICT: pass` \| `VERDICT: fail` \| `VERDICT: inconclusive`.
- Дальше — краткое обоснование свободным текстом. Проза с «error/ошибка» НЕ роняет вердикт: он
  берётся только из явной строки. Нет явной строки → `inconclusive` (не ложный fail).

Следствие для автора: дай judge достаточный `acceptance` (числа, границы, негативные кейсы), иначе
он честно вернёт `inconclusive`.

## 5. Шаги: добавить новый eval

1. **Фикстура (если нужна новая):**
   - добавь id в union `SddEvalFixtureId` (`types.ts`);
   - добавь запись в `FIXTURE_FILES` (`provision.ts`) по каркасу §2 + правилам coverage §3;
   - при необходимости — предзасей спеки/тикеты генераторами под свою фазу.
2. **Сценарий:** добавь объект в `scenarios.json` (или свой JSON) по форме §1. Для `spec-authoring`
   не забудь `scale`. Заполни `acceptance`.
3. **Пересобери:** `npm run build` (обязательно — песочница получает `dist/**`; без пересборки поедет
   старый код). Если менял скелеты/шаблоны (`ai/kit/templates/**`, `templates.ts`) — ещё и
   `npm run build:directives`.
4. **Прогони** (см. RUNBOOK): один сценарий = отдельный JSON с одним объектом.
5. **Замерь двумя измерениями:** вердикт judge (стохастичен) **и** механика
   (`gennady sdd-check --all .`, для execute — `gennady sdd-verify --task <ticket> --phase <P>`).
   Механика — источник истины; расхождение judge с механикой = дефект харнесса/судьи, не флоу.
6. **Залочь детерминированное** юнит-тестом там, где фиксишь инструмент/фикстуру (пример:
   `fixture-coverage.test.ts`).

## 6. Частые грабли (проверено на практике)

- **Пересборка dist обязательна** после правок кода перед прогоном; переиспользуемая песочница держит
  свой dist с момента провижна (идемпотентный skip не перезальёт его) — для свежего кода бери свежий
  root (`mktemp -d`).
- **Батчи авторинга гоняй последовательно** (или ≤2 параллельно): каждый authoring-worker поднимает
  ещё и review-субагента, и N параллельных сценариев множат сессии на один тест-сервер → перегрузка и
  вырожденные прогоны (obs=1, «no messages»). Замер предсказуемости делай последовательно.
- **Бэктики в template-literal ломают `build:directives`** (`node --experimental-strip-types` строже
  tsx): не вставляй `` ` `` внутрь строк-скелетов в `templates.ts`.
- **Симуляция approval между фазами — правкой файлов, не UI** (eval headless): портал
  `specs/README.md` `🚧`→`✅` И записи Decision Log в спеках `Status:`/`Operator decision:`
  `pending`→`approved`. Только портал недостаточно — judge читает и Decision Log. Готовый помощник —
  `operator-approve.sh <sandbox>`.
- **`gennady sdd-state` / `sdd-check`** запускай из каталога песочницы (или с явным путём); не
  полагайся на cwd.
