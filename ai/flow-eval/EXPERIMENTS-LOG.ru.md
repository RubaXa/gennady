## Разбор токенов (базовый факт)

На прогонах repair/authoring **~93–95% токенов — это ВХОД (чтение директив/контекста) + reasoning,
запись ~5%**. Т.е. главный токен-центр — чтение. (repair: in=25271/out=1984/reason=1737; authoring
baseline: in≈83k). Отсюда приоритет — сокращать чтение.

## Brownfield-набор (phase `brownfield`) — существующий код без спеки, маленькие ветко-изолирующие

Каждый eval изолирует ОДНУ ветку решений; объективный golden both-way; без установки зависимостей.

| Eval        | ветка                         | mode              | golden | total | in/out     | msgs |
| ----------- | ----------------------------- | ----------------- | ------ | ----- | ---------- | ---- |
| E-bf-delta  | добавить фичу в существ. код  | modify-code-delta | PASS   | 10104 | 9368 / 631 | 4    |
| E-bf-bugfix | найти+починить дефект по багу | fix-code-delta    | PASS   | 10454 | 9533 / 746 | 6    |

- **E-bf-delta** (ветка «добавить фичу»): рабочий spec-less `bin/report.sh` (2 строки: lines/words) +
  change-request «добавить `chars:`». Воркер прочитал код и сделал **минимальную дельту** (одна строка
  `wc -c`), сохранив формат и контракт ошибок. Объективный `golden/verify.sh` → **PASS**.
- **E-bf-bugfix** (ветка «диагностика+починка»): spec-less `bin/uniq-lines.sh` с дефектом (`sort|uniq`
  теряет порядок первого появления) + баг-репорт. Воркер нашёл причину и заменил на `awk '!seen[$0]++'`,
  сохранив контракт ошибок. Объективный `golden/verify.sh` → **PASS**. Это ДРУГАЯ ветка решений, чем
  E-bf-delta (не «дополнить», а «исправить неверное поведение») — потому отдельный eval.
- Both-way залочено: `brownfield-golden.test` 6/6 (по каждому fixture reference PASS + два негатива FAIL:
  no-op/не-починил и сломал-контракт/сломал-старое).
- Значимость: оба — самые дешёвые evals (~10k), дешевле инфры. Вход в существующий код дёшев, если задача
  локальна. R1(sdd-check) к brownfield НЕ применяется (нет спек), как и к `task` — грейдит только golden.
- Контракт ошибок усилен: golden требует не только non-zero на missing-arg, но и сам текст `usage`
  (иначе `set -e` даёт non-zero и при потерянном сообщении — негатив BUG_LOST_CONTRACT это ловит).
- Дальше (тяжёлые SDD-ветки, нужен полный flow → отложены после оптимизации): E-bf-recover
  (восстановление спеки из кода), E-bf-delta-to-spec (дельта→обновление спеки, путь B шаг 2),
  E-bf-via-spec (изменение через спеку, путь A).

## H3 — оптимизация промпта фазы `task` (words↔example), стенд E-infra-3, отдельный worktree

Изоляция: worktree `opt/task-prompt-ab` со своим `prompts.ts` (treatment), общий `--gennady-root`
(один dist/директивы) — меняется ТОЛЬКО текст фазового промпта. baseline на :4098, treatment на :4099.

- **baseline** (текущий `task`-промпт, ~70 слов): base-1 total=10926 (in=10123/out=773, msgs 5),
  base-2 total=10878 (in=9972/out=899, msgs 6). Среднее: **total≈10902, in≈10048, out≈836**. golden PASS×2.
- **treatment** (терсер ~45 слов + короткий пример bin-скрипта): terse-1 total=11355 (in=10234/out=1010),
  terse-2 total=10571 (in=9690/out=626). Среднее: **total≈10963, in≈9962, out≈818**. golden PASS×2.

**Вывод: разница в пределах шума** (input 10048 vs 9962; output 836 vs 818; диапазоны перекрываются,
N=2). Сжатие слов промпта + добавление примера дало НЕ-компрессию: пример съедает ровно то, что сэкономили
слова. Причина прямо из анатомии токенов (H2): фазовый промпт — ничтожная доля input; токен-центр — это
ЧТЕНИЕ (brief + фиксированный headless-контракт + вывод инструментов), а не формулировка промпта. Качество
(golden) сохранено в обоих плечах.

- **Что это значит для «можем ли сжать флоу»**: на уровне ФОРМУЛИРОВКИ промпта — нет, для дешёвых task-
  evals рычага нет. Реальный рычаг — сокращать ОБЪЁМ ЧТЕНИЯ (директивы/справочные форматы), и делать это
  на уровне инструмента (lazy-загрузка в директивной сборке), а не переписыванием слов. Это подтверждает
  и уточняет H2, теперь на объективно-грейдируемом (golden) стенде, а не на стохастичном authoring.
- **Обратная депурация (verbose)** не гонялась намеренно: терс-плечо уже показало, что промпт — не рычаг;
  тратить бюджет на многословный вариант низко-ценно (ожидаемо тот же шум). Оставлено как явная заметка.
- **Решение по worktree-модели**: вариант НЕ выиграл → в main-worktree (PR) НЕ впитывается, остаётся
  базовый промпт. Абсорбируется только победитель; здесь победителя нет — фиксируем отрицательный результат.

## H4 — оптимизация траектории тяжёлого флоу (≥10 вариаций), бед E-bf-recover

Мотивация: H3 показал, что на ДЕШЁВОЙ задаче промпт — не рычаг. Но E-bf-recover ДЕГРАДИРУЕТ (см.
ниже): reason=68249, msgs=20, спека НЕ создана → golden FAIL. Это идеальный бед: цель — довести
траекторию до артефакта (польза!) И/ИЛИ снизить reasoning/циклы. Метрики каждой вариации: golden
(создана ли адекватная спека), total, input, output, reasoning, msgs. Любой исход ценен — фиксируем,
что уводит в циклы/раздувает reasoning, а что даёт очевидную траекторию.

Оси (10 вариаций recover-промпта; dist общий, меняется только BROWNFIELD_MODE_PROMPTS['recover-spec']):

1. V1 baseline — текущий промпт.
2. V2 few-shot — + 1 короткий пример восстановленной спеки (шаблон разделов).
3. V3 явные шаги — нумерованный план (прочитай код → напиши specs/<name>/<name>.spec.md → стоп).
4. V4 меньше чтения — «читай только SKILL.md, не весь router; пиши спеку сразу».
5. V5 anti-loop — «не перечитывай директивы дважды; максимум ~6 шагов; сначала артефакт».
6. V6 точный путь — «создай specs/report/report.spec.md» (убрать неопределённость размещения).
7. V7 минимализм — без SDD-ceremony: «опиши поведение кода в specs/report/report.spec.md: разделы
   Behaviour + Functional Requirements (измеримые пункты)».
8. V8 рефлексия — «сначала перечисли наблюдаемое поведение списком, затем оформи в спеку».
9. V9 verbose (обратная депурация) — намеренно подробные инструкции (проверка на деградацию).
10. V10 combo — лучшее из V2/V5/V6/V7.

Правило: не жечь бесконечно; N=1 на вариацию (бед дорогой ~130k), при явном сигнале — добор N. Ветка
оптимизации — отдельный worktree, main впитывает только победителя.

надёжен. Это и есть «профитная экономика» для recover.

- **Причина ДОКАЗАНА транскриптом** (диагностический прогон baseline): агент последовательно читает

- V2 убирает ceremony: прочитать код → перечислить поведение → один Write в specs/<tool>/<tool>.spec.md,
  явный запрет читать router/directive chain. Прогон идёт — сравню artifact/reasoning/msgs.
