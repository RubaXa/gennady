# 71 — Гид ревьюера PR плана SDD v1 → v2

> Кому: любому ревьюеру PR в релизную ветку v2 (`codex/sdd-v2-rc52-followup`), включая akkrat и людей без контекста этого плана. Цель: за 15 минут понять, что должен закрывать PR, и проверить, что он это закрывает честно.

## 1. Откуда брать цели (порядок чтения, 20 минут)

| Шаг | Документ (ветка `sdd-v2-audit-migration-3b23b1`, PR #26) | Что даёт |
|---|---|---|
| 1 | `05-SUMMARY.md` §1–§2 | зачем v2 и что считается релизом, одной страницей |
| 2 | `01-INTERVIEW-DECISIONS.md` §1–5 + строки D-* | цели оператора и принятые решения; всё, что PR делает, должно упираться в цель или решение |
| 3 | `20-ISSUES-VERDICTS.md` | issues akkrat (#9.x, #17, #19–#24) с вердиктом «что требуется в v2» — самые конкретные внешние цели |
| 4 | `60-ACCEPTANCE.md` | критерии приёмки релиза A1–A24; каждый PR обязан назвать, какие критерии двигает |
| 5 | `62-BATCH-QUEUE.md` | пачка = PR: цель пачки одним абзацем, список задач словами, что доказывает |
| 6 | `06-ADEQUACY-GAP.md` §0, §3 и `_raw/research/R2-academic-review.md` §6 | почему план считается адекватным целям; принципы из внешнего ресёрча (детерминированный бар, один источник истины, патч вместо перегенерации, не завышать слова `proof`/`verified`) |

Правило: если в PR есть изменение, которое не выводится ни из цели интервью, ни из issue, ни из решения D-*, ни из строки доски `61-TASK-BOARD.md` — это расширение объёма, о нём надо спросить.

## 2. Что обязан содержать каждый PR (по D-57)

1. **Зачем**: какую проблему закрывает, откуда она (issue / аудит / перенос из v1), какой критерий приёмки двигает.
2. **Таблица «было → стало»** и таблица «файл → что изменилось по смыслу».
3. **Схема** «было → стало» для затронутого контура (mermaid).
4. **Доказательства**: команды с результатами и кодами выхода (тесты, `npm run check`, `sdd-check --all`, гейт «ноль новых ошибок»).
5. **Вердикт независимой проверки** (`_raw/V-BATCH-*.md`): что подтверждено, что было блокирующим, как закрыто.
6. **Честно о побочных эффектах и о том, что не сделано.**
7. **Предыстория / база**: если PR стоит поверх другого (стек), это сказано, и назван порядок мержа.

Если чего-то из семи нет — это уже замечание к PR, не к коду.

## 3. Четыре проверки ревьюера

**А. Трассируемость.** Каждый коммит → задача на доске (`61 §1`) → цель/issue/критерий. Спросить про любой коммит, который не находит места в этой цепочке.

**Б. Доказательства.** Перезапустить хотя бы одну команду-доказательство из описания и сравнить числа. Обязательный минимум: `npm run check` и `npm run gate:sdd-check-baseline` в ветке PR. Числа в описании должны сойтись с прогоном; расхождение — вопрос.

**В. Честность результата.** Искать признаки «покраски в зелёное»:
- правка v1-данных (`tasks/**`, `specs/**`) сверх названного в задаче ради снижения числа ошибок (запрещено решением D-39);
- изменение фотографии ошибок baseline (только решением оператора, D-38);
- рост списков исключений/allowlist (должны только сокращаться);
- `.skip`/`.todo`/ослабленные ассерты в тестах;
- слова `proof`, `verified`, `100%` там, где механизм проверяет только наличие или форму.

**Г. Принципы v2** (из ресёрча, `R2` §6): детерминированная проверка — бар, LLM-судья — диагностика; один источник истины (нет второго реестра рядом с первым); изменения патчем, а не перегенерацией всего; человеческий гейт сохраняется на hard stop.

## 4. Неудобные вопросы (задавать всегда)

1. Какую цель или issue закрывает этот коммит? Покажи строку доски.
2. Что случится у потребителя пакета, если этот PR не мержить?
3. Какой тест упадёт, если откатить именно этот коммит? Покажи.
4. Почему вырос список исключений / почему изменился baseline / почему тест стал мягче?
5. Это перенос из v1 или новая возможность? Если новая, где решение оператора?
6. Что не сделано и кто владелец остатка (задача на доске)?
7. Где слово «доказано» подтверждено механизмом, а где это самооценка исполнителя?
8. Почему число предупреждений/ошибок изменилось именно так? Разложи по кодам.
9. Есть ли в PR правки сгенерированных файлов руками (`ai/directives/sdd-v2/**` должны быть только перегенерированы)?
10. Что проверила независимая проверка, а что «не проверяемо» без живого прогона?

## 5. Удобные вопросы (экономят время)

- Какой один файл смотреть первым, чтобы понять суть?
- Какие три числа должны сойтись при моём прогоне?
- Что можно проверить руками за пять минут (одна команда, ожидаемый вывод)?
- Какой порядок мержа, если PR стоит в стеке?

## 6. Форма вердикта

- **Approve** — все семь разделов есть, числа сошлись, трассируемость полная, признаков покраски нет.
- **Request changes** с классом замечания: `цель` (не выводится из плана), `доказательство` (не воспроизводится или отсутствует), `честность` (признак покраски), `стиль` (не блокирует).
- Стековые PR мержатся строго в объявленном порядке; ревьюер не мержит верхний PR раньше нижнего.

## 7. Что ревьюеру не нужно

Читать весь план. Достаточно §1 этого гида и описания PR. Если описание PR не отвечает на вопросы §4 без похода в план, это дефект описания, и его правит автор PR.
