## Раунд 3 — скиллы и директивы

| # | Вопрос | Решение оператора |
|---|---|---|
| 3.1 | Поведенческие улучшения v1-директив | **Как инварианты, не как текст.** Каждое улучшение → проверяемый инвариант (аксиома/контракт/halt), сверка с v2: есть / частично / нет. Гапы правятся в `.hbs` + contract-тест в `ai/kit`. |
| 3.2 | v1-скиллы без аналога в v2 | **Всё пересмотреть. v2 — полная перестройка, полный слом обратной совместимости; совместимость только через миграцию.** Любой новый скилл нужно доказать: его нельзя добавить улучшением flow v2. Есть роутер. **Выбор инфраструктуры (стека) должен детектироваться по репозиторию, в котором запущены; сейчас в v2 выбора нет — только nodejs. Это нужно поправить.** |
| 3.3 | Слой правил (rules) | **Открытый вопрос — часть плана.** Ни в v1, ни в v2 полноценного слоя правил нет; механизмы v2 «не очень». Все четыре гипотезы (стековые правила с пресетом; языконезависимый baseline в ядре; knowledge.xml project-owned; contract-тесты в ai/kit) — **проработать, для каждой придумать решение**. Прежде — сводка: что сделано в v1, что решено/не решено, все issues; что сделано в v2; точки расширения и пересечения; что v2 решает и что нет. |
| 3.4 | Приёмка «v1 больше не нужен» | **Все четыре критерия в план**, каждый — отдельный документ: миграция V1→V2 на реальном проекте; полный цикл на не-Node стеке; все открытые issues с вердиктом и доказательством; v1 удалён из дерева + docs переписаны. Документы насыщаются и валидируются аудитом; решения адаптивные, не финальные; задачи передаются исполнителю так, чтобы он мог приступать и возвращать вопросы. |

## Раунд 5 — протокол оркестрации

| # | Вопрос | Решение оператора |
|---|---|---|
| 5.1 | Формат передачи | **Структурный бриф → структурный отчёт.** Бриф: цель, инварианты, файлы, приёмка (тесты/eval), ссылка на документ плана, блок «вопросы назад». Отчёт: сделано / коммиты / доказательства / отклонения / вопросы. |
| 5.2 | Ритм и полномочия | **Одна задача за раз.** Техвопросы, покрытые документами плана, решает Lead; архитектура, смена скоупа, удаления — оператор. |
| 5.3 | С чего начинать | **Сначала снять всю неопределённость.** Перечень всех известных задач; по каждой: решает ли v2 уже / нет / нужно / решено / дорабатывать / вызывает вопросы / переработать заново; где eval покрывает, где нужен новый или улучшить существующий. Полная карта до выдачи хоть одной задачи. **v1 заморожен**: буквально каждая изменённая строка main, не учтённая в v2, должна получить вердикт нужна/нет. Полный аудит покрытия тестами и инструментами, зрелости eval. |
| 5.4 | Ветка RC и WIP | **RC доделывает WIP; дальше — в той же ветке PR #25.** |
| 5.5 | GitHub / язык | **main заморожен.** **Никаких записей в GitHub без явного OK оператора.** Черновики ответов akkrat готовить можно. **Язык документов плана и всего общения — русский**; директивы и скиллы — английский. |

## Дополнительное указание (после интервью)

> «Обязательно… всё точно подтвердить, используя любое разумное количество подагентов, которые исследуют и докажут, что весь ресёрч и сбор фактуры по актуальному состоянию завершён, что ничего не упущено, что есть подтверждения, независимый взгляд… если что-то не понимаешь — выходи на связь и задавай вопросы… только если мой ответ может разрешить неопределённость.»

Следствия для метода: каждый документ плана проходит (1) сбор фактуры подагентом, (2) независимую верификацию другим подагентом с вердиктами CONFIRMED / REFUTED / UNVERIFIED по каждому утверждению, (3) сводку расхождений; открытые вопросы, которые может закрыть только оператор, собираются в `00-INDEX.md` § «Вопросы оператору».
