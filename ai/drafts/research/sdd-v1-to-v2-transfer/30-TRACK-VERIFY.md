## 0. Резюме в шести пунктах

1. **Две половины одной задачи, и обе живы.** MAIN даёт стек-абстракцию (`services/stack/**`: `Gate`-как-данные, детект по маркеру, `gennady.yaml` deep-merge с провенансом, `ENV_FAIL`/`TIMEOUT`/`VIOLATION`, clean-tree guard + `--wip`, плагины node/golang/anystack, 198/198 юнит-тестов зелёные). RC даёт семантику фазы (профили по kind, halting-лестница, repair-first с exact Target Files, детекторы честности, `SDD_PHASE_RECEIPT` + групповые `SDD_AUDIT_RECEIPT`/`SDD_REVIEW_RECEIPT`, runtime write-zone; 240/240 тестов зелёные — RC-подмножество 172/172 из них воспроизведено в этой сессии, см. §5). Ни одна сторона не покрывает другую.
2. **RC по-прежнему node-only на каждом слое**: `shared/sdd/readiness.ts:15-24` (8 точных npm-скриптов), `gatherReadinessInput` `:596-609` читает только `package.json`, `cli/cmd/sdd-verify/sdd-verify.cmd.ts:223-226` буквально `npm run <script>`, `shared/sdd/phase-verification-plan.ts:270` `` `npm run ${script}` ``, `shared/sdd/probe.ts:12` `CODE_EXT = /\.(js|jsx|ts|tsx)$/` («Node-only support today»), `shared/sdd/ladder.ts:68` `infraDone = packageJsonPresent && …`. В `.ts` RC нет ни `stack.use`, ни `anystack`, ни `extraGates`.
3. **Персистентный контракт RC — не сырой рантайм-`ranCommand`, а `PhaseVerificationGatePlan.command`.** Цепочка (перепроверена по коду, см. И-1 в §3.0): `commandForGate` (`shared/sdd/phase-verification-plan.ts:252-271`, строка для node — `` `npm run ${script}` `` на `:270`) → `receipt.gateEvidence[]` — проекция `{name,state,command,provider}`, сверяется при валидации (`cli/cmd/sdd-verify/phase-receipt-validation.ts:97-106`) → регуляркой `/^npm run (\S+)$/` (`shared/sdd/phase-receipt.ts:1250`) даёт корни `environmentState` → входит в `planState`. Реально исполнившаяся строка (`ranCommand`, `sdd-verify.cmd.ts:230`) в receipt пишется (`phase-run.ts:210-219`), но **валидатором не сверяется ни с чем** — риск несёт именно представление `commandForGate`, а не аргументы рантайм-вызова. Любая смена этого представления инвалидирует все существующие receipts.
4. **Прошлый план (DL-20/22 «checkpoint через `git write-tree`») вытеснен**: RC уже реализовал детекцию мутаций на грязном дереве без git — `cli/cmd/sdd-verify/workspace-mutation.ts` (sha256-снимок всего дерева кроме `.git`/`node_modules`, fail-closed, никогда не откатывает). Фаза 5.6 плана в прежней формулировке неверна.
5. **Рекомендация — вариант A′ (Engine-в-v2 с presets как данные), но с verbatim-переносом примитивов MAIN** (`env-fail.ts`, `stack-config.ts`+`config-loader.ts`, `tree-guard.ts`, типы `Gate`/`Cmd`/`GateSpec`) и **новым node-пресетом, воспроизводящим текущие строки RC** (не `plugins/node/classify-npm-scripts.ts` — у него другая семантика выбора и другие id гейтов). Вариант B (MAIN `services/stack` как движок) проигрывает — но не по всем трём заявленным причинам одинаково твёрдо (см. §3.2, §3.5): железно доказан только один факт (классификатор node не даёт parity), два других («sync `spawnSync` ломает quality-tail», «`runGate` не экспортирован») слабее, чем выглядели в первом проходе. Вариант C (сосуществование двух глаголов) оправдан как переходный этап для CI/оператора — но фасады требуют более узкой формулировки, чем «оставить как есть» (см. переформулированный Q1 в §7).
6. **Стек должен детектироваться из репозитория и протягиваться `sdd-state → readiness → sdd-task → sdd-verify → infra directive → rules`**; сегодня в RC такого узла нет вовсе — единственный «детектор» это `package.json`. Дизайн: один `StackDetection` (из MAIN `stack-registry.ts:44-64` + `resolve-verify-commands.logic.ts` как референс маркеров) → `ReadinessInput.stack` → профили резолвятся пресетом → `sdd-state` печатает `STACK=`, роутер/infra-директива выбирают baseline-правила. Уточнение верификатора: каскад правил (`<Triggers>` у `python-rules`/`go-rules`) резолвится по **расширениям Target Files**, а не по имени инструмента или `STACK=` — перенос файлов правил не зависит от детектора стека (см. §4.4 п.3).

## 3. Варианты A / B / C — с одинаковой строгостью

### 3.0 Критерии и три «жёстких» инварианта, которые режут варианты

Сравнение идёт по семи критериям: (1) **node-parity** — байт-в-байт текущее поведение RC на node-проектах; (2) **покрытие стеков** node/golang/anystack/python/swift; (3) **сохранность receipts** (`SDD_PHASE_RECEIPT`, `SDD_AUDIT_RECEIPT`/`SDD_REVIEW_RECEIPT`); (4) **сохранность детекторов честности** (`isVacuousScript`/`isStubScript`, coverage-freshness, `workspace-mutation`); (5) **публичный конфиг-контракт** `gennady.yaml` `stack:` (реальный потребитель cloud-ios); (6) **закрытие issues #9 / #17 / #20**; (7) стоимость и риск.

Три инварианта, установленные кодом (а не мнением) и **перепроверенные независимой верификацией по актуальным номерам строк**, задают рамку любому варианту:

- **И-1 (parity команд, механизм уточнён верификацией).** Персистентный байт-в-байт контракт — **не** сырой `ranCommand` рантайма (`sdd-verify.cmd.ts:221-241`, вычисление на `:230`: `` ranCommand = `${command} ${args.join(' ')}` ``), а выход `commandForGate` — `PhaseVerificationGatePlan.command` (`shared/sdd/phase-verification-plan.ts:252-271`, строка для node `` `npm run ${script}` `` на `:270`). Цепочка: `commandForGate` → `receipt.gateEvidence[]` (проекция `{name,state,command,provider}`, сверяется при валидации — `cli/cmd/sdd-verify/phase-receipt-validation.ts:97-106`) → регуляркой `/^npm run (\S+)$/` (`shared/sdd/phase-receipt.ts:1250`) даёт корни `environmentState` → входит в `planState` (`PhaseReceiptPlan:28-49,91-93`). `ranCommand` пишется в `receipt.commands[]` (`phase-run.ts:210-219`, только для прошедших ступеней), но **валидатором не сверяется ни с чем**: `phase-receipt-validation.ts:73-136` сверяет только имена ступеней (`:92-96`), `gateEvidence` против плана (`:97-106`), роль (`:121`) и `command` только для §5-extras (`:131`). Для ступени `fix` `ranCommand` — вообще не `npm run …`, а `evidence.join(' && ')` из `describeRepairAction` (`sdd-verify.cmd.ts:313`, `repair-adapters.ts:163-166`). Legacy-receipts без `gateEvidence` валидируются по литеральному списку ступеней (`phase-receipt-validation.ts:83-91`) — переименование ступеней ломает и этот путь. **Следствие: смена представления рантайм-argv receipt не ломает; смена `commandForGate` — ломает всегда** (риски вариантов A и B ниже переоценены с учётом этого).
- **И-2 (parity плана, но узкая; список инвалидаторов дополнен).** `planState = sha256(JSON.stringify(plan))` хэширует **не** массив гейтов, а `PhaseReceiptPlan` (`shared/sdd/phase-receipt.ts:28-49,90-92`): `ticket, phase, profile, profileBasis, targets, deletedFiles, verification[], coverageOwner?, producesCoverage, environmentState`. `receipt.gateEvidence` сверяется с **проекцией** плана на четыре поля — `gatePlan.gates.map(({name, state, command, provider}))` (`:98-106`). **Следствие, важное для всех вариантов: обогащение `PhaseVerificationGatePlan` новыми полями (`argv`, `timeoutMs`, `cwd`, `env`, `envFail`, `stack`) receipt-безопасно** — пока `name`/`state`/`command`/`provider` не меняются. Два уточнения: (а) состав **и порядок** ступеней плана сравниваются точным JSON-равенством (`:95`) — порядок гейтов пресета тоже байт-контракт, что прямо касается anystack-хвоста (§3.1.4): если его гейты попадают в `gatePlan` как `CONFIGURED`, они обязаны появиться в `receipt.commands` в том же порядке, а если не попадают в план — писать их можно только как `gate:'verification'` (§5-extras); (б) `receipt.commands` содержит только **прошедшие** (`status==='pass'`) ступени (`phase-run.ts:212`) — «видимый skip» (issues #9/#12) в доказательство не попадает в принципе.
- **И-3 (`environmentState` привязан к `npm run`; жёстче, чем казалось изначально).** `phaseVerificationPlanEnvironmentState` (`shared/sdd/phase-receipt.ts:1242-1254`) выводит корни fingerprint'а из `gate.command` регуляркой `/^npm run (\S+)$/` (`:1250`), `fix` разворачивает в `['format:fix','lint:fix']` (`:1249`). Отдельный, не менее node-специфичный узел — `phaseVerificationEnvironmentState` (`:1203-1233`), сама читает `package.json` (`:1212-1220`) и жёстко перечисляет `format:fix`, `lint:fix`, `type-check`, `test`/`test:coverage` (`:1224-1229`). `phaseVerificationEnvironmentFromScripts` (`:1127-1200`) открывает `try` **до** `readFileSync(resolve(root,'package.json'))` (`:1132-1133`) и на любой ошибке возвращает `{ok:false, issue:'cannot fingerprint project verification scripts: …'}` (`:1194-1199`) → `receiptError` → `exit 1`. **Репозиторий без `package.json` не может записать receipt вообще** — это немедленный `ERR_CLI_SDD_VERIFY_RECEIPT`, а не тихая деградация до §5-команд, и это причина, по которой eval-харнесс подкладывает `roundtrip-readiness-shim.package.json`. Fingerprint также покрывает lifecycle-хуки `pre*/post*` (`:1152-1154`), неявный `start → node server.js` (`:1159-1160`), fallback `restart → stop+start` (`:1165-1174`), транзитивные `referencedScriptInvocations`/`localInputEntries` (`:1177-1184`). **Каждый новый пресет обязан принести свой источник «тела гейта» и воспроизвести node-семантику побайтово для node** — этому посвящена отдельная задача V-04a в §6, которой не было в первом проходе плана.

#### 3.1.3 Доказательство node-parity (расширено 8 дырами из независимой верификации)

Базовые три доказательства:

1. **Golden резолвнутых гейтов.** `shared/sdd/__tests__/preset-node-golden.test.ts`: на фикстуре `package.json` с восемью кирпичами для профилей `setup`/`code`/`test`(owner)/`test`(non-owner)/`full` сериализовать `resolvePreset('node', profile, root, config)` в JSON `{name, command, mutates, haltsOnFailure, via, required, state}` и сравнить с golden-файлом, снятым с текущего RC.
2. **Поведенческий байт-в-байт.** `cli/cmd/sdd-verify/__tests__/parity-node.test.ts` с инжектируемым `GateRunner`: (a) последовательность вызовов `(command, args)`; (b) stdout-рендер; (c) записанный `SDD_PHASE_RECEIPT` (`planState`, `targetState`, `environmentState`, `commands[]`, `gateEvidence[]`).
3. **Receipt-совместимость на старом артефакте.** Фикстура-тикет с receipt'ом текущего RC должна проходить `validatePhaseReceipt` после миграции.

Восемь дыр, которые эти три теста пропускают (найдено независимой верификацией — обязательны к добавлению):

4. **`durationMs` в stdout.** `lineFor` печатает `✅ ${name} (${secs(durationMs)})` (`sdd-verify.types.ts:288-295,230-232`). Тест п.2b («полный stdout-рендер как одна строка») будет флакать на каждом прогоне. Нормализовать нужно `durationMs` в stdout — **не** «timestamp'ы»: в `PhaseReceipt` их вообще нет (`phase-receipt.ts:52-70`), поэтому сам receipt можно и нужно сравнивать целиком без нормализации.
5. **Exit-коды не пинятся ничем.** Нужна явная матрица `(профиль × состояние скриптов) → {0,1,4}` (`index.ts:23,67,96`). Введение `env-fail` — прямой кандидат незаметно сдвинуть код.
6. **Evidence ступени `fix`.** Golden п.1 сериализует `command='target-repair'` для `fix` и потому не видит дрейф repair-адаптеров. Нужен отдельный golden на `planTargetRepair`+`describeRepairAction`: матрица тел `lint:fix` × расширений целей × наличия `specPath`, с точными argv (`repair-adapters.ts:99-100,121-131,143-151`).
7. **Порядок `PROJECT_LINTER_ADAPTERS`.** First-match, catch-all последним (`repair-adapters.ts:58-77,103-105`). Тест: «для набора тел `lint:fix` выбранный адаптер = X» + «catch-all остаётся последним» — иначе добавление swiftformat/black/gofmt сдвинет выбор адаптера для существующих node-репозиториев.
8. **Матрица golden слишком узка на одной фикстуре.** Не покрыто: `targets.length === 0` (`commandForGate:258` → `fix=null`), отсутствующий `lint:fix`, вакуумный `format:fix`, не-forwarding repair-brick, алиас `typecheck`, `test`-фаза не-владелец покрытия.
9. **`environmentState` доказан только на одной форме `package.json`.** Нужен golden значений `environmentState` минимум на: транзитивный `npm run`-хоп, `pre*/post*`-хуки, `start` без записи в scripts при наличии `server.js`, `restart`-fallback, `pnpm`/`yarn` форвардинг (`PACKAGE_MANAGER_BUILTINS:95`), локальные входы.
10. **Текст отчёта — контракт директив, не косметика.** `audit/steps/STEP_1_MECHANICAL.xml:75-76` парсит связку `⛔` + «обязательная ступень профиля» (строки генерируются в `sdd-verify.cmd.ts:519,621`); `gate-state: …` (`phase-verification-plan.ts:376`) читает `sdd-task`. Нужны тесты на точные подстроки.
11. **Критерий «172 теста без правок» надо ослабить.** Тесты `sdd-verify` гоняются с `--experimental-test-module-mocks`, привязанными к путям модулей; `resolvePreset` в `shared/verify/presets/node.ts` меняет граф импортов — часть моков придётся переадресовать. Формулировка parity-safe: «поведенческие утверждения не меняются», не «файлы тестов не трогаются». Плюс: прогон 172 требует `cwd=<rc>` (подтверждено воспроизведением, см. §5) — фиксировать в задаче, а не в сноске.

Дополнительно, вне восьми пунктов: `tailCap` (120 строк/16 КБ + дайджест `not ok`, `sdd-verify.types.ts:234-281`) и `GATE_MAX_BUFFER_BYTES` — тоже наблюдаемое поведение, тоже требуют теста.

#### 3.1.4 Как приходят стеки

- **node** — пресет-данные, воспроизводящие текущие строки RC (не `plugins/node/classify-npm-scripts.ts`: у него другие id гейтов и другая семантика выбора — статически доказано по коду и подтверждено прогоном, см. §5.5: `typecheck, gennady, lint, test, format` против RC `fix, type-check, test, test:coverage, lint, format, yagni`).
- **golang** — плагин MAIN verbatim; в фазовую модель добавляется маппинг «ступень ладдера → гейты плагина»: `fix` → `gofmt -w` + `go mod tidy` (мутирующие, только по Target Files — по пакетам целей), `type-check` → `go build`+`go vet`, `test` → `go test`, `full` += `generate` (drift), `golangci-lint`. Поля `outputMeansFailure` (`gofmt -l` — «exit 0 + непустой stdout = FAIL») и `driftMeansFailure` (`go generate`-дрейф) обязательны в схеме гейта — без них этот пресет нереализуем. `environmentState` (И-3) для go = хэш `go.mod`+`go.sum`+`Makefile`-рецептов, названных пресетом (задача V-04a).
- **anystack** — плагин MAIN verbatim; ступеней ладдера у него нет, все гейты приходят из `stack.anystack.extraGates`. В фазовой модели anystack-гейты идут после foundation как read-only-хвост; `required` для них — пустое множество. Их порядок в `gatePlan` — часть байт-контракта (И-2 п.а); `environmentState` для проекта, где основной (и единственный) манифест — не `package.json`, требует источника от V-04a, иначе receipt не запишется вовсе (И-3).
- **swift (cloud-ios)** — сегодня это **anystack + `gennady.yaml`** (`stack.use: [anystack]`, три `extraGates`, см. §1.1). Отдельный `plugins/swift` нужен только для readiness/coverage; конфиг потребителя обязан продолжать работать без правок. Что содержал бы swift-пресет: маркеры `Package.swift` | `*.xcodeproj` | `*.xcworkspace` | `Project.swift` (Tuist) | `.mise.toml`; гейты `fix` → `swiftformat <targets>` / `swiftlint --fix <targets>`; `type-check` → `xcodebuild build-for-testing` (или `swift build`); `test` → `xcodebuild test`/`swift test`; `full` += `swiftlint lint --strict`; `envFail` — `outputMatches(/xcodebuild: error: (?:Unable to find a destination|The operation couldn.t be completed)/)`, `outputMatches(/error: unable to attach DB|Provisioning profile/)`, `outputMatches(/Cannot find simulator/)`, `exitCodeMatches('!=2')` для swiftlint; `timeout` 90m; coverage-probe — `CoverageAdapter` с `detect` по `*.xcresult`/`default.profdata`, `artifacts.report = <DerivedData>/…/Coverage.profdata` или `xccov --json`. **Источник `environmentState` для swift не назван нигде в дизайне** — учитывая И-3 (без источника fingerprint'а receipt не пишется вовсе), swift-пресет без явного ответа здесь нереализуем в принципе; кандидат — хэш `Package.swift`/`project.yml` (Tuist/XcodeGen) + версии toolchain (`.mise.toml`/`swift --version`), но это решение оператора не принято.
- **мультистек и одна лестница — не определены.** v1 считает мультистек нормой (`detectStacks` возвращает массив). Фазовая лестница имеет по одной ступени `fix`/`type-check`/`test`. В репозитории с `package.json` **и** `go.mod` (или с eval-шимом + Swift) неясно, чей пресет владеет этими ступенями. Кандидат-ответ: одна «основная» ступень от primary-стека (первый матч по `stack.use`, иначе по порядку `BUILTIN_PLUGINS`) + гейты остальных стеков как read-only-хвост, как и anystack-extraGates — но это тоже требует явного решения, а не молчаливого допущения.

#### 3.1.5 Что происходит с честностью, receipts и мутациями

- `isVacuousScript`/`isStubScript` (`readiness.ts:405,425`) остаются **движком**, но получают вход «тело единицы гейта» от пресета: для node — тело npm-скрипта, для python — строка команды из `[tool.poe.tasks]`/`Makefile`-рецепта, для anystack — `argv` из `gennady.yaml`. Оговорка: сам node-детектор сознательно узок (`node -e "process.exit(0)"` не ловится, `readiness.ts:322-323`), этим пользуется eval-шим — так что «честность теряется молча» без per-stack вакуумности стоит формулировать мягче, чем абсолютный риск.
- **Coverage-freshness** (`verifyCoverageWritten` `sdd-verify.cmd.ts:191-211` + `CoverageProbe:169-182`) выживает без правок семантики: расширяется только реестр `COVERAGE_ADAPTERS`.
- **Receipts** выживают целиком в части И-2: `SDD_PHASE_RECEIPT` привязан к плану + байтам целей, а не к node. Единственная node-специфика — `environmentState` (И-3), лечится per-preset источником fingerprint'а (V-04a). Групповые `SDD_AUDIT_RECEIPT`/`SDD_REVIEW_RECEIPT` стека не касаются вовсе.
- **`fixer` в `GateSpec` — мёртвые данные до V-16.** Фазовый путь мутирует через `planTargetRepair`, а не через `Gate.fixer`; единственный исполнитель `fixer` — `runFix` (`gate-runner.ts:522-531`), доступный только через фасад `gennady fix`. cloud-ios объявляет `fixer` для `swiftlint` — до появления фасада с `RepairMutationBoundary` (см. §3.3, §3.6) это поле парсится и валидируется, но не исполняется в фазовом пути.
- **`workspace-mutation.ts` на iOS — не «ложное срабатывание», а стена по времени.** `snapshotWorkspace` (`:134-169`) обходит **всё** дерево кроме `.git`/`node_modules` и считает sha256 содержимого каждого файла, игнорируя `.gitignore`. Конфиг потребителя пишет `build/DerivedData` (порядка 10 ГБ на worktree, комментарий потребителя) и `build/xcresult` (70-75 МБ × 2); boundary вызывается `before` и `after` (`:378-394`) — то есть **два полных хэша ~10 ГБ на каждую транзакцию**. Расширения списка исключений (`.venv`, `.build`, `DerivedData`, `vendor`) как данных пресета — правильная, но недостаточная правка; нужно явное решение о стратегии обхода: либо `.gitignore`-aware обход, либо lazy-стратегия (mtime+size до содержимого, sha256 только на подозрении).
- `tree-guard.ts` (git-lock + refuse-dirty + `--wip`) остаётся **только** на clean-caller пути; фазовый путь продолжает жить на boundary — DL-20/22 не возвращаются. Открытый вопрос конкурентности фазового пути (два параллельных `sdd-verify` в одном worktree дадут взаимные ложные «мутации вне write-zone») — вынесен в задачу V-18 (§6).

#### 3.1.6 Issues #9 / #17 / #20 в варианте A

- **#9 (`extraGates[].when`, file scoping).** Аддитивный ключ в `GATE_SPEC_KEYS` (`stack-config.ts:34-45`): `when: [<glob>…]`. Гейт без `when` идёт всегда; гейт, чьи globs не пересеклись с Target Files фазы (`phase-context.ts:169-239`), получает `skipped: 'when (gennady.yaml)'`. Ограничение по честности: `receipt.commands` фильтрует только `status==='pass'` (`phase-run.ts:212`), поэтому отсечённая `when`-ступень **не попадает в receipt как доказательство** — факт «не запускался, потому что вне области» нужно писать в `gateEvidence` отдельно. Решение оператора по умолчанию — вопрос **Q4** (§7).
- **#17 (вывод на pass).** Два независимых механизма: (a) поле `showOutputOnPass?: boolean`; (b) конвенция «строка с маркерным префиксом `[gate] ` выживает в вердикт независимо от статуса» — у cloud-ios такая строка уже реально печатается (`echo "[gate] сужено: …"`, §1.1). Рекомендуется (b) как основное (не требует правок конфига у потребителя) + (a) как явный опт-ин. `GateResult.output` в RC уже хранится (`sdd-verify.types.ts:211-212`), правка — одна ветка `lineFor`. В receipt при этом **ничего не добавляется** — иначе ломается И-2. Оговорка: вывод на pass попадает в контекст аудитора и может быть принят за доказательство — рендерить с явной привязкой к имени гейта и не класть в receipt.
- **#20 (`--only` префикс/glob, сужение) — дизайн неверен в исходной формулировке для фазового пути.** `phaseReceiptCommandIssue` требует `JSON.stringify(ladderNames) === JSON.stringify(required)`, где `required` выводится из `gatePlan` (`phase-receipt-validation.ts:79-96`). Если `--only` отбрасывает `CONFIGURED`-ступень — receipt не проходит собственный валидатор, `sdd-log complete` откажет (`sdd-log.types.ts:284-287`). Если вместо этого сузить сам `gatePlan` — меняются `gateEvidence` и через `environmentState` `planState`, то есть фаза перестаёт соответствовать каноническому плану тикета (запрещено `ax-verification-before-handoff.xml:4`). **Верная формулировка: `--only`/`--skip` доступны только `gennady verify` и `sdd-verify --profile full` (оба не пишут фазовый receipt), и никогда при `--task/--phase`.** Часть (iii) issue #20 (`ai/skills/sdd-execute/SKILL.md:98`, `scripts/verify.sh:69-92`) закрывается удалением v1-скилла — этим владеет отдельная задача V-17 (§6), а не «правка попутно».

### 3.3 Вариант C — сосуществование двух глаголов (граница сужена по итогам верификации)

**Тезис.** `sdd-verify` остаётся фазовым/групповым глаголом (receipts, halting, честность), `gennady verify`/`gennady fix` — глаголом чистого дерева: CI, ручной прогон оператора, мутации. Ядро (типы `Gate`, `env-fail`, конфиг, детект, пресеты) общее.

- **Что переносится verbatim:** всё из §3.1.1 плюс `cli/cmd/verify/**` и `cli/cmd/fix/**` целиком.
- **Что переписывается:** ровно то же, что в A, минус «переучить движок» — то есть C = A + сохранение второго CLI-фасада над общим ядром.
- **За.** (a) `gennady fix` — единственный дом мутаций вне фазы, в v2 аналога нет; (b) CI и оператор хотят RUN-ALL-отчёт «всё сразу», а не halting; (c) cloud-ios сегодня зовёт `gennady verify --wip` из скиллов — мгновенная совместимость; (d) `--plan --json` — единственный machine-readable вывод, у `sdd-verify` его нет вовсе.
- **Против — два конкретных дефекта, найденных независимой верификацией, а не общий риск «дрейфа».**
  1. **`verify --wip` заново вводит зелёный вердикт без receipt.** Печатает `ALL_GATES_PASS (n/m)` и выходит 0, не создавая `SDD_PHASE_RECEIPT` — ровно тот артефакт, который `ax-verification-before-handoff.xml:4` объявляет не-доказательством («a hand-written `ver` line is not evidence»). Держать такой глагол рядом с фазовым — постоянный соблазн для агента и оператора подменить канон.
  2. **`gennady fix` противоречит D-SV022.** `workspace-mutation.ts` построен так, чтобы мутации происходили только внутри write-zone фазы. `runFix` (`gate-runner.ts:522-531`) мутирует дерево вообще без guard (`runGate(..., null)`), без Target Files и без инвалидации receipts — после `gennady fix` receipt фазы становится ложным (байты целей поедут), и обнаружится это только при следующей валидации. «Единственный дом мутаций» — это и единственная дыра в границе, которую только что закрыл D-SV022.
- **Оправдание сохранения C, но с сужением объёма.** Решение оператора «v2 заменяет v1 полностью» означает: C допустим не как архитектура, а как поверхность CLI — но два фасада не могут быть «как есть», им нужны границы: (i) `gennady verify --plan --json` — только read-only планировщик/CI-репортёр, без `--wip`-мутаций без receipt (или явная маркировка вывода как «не evidence»); (ii) `gennady fix` — только если он получит ту же `RepairMutationBoundary`, что и фазовый `fix`-rung, иначе он не входит в релиз варианта A′ вовсе, а мутации остаются доступны только через фазу. Тест эквивалентности («оба фасада на одной фикстуре резолвят один набор `Gate`, с точностью до halting/scope») — сам по себе слаб как митигация: фасады различаются моделью области (`ScopeRequest{files|changed|all}` против exact Target Files), профилями (RUN-ALL против halting) и таксономией (`skipped` против `missing`) — «с точностью до…» это и есть щель, в которую уезжает вторая правда.
- **Усилия:** A + S (фасад `verify --plan --json`) + (S, при условии готовой `RepairMutationBoundary`; иначе — не в этом релизе) для `fix`.

### 3.4 Критическая оценка прошлой идеи readiness («Engine + presets сначала, per-stack readiness потом»)

Идея прошлого плана: сначала обобщить движок и пресеты, readiness развязать позже (фаза 5.4). **Она устарела в части «позже», и вот почему:**

1. **Readiness — не хвост, а вход.** `EXECUTION_READY` — жёсткий блок исполнения: `sdd-task.cmd.ts:123` (pickable = только GATE_QUEUE при `!executionReady`), `:462-487` `ERR_CLI_SDD_TASK_INFRA_NOT_READY`; ветвление роутера (`readiness-preflight-gate.xml:6-7`); карточка лестницы (`ladder.ts:68` `infraDone = packageJsonPresent && …`). Пока readiness node-only, **любой** non-node проект не проходит дальше `sdd-task` — то есть пресеты работать не начнут, даже если движок готов.
2. **Это уже подтверждено практикой.** Round-trip eval на cloud-ios (`ai/flow-eval/docs/roundtrip-wall3-assessment.md`) упёрся в wall 3 и обошёл его шимом `roundtrip-readiness-shim.package.json` со стабами `node -e "process.exit(0)"` — файл сам просит удалить его, «once the flow branch consumes anystack readiness». Отсрочка readiness уже стоит фальшивого артефакта в eval-харнессе.
3. **Но «per-stack readiness» в прежней формулировке тоже неверна.** Восемь имён npm-скриптов — это не восемь требований, а node-кодировка семи обязанностей. Правильная декомпозиция: readiness-движок проверяет **обязанности** (`type-check`, `test`, `coverage-producer`, `format-read-only`, `format-write`, `lint-read-only` (доходит до `gennady`), `lint-write`, `public-repair`), а пресет отвечает на четыре вопроса про каждую: *объявлена ли*, *не вакуумна ли*, *read-only или mutating*, *forward-ability*. Уровни `not-ready/provisional/ready` и `executionReady` остаются движковыми.
4. **Минимальный честный компромисс, совместимый с решением оператора «Engine+presets первыми»:** ввести readiness-adapter **интерфейс** уже на шаге 4-5 вместе с пресетом, но реализовать только node-адаптер (байт-в-байт текущий выход) и тривиальный anystack-адаптер: «обязанность считается выполненной, если её закрывает `extraGates`-гейт из `gennady.yaml`». Это снимает wall 3 без полного расщепления и позволяет отложить golang/python/swift-адаптеры без блокировки харнесса. Отсрочка *интерфейса* — нет; отсрочка *адаптеров* — да. **Уточнение по И-3: снятие шима без источника `environmentState` (V-04a) всё равно не даёт cloud-ios писать receipts** — readiness и receipt-fingerprint — два разных узла node-only, и решается только readiness-adapter'ом эта отсечка неполна (см. §6, зависимость V-06 → V-04a).

### 3.6 Рекомендация

**Рекомендуется A′ = вариант A с суженными фасадами варианта C, т.е. A + read-only `verify --plan --json` + условный `fix`.** Причины, по порядку веса:

1. **Parity дешевле именно в A**, и это подтверждено, а не ослаблено верификацией: пресет, воспроизводящий строки RC, — снимок существующего кода; в B ту же работу всё равно придётся сделать (node-плагин MAIN даёт другие id — единственный железный из трёх исходных фактов против B), но сверх неё придётся переучить `gate-runner.ts`. Уточнение: часть этой «переучки» (halting-опция, мутирующая ступень) оказалась дешевле, чем в первом проходе — но async-миграция исполнителя (обязательный per-gate timeout, который в RC отсутствует полностью) остаётся весомой и односторонне выгодной B, а не A.
2. **Ядро v2 — это не runner, а семантика.** Дорогое и невоспроизводимое в RC — receipts (уточнённый механизм И-1/И-2/И-3), `⛔ missing`, coverage-freshness, boundary мутаций, профили и halting-лестница (172 из 240 тестов воспроизведены зелёными в этой сессии). Дорогое в MAIN — данные и примитивы, и они переносятся копированием файлов (с обязательной правкой `tsconfig`/`test-topology`, иначе тесты «зелёные», потому что не запускаются).
3. **`workspace-mutation` уже победил `git write-tree`-checkpoint.** Фазовый путь не нуждается в RUN-ALL-исполнителе и в `reset()`; врезать boundary в чужой sync-runner (B) дороже, чем оставить его на месте. На iOS-фикстуре это ещё и вопрос производительности (два sha256-снимка ~10 ГБ за транзакцию), который надо решать независимо от выбора движка.
4. **Конфиг-контракт `stack:` в A не теряется** — он переносится как отдельный шаг вместе с валидатором и провенансом.
5. **Фасады C закрывают то, чего у `sdd-verify` нет и не должно быть**, но только в суженном виде: `--plan --json` как read-only планировщик, а не второй канал зелёного вердикта; `fix` — только с `RepairMutationBoundary`, иначе он остаётся вне релиза A′ до появления этой границы (см. переформулированный **Q1** в §7).

Что в A′ **не** делать: не переименовывать секцию `stack:` в `verify:` (ломает единственного реального потребителя, DL-21 в этой части ошибочен); не тащить `plugins/node/classify-npm-scripts.ts` в фазовый путь (другая семантика выбора); не возвращать checkpoint через `git write-tree`; не давать `--only/--skip` работать при `--task/--phase` (ломает И-2); не считать `environmentState` для non-node стеков решённым фактом переноса типов — это отдельная задача (V-04a).

### 4.4 Как протянуть выбор стека из репозитория (дизайн)

Один факт, один источник, несколько потребителей:

1. **Источник.** `detectStacks(root, config, registry)` (перенос MAIN `services/stack/stack-registry.ts:44-64`; кандидаты — `plugins/index.ts:15` `BUILTIN_PLUGINS`, сортировка по id; `stack.use` из `gennady.yaml` только **сужает** кандидатов, не назначает стек). Маркеры: `package.json` (`plugins/node/node-plugin.ts:45,51`), `go.mod` (`plugins/golang/golang-plugin.ts:57`), «матчит всегда» для anystack (`plugins/anystack/anystack-plugin.ts:24-34`), новые — `pyproject.toml|setup.cfg|requirements.txt|tox.ini` и `Package.swift|*.xcodeproj|*.xcworkspace|Project.swift`. Результат — `StackDetection[]` (мультистек — нормальный режим, как в v1: `cli/cmd/verify/verify.cmd.ts:160-179`; но какой пресет владеет какой ступенью лестницы при мультистеке — открытый вопрос, см. §3.1.4).
2. **`sdd-state`** (`sdd-state.cmd.ts:152-161`): `detectStacks` вызывается **до** readiness; в блок `[READINESS]` добавляются строки `STACK=<id[,id…]>` и `STACK_SOURCE=<marker:<file> | config:stack.use>`; `readinessInput` получает `stack` и `manifest`; `renderLadder` получает `manifestPresent` вместо `packageJsonPresent` (`ladder.ts:68`), `probeRepo` — расширения/конфиги от пресета (`probe.ts:12`).
3. **readiness** (`readiness.ts:446-609`): `checkReadiness(input, adapter)`, где адаптер отвечает на четыре вопроса про каждую из семи обязанностей (§3.4 п.3). Уровни `not-ready/provisional/ready` и `executionReady:562` — движковые, их текст не меняется (важно: три директивы и `sdd-task` парсят именно этот текст).
4. **`sdd-task`** (`sdd-task.cmd.ts:107,123,462-487`) и **`gate-queue`** (`gate-queue.ts:365,392`): читают тот же `readiness` — правок семантики не требуется; меняются только сообщения, где буквально сказано «npm-скрипт».
5. **`sdd-verify`** (`phase-context.ts:253-296` → `phase-verification-plan.ts:29-92` → `sdd-verify.cmd.ts:357-368`): профиль по kind фазы остаётся; `command`/`argv` каждой ступени берутся из пресета выбранного стека. `SDD_PHASE_RECEIPT` получает `stack` **вне** `PhaseReceiptPlan`-хэша (иначе И-2 инвалидирует старые receipts) — либо, если оператор выберет Q2(b), внутрь, с bump `schema: 2`.
6. **infra-директива** (`infra.directive.xml:75,83,430-432`): стек приходит фактом из `sdd-state`, поэтому (a) «Node/npm runtime artifacts» становится «манифест выбранного стека», (b) Effective Rules резолвятся stack-триггерами.
7. **rules cascade** (`ai/directives/knowledge.xml`): в RC зарегистрировано 14 правил (`typescript-rules, svelte5-runes, sveltekit-rules, testing-common, vitest-rules, node-test, playwright-cli, playwright-e2e, storybook-usage, svelte-testing, eslint-setup, git-setup, nodejs-npm-setup, storybook-setup`) — не 3, как выглядело в первом проходе анализа; но несущая часть верна: `baseline-rules`, `go-rules`, `python-rules` отсутствуют и в реестре, и физически (`ai/directives/coding/` в RC содержит только svelte/ts/uikit). В MAIN есть `baseline-rules` (`knowledge.xml:67,93,103`), `go-rules` (`:95`), `python-rules` (`:85`). Перенос этих трёх файлов + записей реестра — обязательная часть дизайна; и он требует **четвёртого** файла, не названного нигде в первом проходе: MAIN `go-rules.xml:8-11` и `python-rules.xml:7-10` объявляют `<DependsOn>` на `baseline-rules.xml` **и** `ai/directives/testing/baseline-testing.xml` — второго в RC физически нет, и `RULES_CASCADE_CLOSURE` (`shared/sdd/rules-cascade.ts`, тест `shared/sdd/__tests__/rules-cascade.test.ts`) упадёт без него (MAIN `knowledge.xml:129`).
8. **Уточнение: каскад правил не нуждается в `STACK=`.** `<Triggers>` у `python-rules`/`go-rules` — по расширениям Target Files («Target Files include .py source files», `knowledge.xml:88,98`), а не по имени инструмента и не по стеку. ## 7. Решения, которые может принять только оператор

**Q1. Судьба `gennady verify` / `gennady fix` как публичных глаголов при «v2 заменяет v1» — переформулирован по итогам верификации.**
(a) оставить оба фасада над общим ядром без ограничений; (b) оставить только `gennady fix`, а RUN-ALL-отчёт отдать `sdd-verify --profile full --run-all`; (c) удалить оба, всё через `sdd-verify` (CI теряет `--plan --json` и мутации до появления замены); (d) как (a), но `--wip` в CLI-фасаде явно маркирует вывод как «не evidence» (не заменяет receipt); **(e) только read-only `gennady verify --plan --json` как планировщик/CI-репортёр без исполнения; `gennady fix` не входит в релиз A′, пока не получит `RepairMutationBoundary` — мутации до этого момента доступны только через фазовый `fix`-rung — рекомендуется**, потому что закрывает оба найденных верификацией дефекта: зелёный вердикт без receipt (`verify --wip` печатает `ALL_GATES_PASS`, не пишет `SDD_PHASE_RECEIPT`) и мутацию вне boundary, молча инвалидирующую receipt фазы (`runFix` → `gate-runner.ts:522-531`, без guard).

**Q2. Совместимость существующих receipts при переходе.**
(a) жёстко сохранить И-1/И-2/И-3 (никаких изменений `commandForGate` и источника fingerprint'а для node) — рекомендуется; (b) разрешить разовую инвалидацию с явной миграцией (`schema: 2` + правило «legacy receipt валидируется старым способом»); (c) инвалидировать без миграции (все незакрытые фазы придётся перепрогнать).

**Q3. Где живёт readiness-адаптер и когда.**
(a) интерфейс + node-адаптер + тривиальный anystack-адаптер сразу (снимает eval-шим для readiness, ~S; но не снимает блокировку receipt без V-04a — это отдельная зависимость) — рекомендуется; (b) только интерфейс, адаптеры позже (харнесс продолжает жить на `roundtrip-readiness-shim.package.json`); (c) полное расщепление сразу для всех пяти стеков (L, задевает 50 тестов и 3 директивы).

**Q4. Сужение гейтов по файлам (#9/#20) по умолчанию.**
(a) `when` по умолчанию отсутствует → гейт всегда идёт (сегодняшнее поведение, дорого для swift); (b) гейт без `when` идёт всегда, но фазовый путь дополнительно печатает предупреждение о неотсечённых долгих гейтах; (c) в фазовом пути гейт без `when` **пропускается**, если ни один Target File его не касается (быстро, но риск ложного зелёного); (d) `when` обязателен для `extraGates` с `timeout > 10m` (заставляет потребителя объявить область один раз).

**Q5. Вывод на pass (#17).**
(a) конвенция «строки с префиксом `[gate] ` выживают в вердикт» (ничего не менять в конфиге потребителя, факт уже подтверждён в `gennady.yaml`) — рекомендуется; (b) явный per-gate флаг `showOutputOnPass`; (c) `--full-output` начинает сохранять `output` и на pass (только для отчёта, не для receipt); (d) (a)+(b).

**Q6. Swift: отдельный плагин или anystack навсегда.**
(a) swift остаётся anystack + `gennady.yaml` (ноль правок у потребителя, но нет readiness/coverage для swift, и вопрос `environmentState` не встаёт вовсе); (b) отдельный `plugins/swift` с маркерами и ладдером, `extraGates` продолжают работать поверх (рекомендуется, если нужен `test:coverage` и honest readiness на iOS) — при этом обязательно требует ответа на источник `environmentState` (V-04a), иначе receipt не пишется; (c) плагин swift, но без coverage-адаптера на первом шаге.

**Q7. Порядок стеков после node.**
(a) anystack → golang → python → swift (anystack первым, потому что он разблокирует cloud-ios и eval-харнесс) — рекомендуется; (b) golang первым (готовый плагин + 46 тестов, быстрый выигрыш в доверии); (c) python первым (нужен новый плагин целиком, но он самый близкий к node по форме).
