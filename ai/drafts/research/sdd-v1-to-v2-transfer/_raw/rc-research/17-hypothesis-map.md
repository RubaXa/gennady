# Карта гипотез SDD v2 + план независимой проверки

Сводка всех накопленных гипотез с их статусом и способом независимого подтверждения.
Цель: двигаться по приоритету, каждую подтверждать доказательно (не «прогнали раз»).
Методология валидации — см. 18-eval-methodology.md (ресёрч идёт).

## Статус доказанного (базовая линия)
- Фазы изолированно: authoring 2/2, scaffold 2/2, execute 2/2 — воспроизводимо (дешёвая модель).
- Цепочка «с нуля» (authoring→scaffold→execute одним потоком): НЕ пройдена; послойно продвигается фиксами.

## Класс доказательства (из 18-eval-methodology — под ограничение 2–3 потока)
- **ДЕТЕРМИНИРОВАННЫЕ → unit/regression-тест (1 прогон, доказательно):** G1, G2, G3, G4 (готов), G5, G9-парсинг. ОСНОВНОЙ ТРЕК.
- **ВЕРОЯТНОСТНЫЕ → малая пачка A/B + процессные метрики, «сигнал не доказательство»:** G6, G7-тон, G8, G9-перегруз.
- Живой eval (≤3 потока) — для ИНТЕГРАЦИИ (проходит ли цепочка), не статистики.

## Открытый вопрос направления (оператору)
Приоритет проверки: (а) довести цепочку fibonacci (чинить G9 scaffold-бюджет) → доказать end-to-end;
(б) сначала G5+G10 (approval/interview — ядро взаимодействия по мнению оператора);
(в) сначала утвердить методологию (18) и прогнать G6/G7 A/B как самые общие рычаги.
Все A/B требуют протокола из 18 (сколько сидов, baseline, значимость) — иначе шум.

## ЖЁСТКИЕ ОГРАНИЧЕНИЯ ПРОГОНОВ (оператор)
- **Изоляция:** каждый прогон — своя песочница (mktemp gen-*-root, reuse только осознанно для цепочки). Не смешивать состояния.
- **Максимум 2–3 параллельных потока.** НЕ бесконечный workflow, не веер прогонов. A/B гонять ограниченными пачками (2-3 за раз), не десятками.
- Server 4098 один общий для прогонов; concurrency в cli держать ≤3.
- Каждый поток под своим Monitor; собирать вердикт, освобождать слот, потом следующий.
