## 3. Принципы дизайна (не пересматривать — согласованы оператором)
────────────────────────────────────────────────────────

1. **Шаблон = формат.** `sdd-new` создаёт скелет, внутри которого в каждой секции написано, что и как
   заполнять. Отдельные format-файлы либо поглощаются скелетом, либо на них точечно ссылается сама
   секция скелета (путь + «читать при заполнении ЭТОЙ секции»). Директива НЕ раздаёт список форматов
   на предварительное чтение.
2. **Инструкции в секциях — удаляемые и отделённые.** HTML-комментарии `<!-- ... -->`, замещаются
   контентом при заполнении. Заполненная спека не содержит подсказок скелета.
3. **Минимальные примеры.** Большие worked examples провоцируют копирование у дешёвых моделей. Один
   короткий пример на секцию максимум, помечен как удаляемый образец.
4. **Мягкие проверки.** Валидатор проверяет маркеры и заполненность секций и ПОДСКАЗЫВАЕТ («секция X не
   заполнена, см. комментарий в ней»), а не бьёт побайтово. Исполнитель — LLM, не парсер. Draft-режим
   возвращает подсказки, не блокирующие ошибки.
5. **Директива = короткий маршрут.** Что создать → чем проверить → когда остановиться. Section-level
   guidance живёт в скелете, а не в директиве.
6. **Каждая фаза — механический CLI-цикл** (как execute — единственная стабильная фаза): CLI выдал
   контекст → агент сделал → CLI выдал receipt → атомарное закрытие. Authoring получает тот же цикл.
7. **Диалоговая церемония — только при живом операторе.** Approval Check / STOP / ASCII-диаграммы-в-чате
   / breadcrumbs выносятся в interactive-профиль. Автономный прогон: skeleton → fill → check →
   deviation ledger → закрытие, без церемонии.

## 5. Пакеты работ (по порядку; каждый = отдельный коммит с зелёным pre-commit)
────────────────────────────────────────────────────────

Правила для всех пакетов: правки flow и правки харнесса — в РАЗНЫХ коммитах. Сообщение коммита
описывает, что и зачем. После коммита — строка статуса (§9).

### P0 — Инварианты сначала (тесты пишутся ДО изменений кода)
Обобщённые инвариант-тесты (общие, не привязанные к Fibonacci/TodoMVC). Список инвариантов:
- Gate 1 (scaffold) не предъявляется, пока реальные черновики задач не созданы и не проверены `sdd-check`.
- Инфраструктурный провайдер предшествует потребителям; runtime/пакетный менеджер определены до
  установки зависимостей.
- Общие файлы — без параллельных владельцев; негативные сценарии обязательны; Requirement-ID
  присутствуют в задачах и тестах.
- Заполненная спека не содержит комментариев-подсказок скелета.
- Харнесс учитывает untracked-файлы; тайм-лимит не добавляет лишнего ожидания после последнего наблюдения.
- Артефакты покрытия (`coverage/`) не пачкают рабочее дерево (см. §6 — это реальная ловушка).

Тесты, которые обязаны падать на текущем коде, — падают (зафиксируй это в сообщении коммита);
которые проходят — закрепляют ночные фиксы. **Начатое прошлой сессией:** в worktree может лежать
staged/незакоммиченный `shared/sdd/__tests__/rc-recovery-invariants.test.ts` (~150 строк). Проверь его
на соответствие этому списку, дополни недостающим, доведи до зелёного/красного по смыслу и закоммить —
это и есть P0. Не выбрасывай, но и не коммить слепо.

### P1 — Скелет = формат (данные из эмпирики чтений, см. §10)
- Поглотить скелетом и удалить `READ_AND_USE` из директив: `library-spec-structure`,
  `module-spec-structure` (скелет уже байт-в-байт равен им), `requirement-entry-format`,
  `module-map-update`, caption-правила `diagram-vocabulary`.
- Ссылка ИЗ секции скелета (лениво, путь в комментарии секции): `entity-inventory-format`,
  `entity-surface-format`, `dbc-contracts`. Убрать «first»-императивы из `module.directive`.
- Убрать из потока: `module-diagram-ladder.example.md`, `portal-structure`.
- Все инструкции секций — по принципам 2–3.

### P2 — Мягкий receipt: `sdd-check --spec <path> --authoring`
Draft-режим: заполненность секций по SECTION-якорям, остаточные комментарии скелета, негативные
сценарии, REQ-ID-грамматика. Вывод — подсказки «что дозаполнить и где» (тон помощника), терпим к
пустому Module Map на драфте. Переиспользовать существующие коды (`SDD_SPEC_SECTION_MISSING`,
`SDD_REQ_MISSING_UNHAPPY`, `SDD_SECTION_NOT_FOLDED` и др.), не изобретать заново.

### P3 — Директивы → маршрут
- `sdd-new` — ПЕРВЫЙ шаг authoring (сейчас первый содержательный write — шаг 10 из 11).
- Scope/module-директивы сжать до маршрута (цель ~⅓ текущего объёма): классификация → sdd-new →
  заполнение по скелету → `sdd-check --spec --authoring` → закрытие. Вырезать всё, что держит
  скелет/чекер (~35–40%).
- Диалоговую церемонию — в interactive-профиль (принцип 7).
- `sdd-orient` — единственное обязательное чтение чужого контекста; interview-protocol/rule-registry/
  research-gate — по триггеру, не по умолчанию.
- Для scale=function: scope+module одним проходом, один манифест.

### P4 — Атомарное закрытие authoring
Аналог `sdd-log complete` для спек: одна CLI-команда фиксирует «scope draft complete / module draft
complete» (receipt + запись), чтобы свежий агент продолжал с артефактов, а не с транскрипта.

### P5 — Scaffold: материализация до Gate 1
- Реальные черновики задач создаются и проходят `sdd-check --task --authoring` ДО предъявления Gate 1
  (инвариант P0 обязан позеленеть здесь).
- Команда отступления «вернуться к декомпозиции» при ошибках проверки — вместо локального переписывания.
- Спеки обязаны назначать владельца инфраструктуры (runtime/пакетный менеджер/конфигурация) — дыра draft.61.
- Если меняешь границу фазы — синхронно обнови `ai/flow-eval/scenarios.json`, иначе харнесс мерит старую границу.

### P6 — Журнал отклонений + финальный разбор
- Единый механизм записи (переиспользовать Execution Log / Decision Log, не плодить новый файл): каждое
  спорное самостоятельное решение — одна строка (что, почему, где).
- Финальный шаг после ВСЕЙ пачки: динамическая директива «разбор отклонений с оператором» — список
  отклонений + находки аудита + вопросы. До этого момента не замирай на спорных местах.

### P7 — Верификация (живые прогоны; жёсткий анти-цикл)
Операционная процедура — в `ai/flow-eval/RUNBOOK.ru.md` (в worktree). Следуй ей буквально: подготовка
OpenCode, точная команда с `llm-proxy/deepseek-v4-flash`, ОДНА фаза (отдельный scenario-file, НЕ весь
пакет), чтение наблюдений, критерии pass/fail/inconclusive.
1. Локальные тесты зелёные (включая P0) → делегируй ОДИН authoring-прогон runner-подагенту (§8).
   `pass` → зафиксируй + отчёт. `fail`/`inconclusive` → **СТОП, отчёт с evidence, без немедленного фикса.**
2. После pass authoring: полная цепочка toy-задачи authoring → scaffold → execute одним flow.
3. После pass цепочки: TodoMVC с нуля — authoring → scaffold → execute. Это RC-гейт.
Замечания: `inconclusive` = как fail (стоп, не перезапуск). Если прогон упирается в тайм-лимит при
заполненных спеках — это сигнал, что P1–P3 недоделаны (директивы/скелет ещё тяжелы), а НЕ повод
поднять лимит; поднимать лимит только с записью в журнал и обоснованием. final20 (ночь) был почти-проход
(спеки заполнены, 2 смысловые ошибки) — не переделывай то, что там сработало.

## 8. Анти-цикл и бюджет (жёстко; нарушение = СТОП + отчёт)
────────────────────────────────────────────────────────

- Максимум **1 живой eval-прогон на пакет**. Серийные «ещё один прогон» запрещены (это убило первую сессию).
- `fail` и `inconclusive` одинаково = стоп + отчёт, НЕ перезапуск и НЕ немедленный фикс.
- Подозрение на баг харнесса → сначала unit-тест, доказывающий баг, потом фикс, потом (в следующем
  пакете) прогон. Никогда «фикс → прогон → фикс → прогон».
- Правки харнесса и правки flow — в разных коммитах.
- **Глобальный бюджет:** если сделано ≥12 коммитов ИЛИ прошло ≥3 часов, а RC-гейт (P7.3) не достигнут —
  СТОП и отчёт оператору со сводкой, не продолжай молча.
- Никаких новых механизмов, не описанных в этом файле, без записи в журнал отклонений.

## 9. Оркестрация подагентов и отчётность
────────────────────────────────────────────────────────

Живые eval-прогоны (P7) НЕ запускай сам в основном контексте — делегируй **runner-подагенту**
(дешёвая модель, эфемерный, read-only по коду):
- Задача runner'а: запустить ОДИН прогон строго по RUNBOOK, дождаться, при `stuck=true` довериться
  авто-остановке харнесса, собрать bounded evidence (сценарий, worker-сессия, песочница, хронология
  наблюдений, diff --stat, вердикт judge, причинный вывод, что доказано/нет), вернуть ≤30 строк, умереть.
- Runner'у ЗАПРЕЩЕНО править любые файлы и перезапускать после fail.
Большие артефакты (раздутый diff, транскрипт песочницы) разбирай **analyst-подагентом** (read-only,
bounded-выжимка), чтобы не жечь свой контекст.

**Статус оператору** — короткой строкой после каждого пакета: `Pn: сделано <что>, коммит <sha>,
проверки <зелёные/детали>, отклонений <N>, дальше <Pn+1>`. При СТОП — что случилось, evidence, варианты.
