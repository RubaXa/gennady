# P9: Понятные инструменты вместо запретов + наращивание корпуса тестов

Формат: самодостаточные задачи P9.1…P9.6. Оператор передаёт агенту ссылку на этот файл и «возьми задачу P9.N».
Каждая задача = отдельный коммит с зелёным pre-commit. Анти-цикл §8 (RC-PLAN) действует.

## Принцип (согласован оператором + подтверждён ресёрчем)

Промптовые запреты — самый слабый рычаг: модель их обходит («не делай shell через 2>&1» → сделает иначе),
а рост запретов ухудшает вывод. Заменяем формулой:

> **позитивная инструкция + понятный инструмент + структурированная ошибка-с-примером +
> enforcement на уровне инструмента (не промпта) + честный выход для агента.**

Различать два вида «принуждения»:
- **промпт-запрет** («агенту сказано не делать») — убираем, он ненадёжен;
- **tool-level enforcement** («инструмент не делает молча плохое / опасного действия нет в пространстве
  выбора») — оставляем, он детерминированный и надёжный. Это НЕ «запрет модели».

Workaround (изворачивание) трактуем как **диагностический сигнал**: разобрать причину —
непонятный инструмент / нет честного выхода / конфликт требований — и устранить причину, а не глушить запретом.

Источники: Anthropic best-practices (говори что делать, не что не делать); «Structure Beats Verbosity»
(структурированная ошибка > прозы); capability minimization / least-privilege; affordance-дизайн (Норман).

## Правило тестов (сквозное для всех задач)

Каждый найденный дефект → **новый** регрессионный тест/фикстура, старые не переписывать. Корпус только растёт.
Тест сначала падает на текущем коде (доказывает дефект), потом зеленеет после фикса. Дубли допустимы —
если баг прошёл, значит существующие тесты его не покрывают.

## P9.1 — Корпус «непонятых случаев» (сначала, до фиксов инструментов)

**Зачем.** Зафиксировать реальные провалы прогонов как тесты до того, как чинить инструменты.
**Что сделать.** Добавить фикстуры/тесты на документированные дефекты (из реальных прогонов):
- `module == scope` → задвоенный путь `specs/<scope>/<scope>/<scope>.spec.md` (факт: `sdd-new module --scope fibonacci --module fibonacci`);
- worker фильтрует вывод чекера через `2>&1 | rg` (факт: `sdd-check n.spec.md --authoring 2>&1 | rg`);
- повторные полные Write вместо одного (факт: 9 write) — как метрика, не как запрет;
- остаточные `<!--` подсказки скелета в готовой спеке.
**Критерий готовности.** Тесты добавлены, падающие — падают и это зафиксировано в коммите; корпус подключён к прогону.

## P9.2 — `sdd-new`: объясняющий enforcement для module (не молчаливое создание)

**Зачем.** worker не понял идею модуля (назвал модуль как scope), а инструмент молча создал задвоенный путь.
**Что сделать (tool-level + структурированная ошибка-с-примером, БЕЗ промпт-запрета):**
- При `module == scope` и иных бессмысленных структурах `sdd-new` НЕ создаёт файл, а возвращает structured error:
  называет место, причину, **пример правильной структуры** и **пример имени** —
  «модуль — часть scope со своей ответственностью; структура `specs/<scope>/<module>/<module>.spec.md`;
  для scope `fibonacci` модуль обычно `nth`/`sequence`, не `fibonacci`; ты создаёшь `specs/fibonacci/fibonacci/` — так модули не устроены».
- Формулировки позитивные (как правильно), не «нельзя».
- Убрать дублирующие промпт-запреты про имена модулей, если они есть в директивах.
**Критерий готовности.** P9.1-тест на `module==scope` зеленеет; ошибка содержит пример структуры и имени.

## P9.3 — Честный выход вместо shell-workaround (вывод чекера)

**Зачем.** worker гонял `sdd-check --authoring 2>&1 | rg` — хотел **отфильтровать findings чекера**;
понятного способа не было, shell-redirect заблокирован policy → state залип `stuck=true` → judge FAIL.
Это «нет честного выхода», не злой умысел.
**Что сделать:**
- Дать `sdd-check --spec --authoring` **структурированный, фильтруемый вывод** (машиночитаемые findings:
  код, секция, что дозаполнить, пример) — чтобы worker'у НЕ нужно было `2>&1 | rg` для поиска своих ошибок.
- Убрать промпт/observer-запрет `2>&1` как основной механизм (он ловит симптом). Если redirect более не нужен
  для легитимной цели — он естественно исчезает; если инструмент его технически не требует — тем лучше.
- `stuck=true` от одиночного форматного shell не должен быть терминальным при валидном контенте
  (не наказывать за симптом, когда контент корректен).
**Критерий готовности.** Тест: worker получает findings чекера без shell-pipe; форматный redirect не залипляет state.

## P9.4 — Структурированные ошибки всех flow-инструментов (guidance, не дженерик)

**Зачем.** «Structure Beats Verbosity»: агент чинит ошибку надёжнее, когда сообщение называет место+причину+шаг+пример.
**Что сделать.** Пройти по `sdd-new`, `sdd-check`, `sdd-log`, `sdd-task`: ошибки/receipt должны давать
структурированный ответ (код, затронутый объект, конкретный следующий шаг, пример правильного вызова),
а не дженерик-код или длинную прозу. Schema-first.
**Критерий готовности.** Тесты на 2-3 типовые ошибки каждого инструмента: присутствуют место+причина+пример.

## P9.5 — Диагностика «понимания идеи» → signifiers инструмента

**Зачем.** Оператор: worker системно не понимает замысел (что такое модуль, декомпозиция).
**Что сделать (read-only диагностика → затем правки):**
- Собрать из worker-сессий прогонов места, где модель путается в концепциях (scope vs module, границы фазы,
  что заполнять) — bounded, без полного transcript.
- Превратить каждое системное непонимание в **signifier инструмента**: стейт/вывод CLI объясняет идею в момент
  действия (напр. `sdd-new module` печатает «модуль — часть scope: <примеры модулей этого scope>»), + фикстура в корпус.
- Калибровать по прогонам: допуски и формулировки выводить из фактов, не из догадок (куда реально корёжит модель).
**Критерий готовности.** Каждое найденное непонимание → либо signifier, либо фикстура; список задокументирован.

## P9.6 — Верификация

**Что сделать.** Один прогон P7.1 (анти-цикл §8, через runner на host, RUNBOOK). Замерить:
- module-путь корректный (нет `fibonacci/fibonacci`)?
- shell-workaround исчез (worker получает findings нормально)?
- число tool-вызовов и укладывается ли в бюджет?
- собрать новые «корёжения» → обратно в корпус (P9.1/P9.5).
**Критерий готовности.** pass → фиксация + отчёт; реальный fail/inconclusive → стоп + отчёт с evidence, без немедленного фикса.
