# H-adaptive-cli: ресёрч — детерминированное определение фазы + мягкие подсказки vs жёсткий next

Наблюдение: CLI `AUTHORING_SCOPE_NEXT` увёл worker'а назад в завершённую фазу → застrevание. Гипотеза оператора:
CLI должен детерминированно определять фазу по состоянию репо + мягко намекать, не диктовать.

## Вердикт: подтверждается, с важным уточнением про КОРРЕКТНОСТЬ

1. **Определение фазы — детерминированно из состояния репо, не инференс агента.** Control-plane/FSM паттерн.
   StateFlow: +13% success 5x дешевле (SQL), +28% 3x дешевле (ALFWorld) vs ReAct-free-form. LLM = stateless-узел,
   выбирающий из перечисленных легальных переходов, а не «догадайся». (arXiv 2403.11322, 2606.26924, HackerNoon control-flow)
2. **Неверный жёсткий next = value inversion** — агент с вводящим в заблуждение фидбэком работает ХУЖЕ, чем БЕЗ подсказки
   вовсе (HotpotQA: 44.8 → 22.3 без фидбэка → 4.7 с неверным). Агенты слепо доверяют tool-выводу, сильные — сильнее.
   Наш AUTHORING_SCOPE_NEXT — ровно этот механизм: не проигнорирован, а активно увёл. (arXiv 2606.21409, 2606.14476)
3. **Мягкая подсказка лучше жёсткого неверного — но выигрыш от КОРРЕКТНОСТИ сигнала, не от смягчения тона.**
   Агенты гиперчувствительны даже к мягким намёкам (arXiv 2505.11584). Смягчение снижает цену ошибки, корректность её
   устраняет — нужно и то, и другое.
4. **Заземление на evidence из репо** (read-only probing) вместо догадок — прямая практика spec-driven агентов (arXiv 2604.05278).

## Контраргументы (честно)
- Детерминированный детектор фазы САМ ошибается на неоднозначном/грязном репо (частичная миграция, прерванный прогон) →
  ложная уверенность вреднее (value inversion). **ОБЯЗАТЕЛЕН честный класс `AMBIGUOUS/UNKNOWN`** — не принуждать выбор фазы.
- Мягкую подсказку могут проигнорировать где нужен гейт — но данные говорят: агенты скорее ПЕРЕ-реагируют. Настоящие
  инварианты (безопасность, необратимое) остаются hard-гейтом на enforcement-точке; «куда дальше» — soft.
- FSM душит open-ended задачи, но наш flow authoring→scaffold→execute структурирован → FSM уместен (подтвердить эвалом).

## Реализация (control-plane паттерн)
Детектор фазы — детерминированный код: возвращает `{phase, available_transitions, confidence}` из git-состояния
(созданные/изменённые файлы, наличие спек, authoring-complete, статусы). При `confidence=low` → `AMBIGUOUS` +
подсказка «состояние неоднозначно, проверь X», а не выбор фазы. Инварианты = hard-гейт; «куда дальше» = soft-намёк.
Это снимает и баг (неверный жёсткий next), и риск ложной уверенности детектора.

## Дизайн A/B (2×2 + baseline)
- **A (контроль):** текущий жёсткий next (AUTHORING_SCOPE_NEXT-стиль), фаза не вычисляется.
- **B:** детерминированная фаза из git + мягкая подсказка «ты в X, обычно дальше Y».
- **B2:** детерминированная фаза + жёсткая директива (развести фактор «источник состояния» vs «тон» → 2×2).
- **no-hint baseline:** без next вовсе (ОБЯЗАТЕЛЕН — иначе value inversion не видно).
Adversarial-кейсы: clean-переходы; repeat (регресс на наш баг с уводом назад); ambiguous-репо (проверка честного UNKNOWN);
кейсы где реально надо назад (B не залипает вперёд).
Метрики: **phase_leak** (действие не в своей фазе/уход назад), **boundary_stall** (застревание на границе — прямо наш chain-2),
**wrong_hint_follow_rate** (на adversarial — value inversion), tool_calls/bash_probes, pass.
Подтверждение: B/B2 значимо снижают phase_leak+boundary_stall без регресса pass; на adversarial wrong_hint_follow_rate у B
ниже и не хуже no-hint baseline; снижение bash_probes; B vs B2 покажет вклад мягкого тона. Эффект-сайз ~StateFlow (десятки %).
