# План переноса SDD v1 (main) → SDD v2 (RC) — индекс

> Статус: В РАБОТЕ (аудит). Ведёт сессия «SDD v2 // Lead». Исполнитель — сессия «SDD v2 RC v6» (ветка `codex/sdd-v2-rc52-followup`, PR #25).
> Baseline: main `8bb38477` (0.9.0-next.3, заморожен) · RC `95329c19` (0.8.4) · merge-base `46c6d616` · 115 коммитов main после merge-base.
> Все документы — русский; идентификаторы, команды, пути — как в коде.

## 1. Цель и границы (из интервью, `01-INTERVIEW-DECISIONS.md`)

- RC → единственный SDD; v1 удаляется из дерева после переноса всего полезного; совместимость только через миграцию V1→V2.
- Каждое изменение main после merge-base получает вердикт: **уже закрыто в v2 / приземлить в v2 / не нужно** — с доказательством (file:line, коммит, тест) и, для групп проблем, минимальным eval.
- Ни одна задача не выдаётся исполнителю, пока карта не полная и не верифицирована независимо.

## 2. Метод

```
A. Инвентари (подагенты, Opus)     B. Треки (глубокий анализ)      C. Верификация (fresh eyes)     D. Документы плана
A1 дельта main                      B1 VERIFY                        V-A1, V-A2, V-A3a, V-A3b, V-A4, V-B*   10–60 (этот каталог)
A2 состояние v2                     B2 CHECK-LOG / журнал                                              → вопросы оператору
A3a/A3b дайджесты сессий            B3 SYNC-OWNERSHIP                                                  → брифы (после утверждения)
A4 issues akkrat                    B4 RULES · B5 RELEASE · B6 DIRECTIVES/SKILLS · B7 EVAL
```

Стандарт доказательства: каждое утверждение — file:line + коммит/PR/issue + тест; независимая перепроверка; запуск кода, где дёшево; по группе схожих проблем — один минимальный eval (G1 не-Node стек; G2 sync/ownership; G3 целостность журнала execute→audit→critic; G4 миграция V1→V2 на реальном слепке).
