# 70 — Протокол оркестрации Lead ↔ RC

> Статус: ЗАФИКСИРОВАНО решениями интервью 5.1–5.5 (см. `01-INTERVIEW-DECISIONS.md`).
> Lead = сессия «SDD v2 // Lead» (`local_ab51a8c5-017e-4432-b0ba-306a3aac8f66`, ветка `sdd-v2-audit-migration-3b23b1`).
> RC = сессия «SDD v2 RC v6» (`local_45cab169-342c-44fe-92f9-11b0f55df201`, ветка `codex/sdd-v2-rc52-followup`, PR #25).

## Принципы

1. **Ни одной задачи до снятия неопределённости.** Задачи выдаются только из документа плана со статусом `ГОТОВ К ВЫДАЧЕ`, у которого все утверждения верифицированы (CONFIRMED) и нет открытых вопросов оператора.
2. **Одна задача в RC за раз.** Следующая — только после отчёта и его приёмки Lead.
3. **Полномочия.** Техвопросы, ответ на которые есть в документах плана, закрывает Lead. Выбор архитектуры, изменение скоупа, удаления, любые записи в GitHub — только оператор.
4. **Ветка.** Все коммиты переноса — в `codex/sdd-v2-rc52-followup`. Каждый коммит проходит полный гейт (`npm run check`), без `--no-verify`.
5. **Язык.** Общение и документы — русский; директивы, скиллы, код, идентификаторы — английский.
6. **Доказательства.** Отчёт без коммит-sha, имени теста и команды-доказательства не принимается.

## Цикл

```
Lead: документ плана → верификация подагентами → ГОТОВ К ВЫДАЧЕ → бриф
RC:   выполнение → коммит(ы) в PR #25 → отчёт
Lead: приёмка (перепроверка доказательств, при необходимости подагентом) → обновление документа плана
      → вопросы оператору (если появились) → следующий бриф
```

## § Доказательство и визуализация результата брифа (D-53, с Брифа 1/5)

**Ветка и PR.** Исполнитель (`rc-executor`) работает на ветке `lead/<task-id>` от `origin/codex/sdd-v2-rc52-followup`, коммиты локально, пуш и PR — Lead (D-52). PR открывается в `codex/sdd-v2-rc52-followup` (draft), описание PR = отчёт изменений целиком. После верификации Lead вливает PR merge-коммитом (без squash: SHA коммитов должны совпадать с отчётом). Задача на доске → ВЫПОЛНЕНО с номером PR и SHA.

**Отчёт изменений** (`_raw/reports/R-<task-id>.md`, обязательные разделы):
1. **Файлы.** Таблица: путь → новый / правка / удалён → смысловое изменение одной фразой (не дифф) → чем доказано (тест/команда). Каждый файл из `git diff --stat` имеет строку.
2. **Архитектура было / стало.** Две mermaid-диаграммы затронутого контура (flowchart компонентов или sequenceDiagram; для сценариев — use-case flowchart). Каждая стрелка «стало» соответствует реальному вызову/зависимости с `file:line`. Нетронутые части контура — серым, новые — выделены.
3. **Доказательства.** Каждый пункт ПРИЁМКИ брифа: команда, фактический вывод, exit-код, ВЫПОЛНЕНО / НЕ ВЫПОЛНЕНО.
4. **Отклонения и открытые вопросы**, команды пуша для Lead.

**Верификация** (`plan-verifier`, свежие глаза): каждый файл диффа имеет строку; каждая команда перезапущена; каждая стрелка «стало» найдена в коде; числа пересчитаны. Итог: блокирующее / неблокирующее / подтверждено. Без «подтверждено» пуша нет.

**В чате оператору** — короткая версия: таблица файлов (≤10 строк) и одна схема «было → стало»; ссылка на PR с полной версией.

**Именованные воркеры** (`.claude/agents/`): `rc-executor` (Sonnet), `plan-verifier` (Opus), `plan-editor` (Sonnet), `research-analyst` (Opus). Новый агент — только при поломке существующего; имя и роль постоянны.

## § Пачки и PR (D-56, D-57, с 2026-09-08)

1. **Очередь** (`62-BATCH-QUEUE.md`): пачки по темам, 3–8 задач, сначала автономные (без решений оператора и обсуждений), затем требующие разговора. Пачка называется словами, не кодами.
2. **Исполнение пачки**: ветка `lead/<тема>` от головы `codex/sdd-v2-rc52-followup`; задачи внутри — последовательно одним `rc-executor` (или двумя в разных деревьях при непересекающихся файлах); каждая задача — свой коммит и свой отчёт `_raw/reports/R-<id>.md`; независимая проверка `plan-verifier` на пачку целиком.
3. **PR**: Lead пушит ветку и открывает PR в `codex/sdd-v2-rc52-followup` с описанием по D-57. В чат — три строки: тема, ссылка на PR, что проверить глазами.
4. **Мерж** — оператор. Lead перед стартом зависимой пачки проверяет `gh pr view` (MERGED); независимые пачки идут параллельно от текущей головы.
5. **Красная задача** внутри пачки не держит пачку: выносится в отдельную ветку/пачку с пометкой в описании PR.

## § Условия безусловной остановки и stop-criterion (GAP-P-1, с 2026-09-08)

**Предмет.** Гейт адекватности (`06-ADEQUACY-GAP.md` §2.2 T12, §2.3 №22, §2.4 G-11) нашёл, что ни один пункт плана не имел статуса «проверено на SDD v2» и что протокол не содержал ни явных stop-conditions, ни требования null/stop-criterion на измеряющие задачи — единственное известное лекарство против **composition fallacy** (`06:384`: ошибка на раннем шаге может пройти все локальные гейты и красиво коррелировать с неполным графом дальше). Раздел закрывает оба MUST-lite пункта одним документом; сам он **документный, не измеряющий** (`06:384`).

### Когда исполнитель (`rc-executor`) обязан остановиться

Список закрытый; ни один из пяти классов не «додумывается» по ситуации — при срабатывании исполнитель прекращает работу над задачей/пачкой, пишет `СТАТУС: BLOCKED` в отчёт (шаблон выше) и передаёт решение Lead без попытки обойти или смягчить формулировку:

1. **Стоп-условия брифа.** Раздел брифа «ВОПРОСЫ НАЗАД» — не пожелание, а обязывающий список условий; при совпадении текста условия с наблюдаемым фактом исполнитель обязан остановиться и спросить Lead, а не выбирать самостоятельно между несколькими прочтениями брифа.
2. **Красный гейт.** `npm run check` (или его часть — `sdd-check --all`, тесты, типы, линт) не проходит, либо предикат «ноль новых ошибок» (`GAP-B-1`/`GAP-B-2`, `pre-push`-хук) отклоняет push. Это встроенный стоп-сигнал (`62-BATCH-QUEUE.md:22`: «любая пачка, добавляющая новую ошибку `sdd-check`, физически не запушится»), не решение исполнителя — красная задача не чинится втихую расширением baseline (изменение baseline — отдельное operator-approved решение, `61:226`).
3. **Конфликт с невлитыми PR.** Файлы задачи пересекаются с файлами пачки, чей PR ещё не в статусе `MERGED` (`gh pr view`), и последовательное слияние с ней не было явно предусмотрено в очереди (`62-BATCH-QUEUE.md` §0 «Предпосылки» — только невлитые пачки). Исполнитель не сливает и не перебазируется через голову Lead.
4. **Открытое решение оператора.** Задача или её зависимость несёт статус `ЗАБЛОКИРОВАН <причина>` на доске (`61 §5.3`), ссылается на нерешённый `O-*` (`00-INDEX.md` §4) или требует выбора из перечисленных на доске вариантов (архитектура, удаление, запись в GitHub — Принцип 3 выше). Исполнитель не выбирает вариант сам, даже когда один из них выглядит очевидным.
5. **Лимит попыток.** Повтор одного и того же блокирующего набора находок без нового доказательства (нового `file:line`, нового прогона, нового вывода команды) не продолжает цикл — это тот же класс остановки, что вводит задача `T-B6-16` (`61:247`, Пачка 5) для фазового агента внутри RC; на уровне Lead↔RC цикла применяется симметрично: второй отчёт с теми же находками, что и первый, без новых доказательств, останавливает бриф, а не порождает третью попытку.

### Stop-criterion пачки

**Определение (по образцу R2 №22, `06:153`: baseline, falsifiable claim, owner, null/stop criterion).** Каждая **измеряющая** задача — та, чей результат приёмки не бинарный факт кода/теста, а число, вердикт корпуса, метрика или сравнение с baseline (классы: `E-*`/`GAP-E-*` эвал, `B2-22` versioned-baseline переход, `IDN-3` repo-wide подсчёт, `T-B6-10` бюджеты, любая задача с «измерение до/после» в колонке «Чем доказываем») — обязана называть в брифе **stop-criterion пачки**, предзаявленный **до** исполнения:

- **baseline** — точка отсчёта, от которой считается результат (например `GAP-B-1` — 198 error/431 warn на `227c03a8`; `E-22` — golden-v1 корпус; `B2-22` — версионированный baseline 140 строк корпуса);
- **falsifiable claim** — что именно проверяется в форме, которую можно опровергнуть наблюдением, не «стало лучше», а «метрика X не превышает Y» / «класс находок Z не появляется»;
- **owner** — кто в плане отвечает за задачу (id задачи доски, не абстрактный «трек»);
- **null/stop criterion** — при каком конкретном наблюдаемом исходе пачка считается **провалившейся**, сформулированный заранее, а не постфактум: например «если после `B2-20` (WARN→ERROR) `sdd-check --all` на самомигрированном корпусе (`E-14`) даёт хотя бы один новый error относительно `golden-v1` (`E-22`) — пачка провалена, порог не включается» (уже сформулировано именно так в приёмке B2-20, `61:83`, «06 §5.2 п.37»).

Stop-criterion пишется в брифе рядом с ПРИЁМКОЙ, **до** того как задача выдана в RC — постфактум переформулированный критерий не считается стоп-критерием (иначе это рационализация результата, а не проверка гипотезы). Задачи, приёмка которых уже сформулирована как выше (`GAP-B-1`, `B2-20`, `B2-22`, `E-22`, `E-23`, `E-07` bar исполнимости), стоп-критерию уже удовлетворяют — раздел не требует их переписывать, только явно называть в новых брифах по этому образцу.

### Кто снимает остановку

По Принципу 3 выше, без исключений для стоп-условий: **Lead** снимает остановку, когда ответ уже есть в документах плана (техвопрос, уточнение формулировки, ссылка на существующую задачу-владельца) — фиксирует ответ в документе и переоткрывает бриф. **Оператор** снимает остановку, когда решение требует выбора архитектуры, изменения скоупа, удаления данных или записи в GitHub, либо когда стоп-условие вскрыло открытый `O-*`/новое противоречие — Lead формулирует вопрос оператору (по образцу `00-INDEX.md` §4), исполнение не продолжается до ответа. Остановку по красному гейту (класс 2) технически снимает исправление причины (коммит, зелёный прогон) — но подтверждает снятие всё равно Lead через `plan-verifier`, не сам `rc-executor`: самопроверка исполнителя не заменяет независимую верификацию (см. § Доказательство выше).

## § Правила брифа по итогам аудита волн (AUDIT-WAVES-2026-09-10 §4.3, с 2026-09-10)

Обязательны в каждом брифе исполнителю и проверяются верификатором:
1. **Перенос из v1** — перед переносом текста найти последний коммит, менявший его (`git log -S`), и переносить актуальную редакцию; абзац, описывающий механику, которой в v2 нет, не переносится, а называется в отчёте с решением L-N (прецеденты L-25, L-27).
2. **Замок** — считается замком, только если уронен мутацией: отвязать инвариант и показать красный; в отчёте — команда мутации и её вывод.
3. **Числа** — любое число в отчёте есть вывод команды, вставленный целиком и воспроизводимый; «на слово» не принимается.
4. **Спеки** — закрывая задачу, названную владельцем записи `Usage Waiver` или строки спеки, обязательно снять запись или явно пересмотреть её.
5. **Повторная проверка** — любая блокирующая находка ⇒ повторная независимая проверка правок до пуша и PR (нарушено один раз, пачка 21; исправлено постфактум).
6. **Токен отложенного решения** — каждый открытый пункт отчёта несёт токен по L-16, не прозу.
7. **Без `git stash`** — стек стешей общий для всех worktree репозитория; исполнители и верификаторы делают мутации только во временных клонах/копиях (`git worktree add --detach <tmp>`, файловая копия), никогда через `git stash`/`stash pop` (инцидент пачки 13: подхвачен чужой стеш; пачка 16: мутации через stash — сработало, но риск тот же).
