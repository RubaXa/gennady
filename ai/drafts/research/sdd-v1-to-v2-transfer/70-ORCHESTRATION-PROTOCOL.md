# 70 — Протокол оркестрации Lead ↔ RC

> Статус: ЗАФИКСИРОВАНО решениями интервью 5.1–5.5 (см. `01-INTERVIEW-DECISIONS.md`).
> Lead = сессия «SDD v2 // Lead» (`local_ab51a8c5-017e-4432-b0ba-306a3aac8f66`, ветка `sdd-v2-audit-migration-3b23b1`).
> RC = сессия «SDD v2 RC v6» (`local_45cab169-342c-44fe-92f9-11b0f55df201`, ветка `codex/sdd-v2-rc52-followup`, PR #25).

## Принципы

1. **Ни одной задачи до снятия неопределённости.** Задачи выдаются только из документа плана со статусом `ГОТОВ К ВЫДАЧЕ`, у которого все утверждения верифицированы (CONFIRMED) и нет открытых вопросов оператора.
2. **Одна задача в RC за раз.** Следующая — только после отчёта и его приёмки Lead.
3. **Полномочия.** Техвопросы, ответ на которые есть в документах плана, закрывает Lead. Выбор архитектуры, изменение скоупа, удаления, любые записи в GitHub — только оператор.
4. **Ветка.** Все коммиты переноса — в `codex/sdd-v2-rc52-followup`. Каждый коммит проходит полный гейт (`npm run check`), без `--no-verify`.
5. **Язык.** Общение и документы — русский; директивы, скиллы, код, идентификаторы — английский.
6. **Доказательства.** Отчёт без коммит-sha, имени теста и команды-доказательства не принимается.

## Шаблон отчёта (RC → Lead)

```
ОТЧЁТ <NN-документ>/<номер задачи>: <короткое имя>

СТАТУС: DONE | PARTIAL | BLOCKED
КОММИТЫ: <sha> <subject> (по одному на строку)
СДЕЛАНО: <что именно, file:line>
ДОКАЗАТЕЛЬСТВА: <команда → результат>, <тест → pass/fail>, <eval → verdict>
ОТКЛОНЕНИЯ ОТ БРИФА: <что и почему> | нет
НАЙДЕНО ПОПУТНО: <дефекты/наблюдения, не входящие в задачу>
ВОПРОСЫ: <нумерованный список> | нет
```

## Цикл

```
Lead: документ плана → верификация подагентами → ГОТОВ К ВЫДАЧЕ → бриф
RC:   выполнение → коммит(ы) в PR #25 → отчёт
Lead: приёмка (перепроверка доказательств, при необходимости подагентом) → обновление документа плана
      → вопросы оператору (если появились) → следующий бриф
```

## § Доказательство и визуализация результата брифа (D-53, с Брифа 1/5)

**Ветка и PR.** Исполнитель (`rc-executor`) работает на ветке `lead/<task-id>` от `origin/codex/sdd-v2-rc52-followup`, коммиты локально, пуш и PR — Lead (D-52). PR открывается в `codex/sdd-v2-rc52-followup` (draft), описание PR = отчёт изменений целиком. После верификации Lead вливает PR merge-коммитом (без squash: SHA коммитов должны совпадать с отчётом). Задача на доске → ВЫПОЛНЕНО с номером PR и SHA.

**Отчёт изменений** (`_raw/reports/R-<task-id>.md`, обязательные разделы):
1. **Файлы.** Таблица: путь → новый / правка / удалён → смысловое изменение одной фразой (не дифф) → чем доказано (тест/команда). Каждый файл из `git diff --stat` имеет строку.
2. **Архитектура было / стало.** Две mermaid-диаграммы затронутого контура (flowchart компонентов или sequenceDiagram; для сценариев — use-case flowchart). Каждая стрелка «стало» соответствует реальному вызову/зависимости с `file:line`. Нетронутые части контура — серым, новые — выделены.
3. **Доказательства.** Каждый пункт ПРИЁМКИ брифа: команда, фактический вывод, exit-код, ВЫПОЛНЕНО / НЕ ВЫПОЛНЕНО.
4. **Отклонения и открытые вопросы**, команды пуша для Lead.

**Верификация** (`plan-verifier`, свежие глаза): каждый файл диффа имеет строку; каждая команда перезапущена; каждая стрелка «стало» найдена в коде; числа пересчитаны. Итог: блокирующее / неблокирующее / подтверждено. Без «подтверждено» пуша нет.

**В чате оператору** — короткая версия: таблица файлов (≤10 строк) и одна схема «было → стало»; ссылка на PR с полной версией.

**Именованные воркеры** (`.claude/agents/`): `rc-executor` (Sonnet), `plan-verifier` (Opus), `plan-editor` (Sonnet), `research-analyst` (Opus). Новый агент — только при поломке существующего; имя и роль постоянны.
