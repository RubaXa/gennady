# SDD v2 Flow Simulation Protocol

## Цель

Инструменты (`cli/cmd/*`, `shared/sdd/*`) покрыты юнит-тестами — это проверяет их изолированно.
Директивы (`ai/directives/sdd-v2/*.directive.xml`) — не код, юнит-тест их не запустит. Единственный
способ проверить, что LOGIC_SWITCH выбирает правильную ветку, что STOP срабатывает там, где написано,
и что агент не тащит в контекст директиву, которую не должен был загружать — живой прогон агентом
по фиксированному сценарию, с последующей проверкой трейса против текста директивы.

Это верификация ветвлений и лайфсайклов флоу, а не самих артефактов SDD (спек / тикетов) — те
проверяет `sdd-check` / `gennady lint`.

## Роли

**Executor** — дешёвая модель, слепой прогон. Получает ТОЛЬКО:

- карту сценария из `ai/flow-sim/scenarios/` БЕЗ секции `## Checkpoints` (оркестратор вырезает её
  перед выдачей — Executor не должен знать, что проверяют),
- фикстуру (собирает её сам по рецепту карты, дословно),
- путь к изолированной песочнице (выдаёт оркестратор).

Executor не знает, что он участвует в проверке директивы — он просто выполняет роль оператора SDD
и агента SDD как обычно, честно, до `## Stop`.

**Verifier** — сильная модель. Получает: полную карту сценария (включая Checkpoints), TRACE от
Executor, и `git diff` фикстуры (что реально изменилось на диске). Выносит вердикт по каждому
Checkpoint: `CONFIRMED` (трейс + текст директивы совпадают) или `VIOLATED` (с уликой — строка трейса
против строки директивы). Отдельно — секция «Импровизации»: свободные находки о том, что Executor
сделал сверх карты, или недоделал из предписанного.

**Arbiter** — разводит `VIOLATED` на два принципиально разных случая:

- **дефект директивы** — сама директива неоднозначна / противоречива / даёт агенту возможность
  свернуть не туда при точном следовании тексту → правится директива;
- **слабость исполнителя** — директива однозначна, Executor её просто не выполнил → это сигнал
  _упростить_ директиву (слишком длинная/сложная для дешёвой модели), а не чинить директиву как
  дефектную.

Arbiter не запускается автоматически в рамках одной карты — это ручной шаг оператора после того, как
Verifier выдал `VIOLATED`.

## TRACE_FORMAT

Executor пишет трейс построчно, append-only, СТРОГО в типизированном виде — свободная проза вне
этих строк запрещена (Verifier не парсит естественный язык, он ищет типизированные записи).

Канонична голая типизированная строка — префикс `T<n> | ` ОПЦИОНАЛЕН (3 прогона из 5 его теряли;
требовать его — упрощать было не о чем упрощать, раз Verifier его фактически не использует). Verifier
ссылается на находку по номеру строки ФАЙЛА `TRACE.md` (`строка 42`), не по `T<n>`. Executor может
проставлять `T<n>` для собственного удобства — это не ошибка, просто не проверяется и не требуется:

```
directive: <file> loaded
step: <STEP_ID>
branch: <WHEN label дословно>
tool: <команда дословно> → exit=<N>
  output: <краткий вывод команды — что она напечатала/вернула, в одну-две строки>
show: <перечень секций/маркеров показанного оператору блока>
ask: <канал: AskUserQuestion|QUESTION_FORMAT> — <заголовок вопроса>
halt: <H_*> — <причина>
stop: per-map — <условие Stop дословно>
operator: <вопрос агента> ← <ответ из скрипта>
write: <путь>
note: <отклонение/неуверенность>
```

- `directive:` — каждый файл директивы в момент, когда агент его READ_AND_USE_DIRECTIVE'ит (не при
  каждом обращении — один раз на загрузку).
- `step:` — каждый переход `<Step id="...">` внутри активной директивы.
- `branch:` — дословная копия `WHEN`-условия из `LogicSwitch`/`LOGIC_SWITCH`, которое сработало (не
  пересказ, не номер — точный текст label).
- `tool:` — дословная команда (включая флаги, включая `--write` / его отсутствие) и код возврата.
- `  output:` — подстрока строго ПОД своей строкой `tool:`, с отступом (двумя пробелами), краткий
  фактический вывод этой команды (что она напечатала в stdout/stderr, или структурный итог — «3
  units, 2 tickets, 0 orphans»). Не отдельная типизированная строка трейса — привязана к
  предшествующему `tool:` и не имеет смысла без него. Без неё Verifier не может проверить чекпоинты
  про СОДЕРЖИМОЕ того, что инструмент вернул (не только что он был вызван и с каким `exit=`) —
  легитимизирована, потому что несколько прогонов её изобрели самостоятельно именно по этой причине.
- `show:` — ОБЯЗАТЕЛЬНА для каждого содержательного сообщения оператору (decision-card, картина
  survey, отчёт формы, манифест секций, итог гейта): перечень секций/маркеров того, что именно было
  показано. Без этой строки чекпоинты про содержимое показанного блока непроверяемы — Verifier не
  видит текста, который агент фактически вывел, только то, что Executor заявил строкой трейса.
- `ask:` — каждый вопрос, заданный оператору через определённый директивой канал (`AskUserQuestion`
  или текстовый `QUESTION_FORMAT`), с указанием канала и заголовка вопроса. Дополняет `operator:` —
  `ask:` фиксирует ЧТО и КАК было спрошено, `operator:` фиксирует связку вопрос-ответ.
- `halt:` — ТОЛЬКО настоящий `H_*` из текста директивы (`H_NOT_V1`, `H_NO_PORTAL`,
  `H_SCOPE_NOT_CONFIRMED` и т.п.), с причиной в одну фразу. Остановка по карте (`## Stop`) — это
  НЕ `halt:`, это `stop:` (см. ниже); `halt:` зарезервирована исключительно за директивными
  H-гейтами.
- `stop:` — остановка прогона по условию `## Stop` карты сценария (не по директивной `H_*`-гейту):
  `stop: per-map — <условие Stop дословно>`, последняя строка трейса.
- `operator:` — вопрос, который агент задал оператору, и какой ответ был взят (следующий неиспользованный
  из Operator Script).
- `write:` — КАЖДЫЙ файл, который агент создал или изменил на диске, БЕЗ ИСКЛЮЧЕНИЯ по инструменту
  записи. Правка через Edit-подобный инструмент — тоже `write:` (`tool: edit <путь>` — если Executor
  пишет и такую строку — фиксирует ВЫЗОВ инструмента, но не заменяет обязательную `write: <путь>`
  для самого факта записи на диск; строки дополняют друг друга, одна не покрывает другую).
- `note:` — любое отклонение, неуверенность, или момент, где Executor не был уверен, что делать.

## Правила исполнителя

- Фикстуру собрать **дословно** по рецепту `## Fixture` карты, в изолированной директории — путь
  передаёт оркестратор, никогда не текущий репозиторий.
- CLI-команды звать `npx tsx <worktree>/cli/gennady.ts <cmd> <args>` (путь к worktree gennady — от
  оркестратора), НЕ `npx gennady` — фикстура не проходила path-normalizer.
- Если `npx tsx` падает (403 / нет сети до реестра пакетов) — легитимный фолбэк:
  `<worktree>/node_modules/.bin/tsx <worktree>/cli/gennady.ts <cmd> <args>`, с ОДНОЙ строкой `note:`,
  фиксирующей переход на фолбэк и причину. Главное инвариант — бить строго в `<worktree>` (тот, что
  выдал оркестратор), никогда в `~/Developer/gennady` или любой другой чужой чекаут.
- `TRACE.md`/`DIFF.txt` прогона писать ВНЕ git-репозитория фикстуры — например, в родительском
  каталоге песочницы, а не внутри неё. Если фикстура сама является git-репозиторием, её `git status`
  должен читаться как «что изменил флоу» и ничего больше — файлы прогона (трейс, дифф) там не место.
- В песочнице легитимен ТОЛЬКО baseline-коммит (`git add -A && git commit -m fixture-baseline`) ДО
  запуска флоу. НИКАКИХ дополнительных коммитов фикстуры по ходу прогона, если карта явно не велит —
  промежуточный коммит смешивает то, что сделал флоу, с тем, что сделал Executor, и убивает
  `git diff`/`git --follow`-проверяемость Verifier'а (карта S11 однажды слила move+restructure в один
  коммит и уничтожила `git --follow`-проверяемость самим этим смешением). Для карт, где сама
  директива-первоисточник по своему тексту коммитит (например, вызывает `git mv` /
  `git commit` как часть шага) — карта ОБЯЗАНА явно перечислить в `## Fixture` или `## Stop`, какие
  коммиты внутри прогона легальны и на каком шаге; Executor коммитит только то, что карта так назвала,
  ничего сверх.
- Чтение любых файлов проекта (внутри фикстуры или директив/скиллов) — тоже `tool:`-строки в трейсе
  (`cat <path>`, чтение через Read и т.п.), не тихие фоновые действия. Реестр правил и любые файлы
  проекта читать ТОЛЬКО внутри песочницы фикстуры, никогда из `<worktree>` — единственное исключение:
  `ai/directives/` и `ai/skills/` самого флоу (`v2`-директивы, которые прогон и проверяет).
- На вопросы оператора отвечать строго по `## Operator Script` — следующий неиспользованный ответ по
  порядку. Скрипт кончился, а агент всё ещё спрашивает → `note` в трейсе, фиксирующая расхождение, и
  прогон завершается (это находка для Verifier, не тупик для Executor; НЕ `halt:` — это не
  директивный `H_*`-гейт).
- `## Stop` карты — обязательная стоп-точка. Карты режут прогон РАНЬШЕ естественного конца директивы
  именно для этого — не жечь токены на шаги, которые чекпоинты не проверяют. Остановиться на
  условии `Stop`, даже если директива по своему тексту продолжила бы работать — записать это как
  `stop: per-map — <условие Stop дословно>`, последней строкой трейса.
- Один прогон — одна карта. Не пытаться пройти сразу несколько сценариев в одной сессии.

## Правила верификатора

- Каждый Checkpoint сверяется ДВАЖДЫ: против TRACE (это случилось?) и против текста
  директивы-первоисточника (это именно то, что директива предписывает?). Вердикт без второй сверки
  не принимается — Verifier обязан процитировать директиву.
- Вердикт по каждому Checkpoint — `CONFIRMED` / `VIOLATED`, с уликой: конкретный номер строки файла
  `TRACE.md` (`строка 42`, не `T<n>` — префикс `T<n>` опционален и Verifier на него не полагается)
  ПРОТИВ конкретной цитаты из директивы.
- Секция «Импровизации» (отдельно от Checkpoints) — свободные находки:
  - что Executor сделал, чего карта/директива не велела (лишний tool-вызов, лишняя загрузка
    директивы, самовольное продолжение после `Stop`);
  - что из предписанного Executor пропустил (не задал обязательный вопрос, не вызвал гейт).
- Финальный вердикт на карту: `PASS` (все Checkpoints `CONFIRMED`, нет находок) / `PASS_WITH_FINDINGS`
  (Checkpoints `CONFIRMED`, но есть находки в «Импровизациях») / `FAIL` (хотя бы один `VIOLATED`).

## Детерминизм и повторяемость

- Одна карта = один воспроизводимый прогон: фиксированная фикстура + фиксированный Operator Script +
  фиксированный Stop → один и тот же маршрут по директивам при точном исполнении.
- Карты версионируются в git (`ai/flow-sim/scenarios/`) — правки карты идут тем же PR-процессом, что
  правки директив.
- Трейсы и `git diff` фикстуры — эфемерные артефакты прогона. Пишутся в scratch-директорию ВНЕ
  репозитория (её путь даёт оркестратор), в `ai/flow-sim/` не коммитятся.
