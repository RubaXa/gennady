# Research: репозиторий ponytail (DietrichGebert) — формат общения и структура промптов

<!--SECTION:STATUS-->

## Status

proposed · 2026-08-22 · репозиторий изучен целиком через GitHub API и raw-файлы (README, `AGENTS.md`, все шесть `skills/*/SKILL.md`, хуки, `docs/`, часть `benchmarks/results/*.md`). Ключевой вывод сразу здесь: ponytail — не директива процесса, а поведенческий скилл («будь ленивым senior-разработчиком») с шестью дочерними мини-скиллами отчётности; прямого аналога SDD-директиве (много шагов одного процесса) в репозитории нет. Зато формат общения с оператором и инженерия самого текста скилла — ровно то, что просил посмотреть оператор, и там есть конкретные, обильно задокументированные паттерны. Решение по применимости — за оператором.

## Problem

gennady сейчас держит несколько открытых решений по SDD-директивам: ленивые скелеты ≤6k токенов + пакеты шагов через CLI, полные предложения со структурной плотностью вместо телеграфного стиля, и контракты общения с оператором (форматы вопросов, прогресс-строки, message-layout), которые итерируются многократно и остаются «больной зоной». Оператор попросил посмотреть репозиторий `github.com/dietrichgebert/ponytail` — популярный (по факту 108k+ звёзд) скилл для AI-агентов — на две вещи: (1) как он устроен как формат общения агента с человеком (структура сообщений, вопросы, прогресс, стиль инструкций); (2) как написаны его промпты/инструкции (размер, структура, ленивость, плотность) — и сравнить с решениями gennady.

## Options

### Академия

Ponytail сам — не академическая работа, а инженерный проект практика; прямых ссылок на статьи в репозитории нет. Но его собственный benchmark-харнесс случайно замыкает открытый вопрос из соседнего ресёрча gennady про телеграфный стиль.

**Прямая связка с `caveman` из прошлого ресёрча gennady.** `2026-08-22-prompt-compression.research.md` разбирал академическую работу Telegraph English (`arXiv:2605.04426`) и практику «caveman»-компрессии вывода, но не нашёл контролируемого эксперимента про перенос телеграфного регистра в реальную агентную сессию. Ponytail держит в своём харнессе третье плечо — именно `caveman` (`github.com/JuliusBrussee/caveman`, тот же проект, что и в прошлом ресёрче) — и публикует числа против него на одних и тех же задачах. В агентном (не однократном) прогоне на 90 реальных сессиях Claude Code caveman не улучшает, а *ухудшает* три из четырёх метрик против безскилльного бейзлайна: токены +7%, стоимость +3%, время +2% (LOC −20%, то есть код короче, но сессия дороже и дольше). Это не прямой ответ на вопрос «протекает ли телеграфный регистр инструкции в стиль вывода молча», но первое найденное измерение обратного эффекта телеграфной компрессии в *многоходовой* агентной работе, а не в однократной генерации — предыдущий ресёрч располагал только однократными (single-shot) числами компрессоров. Авторы ponytail сами делают ту же методологическую оговорку, что нашёл прошлый ресёрч про caveman: их же более раннее «однократное» измерение (80–94% меньше кода) было артефактом слабого бейзлайна (бессистемная модель добавляет прозу и варианты), и они прямо откатили заявление после независимого issue (#126), заменив его агентным замером.

**Косвенная связка с работой про архитектуру Agent Skills.** `2026-08-22-lazy-directive-loading.research.md` цитирует обзор `arXiv:2602.12430` про трёхуровневый progressive disclosure (метаданные → тело SKILL.md по триггеру → файлы уровня 3+ по требованию). Ponytail — не цитата этой архитектуры, а живая реализация той же формы в масштабе реального продукта с 108k+ звёзд (см. «Лидеры рынка» и «Готовые инструменты» ниже): маленькое эагерное ядро (`AGENTS.md`) + лениво триггерящееся тело (`SKILL.md`) + отдельная лёгкая фильтрация по режиму при инъекции.

### Лидеры рынка

Ponytail — не платформа, а продукт-скилл, но его рыночный успех (проверено напрямую GitHub API, не по сниппетам) — сам по себе рыночный сигнал: 108 041 звезда, 5 968 форков, MIT-лицензия, опубликован на npm (`@dietrichgebert/ponytail`), версия `4.9.0`, создан 2026-06-12, последний push 2026-08-07, топ на GitHub Trending. Он портируется на 20+ агентных хостов (Claude Code, Codex, Cursor, Windsurf, Cline, GitHub Copilot/Copilot CLI, Gemini CLI, OpenCode, Hermes Agent, pi, Kiro, Qoder, Zed, Amp, Jules и другие) через задокументированный слой адаптеров (`docs/agent-portability.md`): хосты с поддержкой скиллов/хуков получают полный `skills/` + `hooks/`, хосты без неё — только always-on инструкционный файл (`AGENTS.md`), скопированный побайтово в дюжину хост-специфичных мест (`.cursor/rules/ponytail.mdc`, `.windsurf/rules/ponytail.md`, `.clinerules/ponytail.md`, `.github/copilot-instructions.md` и т.д. — сверено напрямую, файлы идентичны `AGENTS.md`). Это на практике подтверждает вывод предыдущего lazy-loading-ресёрча («маленькое эагерное ядро + длинный ленивый хвост», ранее подтверждённый только цифрами Anthropic Tool Search и правилом Cursor 1–2 always-apply) конкретным, крупномасштабным, не-вендорским примером: эагерное ядро `AGENTS.md` — 2493–2620 байт (≈600–650 токенов, грубая оценка агента по байтам, не измерено токенизатором) против ленивого тела `skills/ponytail/SKILL.md` — 6637 байт (≈1600–1800 токенов) — то есть тело примерно в 2.5–3 раза больше ядра и всё равно укладывается в потолок ≈5000 токенов из спецификации Agent Skills.

Проект держит копии эагерного ядра синхронными механически, а не вручную: `scripts/check-rule-copies.js` — отдельный тест, сверяющий, что все хост-специфичные копии `AGENTS.md`/`ponytail.mdc`/`.clinerules` побайтово совпадают. У gennady риск другой формы (директивы генерируются один раз из партиалов Handlebars, а не копируются вручную по хостам), но сам инстинкт — «гарантировать одинаковость эагерного ядра явной проверкой, а не доверием» — переносим.

Режим-переключатель `lite | full | ultra` разрешается по приоритету `переменная окружения > конфиг-файл > дефолт (full)` — компактный способ дать оператору ручку без раздувания эагерного ядра: сама ручка не в тексте промпта, а вовне (env/config), а промпт лишь читает результат.

### Готовые инструменты

Основная находка — сам ponytail как инструмент. Раскладка по частям.

**Структура репозитория.** Шесть скиллов в `skills/*/SKILL.md`: `ponytail` (режим поведения, персистентный), `ponytail-review` и `ponytail-audit` (находки над диффом/репозиторием), `ponytail-debt` (сбор оставленных меток долга), `ponytail-gain` (карточка измеренного эффекта), `ponytail-help` (справка). Плюс `AGENTS.md` (компактное эагерное ядро для хостов без скиллов), `hooks/` (инъекция при старте сессии, персистентность режима, statusline-индикатор), `commands/*.toml` (slash-команды для хостов на TOML), `benchmarks/` (полный eval-харнесс).

**Формат общения — то, что прямо просил оператор.**

1. Фиксированные однострочные шаблоны находок с именованной грамматикой, а не свободный текст: `L<line>: <tag> <what>. <replacement>.` (review), тот же формат с рангом и путём для whole-repo аудита — `<tag> <what to cut>. <replacement>. [path]`, и `<file>:<line>, <what>. ceiling: <..>. upgrade: <..>.` для долга. Каждый отчётный скилл обязан закончиться одной фиксированной итоговой строкой: `net: -<N> lines possible.` / `net: -<N> lines, -<M> deps possible.` / `<N> markers, <M> with no trigger.` — и для пустого результата это не пустой список и не извиняющийся текст, а другая заранее заданная строка: `Lean already. Ship.` / `No ponytail: debt. Clean ledger.`. Формат задаёт не только форму отдельной находки, но и обязательный терминальный элемент ответа на любой объём находок, включая ноль.
2. Именованный «honesty boundary» прямо внутри текста скилла как структурный раздел, не как внешнее правило: `ponytail-gain` явным текстом запрещает себе придумывать цифру экономии для конкретного репозитория («NEVER print a per-repo savings number... there is no real baseline to subtract from in a live repo») и обязан вместо этого указать на единственный скилл, где цифра реально посчитана (`ponytail-debt`, живой grep). Это структурный аналог заботы gennady о фабрикованных вердиктах/DONE — здесь она закодирована как часть самого текста промпта, а не только как внешний аудит после факта.
3. Раздел «Boundaries» — повторяющийся именованный блок в конце всех шести файлов, всегда отвечающий на три одних и те же вопроса в одном порядке: что явно вне скоупа и куда это направить (а не тихо поглотить), меняет ли скилл что-то (persist / one-shot / ничего не меняет), и точная фраза деактивации — единообразно `"stop <skill-name>"` или `"normal mode"` во всех шести файлах. Это общий для всего проекта message-контракт, обеспеченный повторением одной и той же формы раздела в каждом файле, а не общей библиотекой кода.
4. Правило формы вывода прямо в основном скилле: «Code first. Then at most three short lines: what was skipped, when to add it… Pattern: `[code] → skipped: [X], add when [Y].`» — с тремя проработанными примерами одной и той же задачи под разные уровни интенсивности (lite/full/ultra), то есть шаблон не описан абстрактно, а показан целиком три раза подряд на одном кейсе.
5. Прогресс/scoreboard как буквальный ASCII-рендер с инструкцией «длина полосы кодирует диапазон, подпись несёт точную цифру» — текстовый аналог progress bar, работающий в любом хосте с моноширинным выводом, независимо от наличия графики.
6. Малошумный персистентный индикатор состояния: statusline-хук печатает `[PONYTAIL]` (зелёным) или `[PONYTAIL:ULTRA]` (янтарным для повышенной интенсивности); в коде явно прокомментировано, что цвет — избыточная подсказка вдобавок к тексту, а не единственный сигнал, то есть состояние читается и без цвета.

**Размер, структура, ленивость промптов.**

- Эагерное ядро (`AGENTS.md` и все хост-копии): 2493–2620 байт — грубая оценка ≈600–650 токенов, не измерено токенизатором.
- Основной ленивый скилл (`skills/ponytail/SKILL.md`): 6637 байт — грубая оценка ≈1600–1800 токенов, всё ещё внутри потолка ≈5000 токенов, названного в спецификации Agent Skills в прошлом ресёрче gennady.
- Пять компактных отчётных скиллов (`review`/`audit`/`debt`/`gain`/`help`): 1652–2796 байт каждый (грубая оценка ≈400–700 токенов) — маленькие, одноцелевые, каждый явно во фронтматтере или тексте помечает себя persist/one-shot.
- Фильтрация по режиму происходит не силой убеждения модели, а механически на этапе инъекции: `hooks/ponytail-instructions.js` перед тем, как передать текст модели, регулярным выражением вырезает строки таблицы интенсивности и примеры, не совпадающие с активным режимом (`filterSkillBodyForMode`), оставляя обычные правила без изменений. То есть ленивость применена к самому инжектируемому тексту хостом до модели, а не оставлена на решение модели «эту секцию можно пропустить» — иная ось лени, чем пошаговая (по фазам процесса), которую разбирал `2026-08-22-lazy-directive-loading.research.md`: здесь лениво то, что относится к другому фасету (уровню интенсивности), а не к другому шагу процесса.

**Инструменты, гейты, тестирование промптов (пункт г).**

- `benchmarks/` — полноценный eval-харнесс с метриками по ролям: `loc.js` — чистое измерение (всегда «проходит», просто считает строки), `correctness.js` — гейт, который *обязан* провалиться, если код не работает (и явно проверяется, что гейт умеет ловить сломанный однострочник, а не только хвалить короткий). У каждого испытания есть флаг `--selftest`, который до единого вызова модели проверяет, что заранее заданные «good»- и «bad»-эталоны проходят и падают как ожидается — то есть тестируется сама измерительная линейка, прежде чем тратить вызовы модели на измерение промпта.
- Задокументированный отрицательный результат как полноправный артефакт, не потерянная попытка: ресёрч робастности 2026-06-16 перепробовал 8 разных правок `SKILL.md`, пытаясь исправить измеренный провал на валидации email конкретно у моделей OpenAI (парсер `email.utils.parseaddr` принимается за валидатор под давлением «сначала stdlib»); все 8 правок дали результат не лучше текущего (одна упала с 96% до 78%), ни одна не была принята — «добавление текста в скилл, который не двигает цифру, — ровно тот cargo cult, для борьбы с которым существует Ponytail». Это прямо переносимая практика: правка промпта — это утверждение, которое нужно измерить против бейзлайна на N прогонах, а не самоочевидное благо, потому что текст «звучит аккуратнее».
- Контролируемый A/B именно на формулировке одной инструкции, не только скилл-против-бейзлайна целиком: ресёрч 2026-06-22 сравнил абстрактную фразу «trace the flow end to end» и операционную фразу «grep every caller of the function you touch» на одной и той же задаче на одной модели — абстрактная формулировка держится на 0/3, операционная — на 6/6. Разделены метрика корректности и метрика «качества» (починен ли расшаренный путь, не названный в тикете) — они специально не смешаны в одну цифру.
- Явная отчётность о потолке возможностей модели, а не маскировка его как дефекта скилла: тот же ресёрч прямо пишет, что слабые модели (Haiku на многошаговой инструкции, локальная Llama 3.2 на лестнице решений) не выполняют исправление надёжно независимо от формулировки, и называет это потолком модели, а не браком промпта — разграничение, которое стоит явно проговаривать и у gennady при оценке, держится ли сжатая/ленивая директива на всём диапазоне целевых моделей/агентов.
- Прозрачность при инвалидации собственного замера: файл `benchmarks/results/2026-06-17-agentic-safety.md` не удалён после того, как авторы обнаружили артефакт измерения (хук ponytail неожиданно срабатывал и на «безскилльном» плече), а оставлен с баннером `SUPERSEDED` в первой строке, ссылкой на исправленный документ и явным «do not cite the LOC numbers below» — при этом единственная выжившая находка того прогона (голый «one-liner»-промпт роняет гарантию безопасности) прямо помечена как переподтверждённая в новом прогоне. Структурно близко к тому, что gennady хочет от Decision Log — не переписывать историю, а метить, что из старого решения всё ещё в силе, а что отозвано, и почему.

## Decision

2026-08-22, решения оператора по итогам обсуждения:

- ПРИНЯТО: терминальная строка отчёта на любой объём находок, включая каноничную строку нулевого результата (вместо пустого списка или извиняющегося текста), — в отчётные контракты gennady (аудит, ревью, статус).
- ПРИНЯТО: «honesty boundary» как раздел самозапрета внутри отчётных директив — не изобретать цифру/вердикт, который сам не считал, с указанием, где эта цифра считается.
- DEFERRED_DECISION: механическая фильтрация пакетов по фасету/режиму директивы (ось ленивости, ортогональная шагам, по образцу filterSkillBodyForMode) — идея признана правильной, отложена до фазы раскатки ленивых скелетов; вернуться после пилота двух режимов сборки.
- DEFERRED_DECISION: eval-харнесс с --selftest и обязательным A/B (N прогонов) перед принятием правок текста директив — идея признана правильной, отложена как отдельный проект; вернуться, когда правки директив станут измеримыми по частоте/цене.
- Практика SUPERSEDED-баннера вместо удаления — уже покрыта нашим Decision Log; отдельной нормы не заводим.

## Consequences

Заполняется вместе с Decision. Независимо от выбора, любое из этих направлений задевает разные части gennady: message-layout-шаблоны — контракты общения с оператором (`ai/kit/contract/**`, `AX_OPERATOR_DIALOGUE_STYLE`); механическая фильтрация по фасету — генератор директив из партиалов (`ai/kit/templates/sdd-v2/*.directive.hbs`) и, возможно, `sdd-extract`, если фасетная лень должна жить там же, где секционная; eval-харнесс для правок текста директивы — новая инфраструктура, которой пока нет (`sdd-critic` проверяет артефакты SDD, а не эффект правки текста самой директивы на поведение агента); Boundaries/Honesty-раздел внутри директивы — потенциальное расширение контракта `skill-contract.spec.md`, который сейчас описывает структуру `SKILL.md`, но не обязывает к именованному разделу такого рода.

Открытый риск независимо от решения: ponytail — поведенческий скилл на одну задачу («будь ленивым разработчиком»), а не пошаговая директива процесса на 10–16k токенов вроде `execute.directive.xml`; перенос его message-layout-паттернов на многошаговый процесс (где отчётность выдаётся не один раз в конце, а на каждом шаге) не проверен здесь и может требовать адаптации, а не копирования формата один в один.
