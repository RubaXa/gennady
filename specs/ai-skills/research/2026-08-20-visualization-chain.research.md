# Research: визуализация цепочки от требований до композиции абстракций

## Status

<!--/SECTION:STATUS-->

<!--SECTION:PROBLEM-->

## Problem

Диаграммы в спецификациях не дают проследить, как работает фича: они показывают статическую композицию («кто из чего состоит»), но не поток данных, не цепочку вызовов и не то, что именно добавляется в композицию абстракций при доработке модуля. Читатель не может по спеке понять, как данные текут и какие абстракции сцепляются между собой; вводимые агентом сущности появляются без картины их композиционного размещения.

Требуемая цепочка: требования (функциональные и нефункциональные) → use cases → поток данных → цепочки вызовов API → вводимые абстракции и их композиция → дельта при доработке. Ограничение: читаться без экспертизы в UML; предпочтение ASCII в чате (дешево и быстро), диаграмма в артефакте — вторична.

## Options

### Текущее состояние флоу (инвентарь, факты с цитатами)

**Что есть.** Словарь диаграмм (`ai/directives/sdd-v2/formats/diagram-vocabulary.xml`, порт из agent-inbox `visual-vocabulary`) с аксиомами: реляционный смысл → картинка; ≤7 узлов и один вопрос на диаграмму; ASCII в чате раньше mermaid в спеке; пол «≥1 диаграмма в Overview» для scope/module/infra/interface. Лесенка модуля предписывает пять рунгов (Overview, Module Map, инвентарь сущностей как ER, жизненный цикл сущности, граф контрактов Port/Adapter/Service), лесенка scope — Overview + High-Level Architecture, плюс Use Cases для product.

**Что проверяется механически.** Только один рунг: `SDD_NO_DIAGRAM_BLOCK` / `SDD_DIAGRAM_BLOCK_EMPTY` для секции OVERVIEW (`shared/sdd/check.ts:1388-1409`), плюс синтаксис любого mermaid-блока (`shared/sdd/mermaid-check.ts`). Остальные рунги держатся дисциплиной агента в чате.

**Что нарисовано в живом корпусе.** 8 mermaid-блоков + 1 ASCII в gennady-todomvc: 7 из 8 — граф зависимостей или композиции (`flowchart` / `graph`), 1 — use-case (актор → сценарии). По всему репозиторию gennady: 34 файла с mermaid, все блоки — `graph TD` (28) или `flowchart LR` (8). **Ни одной** диаграммы последовательности, состояний или сущностей-связей ни в одном из двух репозиториев, хотя словарь их предлагает. Ни одна из пяти живых Overview-диаграмм не несёт предписанной подписи одной строкой.

**Пробелы относительно цели** (ранжированы): (1) цепочка вызовов не рисуется нигде — `sequenceDiagram` не входит ни в один обязательный пол; композиционный граф контрактов показывает только `implements`/`depends on`, не порядок вызовов; (2) проверяется один рунг из пяти — в живом примере диаграмма контрактов осталась ASCII вместо предписанного mermaid, и проверка этого не заметила; (3) трассируемости «требование → use case → диаграмма → абстракция» нет: тег `[<ACR>-REQ-N]` связывает только BDD-сценарий тикета с требованием, диаграмма не имеет собственного якоря и не адресуется; в живом примере номера тикета (`TDM-REQ-N`) даже не совпадают с требованиями спеки (`F1…F10`); (4) порядок обратный цели — Use Cases рисуются до закрытия требований; (5) дельта при доработке чисто текстовая (манифест изменений `✚`/`~`), before/after диаграмма помечена как «на усмотрение, никогда не гейт»; (6) портал не даёт картинки вообще — `renderScopeGraph` печатает плоский текст уровней и рёбер.

### Нотации: что существует и что переносимо

**C4 (Simon Brown).** Уровни Context → Container → Component → Code как zoom-in; нотационно-независим, есть три текстовых DSL (Structurizr DSL, Mermaid C4 с пятью подтипами, C4-PlantUML). Порог низкий: две фигуры и подписанные стрелки. Практика (вторичные источники, не сама спецификация) рекомендует не поддерживать уровень Code руками — он устаревает за спринт. Покрывает: границы системы, композицию крупных блоков, частично динамику (`C4Dynamic`).

**Data Flow Diagram (Yourdon/DeMarco, Gane-Sarson).** Четыре элемента: внешняя сущность, процесс, хранилище, поток. Уровни 0/1+ как раскрытие процесса. Принципиально: в DFD нет управляющей логики — ни условий, ни циклов, только «что куда течёт». Порог низкий, ASCII-выразимость высокая. Единственная нотация, прямо закрывающая звено «поток данных».

**Sequence diagram.** Хронология вызовов между участниками — прямая проекция на «цепочку вызовов API». Текстовый DSL по сути и есть ASCII (`Client->>API: POST /orders`). Порог низкий: стрелки читаются интуитивно. Риск читаемости — не нотация, а перегрузка (длинные подписи, много участников).

**Statechart (Harel).** Состояния и переходы с иерархией и параллелизмом; решает взрыв состояний плоского автомата. Нужен, когда у сущности есть явный жизненный цикл; для линейного процесса избыточен. ASCII хорош для плоского автомата, для вложенности выигрывает mermaid.

**ERD.** Сущности, атрибуты, кардинальность связей. Единственная нотация в подборке, где символика (crow's foot `||--o{`) требует легенды — порог средний.

**Граф зависимостей и композиции.** Узел = модуль/порт, стрелка = зависимость или реализация. Для портов и адаптеров минимум: домен в центре, порт на границе, адаптер снаружи, правило «стрелка зависимости направлена внутрь». ASCII хорош до 15–20 узлов, дальше нужен автолейаут.

**Event modeling (Dymitruk) и event storming (Brandolini).** Дорожки по ролям, время слева-направо, ячейки «команда → событие → состояние/read model». Одна схема закрывает use case, поток данных и вызовы одновременно. Находка ресёрча: Mermaid включает тип `Event Modeling` в актуальный список (страница синтаксиса не найдена — перед использованием нужна проверка). Event storming в исходном виде — воркшоп со стикерами, для текста плохо переносим.

**Прочее из практики.** Swimlane (роли как дорожки, есть текстовый DSL swimlanes.io), block/deployment diagram (`block-beta`, `C4Deployment`, `architecture-beta` в mermaid), call graph (генерируется, стандартный выход — Graphviz DOT), реестр решений ADR с цветокодом статусов, Wardley map (стратегический инструмент, для механики фичи не применим), **sequence-как-таблица** (колонки шаг/компонент/действие/данные — доступнее диаграммы для нетехнического читателя), use case как текстовая таблица (актор/цель/триггер/шаги/пред- и постусловия) вместо UML-овалов.

**Инструменты.** Mermaid — 30 типов диаграмм в актуальной документации, рендерится нативно в чатах и артефактах, автолейаут dagre. PlantUML, D2, Graphviz, Structurizr требуют внешний рендерер — дороже по инфраструктуре. Чистый ASCII (box-drawing или `-->`) рендерится буквально везде и стоит дешевле всего.

**Читаемость.** UML критикуют за избыточность (14 типов, «gratuitously large and complex») — отсюда порог входа. Практика diagrams-as-code: диаграмма живёт в git, ревьюится в PR. Количественная опора одна: правило 7±2 Миллера (современные пересчёты Cowan снижают предел активно обрабатываемых элементов до ~4) → практический вывод ≤7–9 узлов на схему с группировкой деталей за подграфы, что совпадает с механикой уровней C4 и DFD. Контролируемых экспериментов «какая нотация понятна без обучения» не найдено — только практические статьи.

### Четыре набора нотаций, закрывающих цепочку

**Набор 1 — Mermaid-first.** Требования таблицей; use cases и поток данных — `flowchart` с подграфами; вызовы — `sequenceDiagram`; композиция и дельта — `flowchart`/`C4Component` с пометкой новых узлов. Один синтаксис стрелок и блоков переиспользуется во всех типах: читателю учить один раз. Стоимость порядка 40–70 токенов на схему.

**Набор 2 — ASCII-only.** Требования и use cases списком/таблицей; поток данных — box-drawing DFD; вызовы — нумерованный список шагов; композиция — ASCII-дерево зависимостей с пометкой `NEW`. Нулевые зависимости, 30–60 токенов; плохо масштабируется свыше 8 узлов и на нелинейных вызовах.

**Набор 3 — Event modeling как сквозная нотация.** Одна дорожечная таблица закрывает use case, поток данных и вызовы сразу (дорожки — роли, столбцы — время, ячейки — команда/событие/состояние). Требуется ещё таблица требований и граф композиции — итого три нотации. 50–80 токенов.

**Набор 4 — Delta-focused (для доработки).** Минимум для аудита изменений: граф зависимостей с маркерами добавленного плюс диаграмма последовательности с новыми шагами; неизменная часть системы не перерисовывается. 40–60 токенов на пару.

## Decision

Решение не принято на 2026-08-20 — документ собран как база для выбора. Выводы, которые считаю опорными (вывод агента, не утверждение источников):

1. Звено «цепочка вызовов API» закрывается только диаграммой последовательности либо её табличным эквивалентом; в текущем флоу оба отсутствуют как обязательство, и в корпусе из 34 файлов нет ни одного примера — это главный пробел.
2. Звено «поток данных» закрывается DFD (четыре элемента, порог низкий) — сейчас во флоу нет ни требования, ни примера.
3. Композиция абстракций уже покрыта графом контрактов, но не проверяется механически и в живом примере осталась в ASCII вместо предписанного формата — пол без проверки расползается.
4. Дельта при доработке дешевле всего показывается тем же графом с маркером нового узла плюс диаграммой последовательности с новыми шагами (набор 4) — перерисовывать неизменное не нужно.
5. Ограничение ≤7–9 узлов на схему и группировка деталей за уровни — единственная количественная опора; она же оправдывает уровни C4 и уровни DFD как способ не перегружать читателя.
6. Трассируемость требует, чтобы диаграмма была адресуемым узлом (свой якорь или подпись с идентификаторами требований), иначе связь «требование → диаграмма» остаётся ручной.

## Consequences

Расширение обязательного пола диаграмм увеличивает стоимость каждой спеки: 40–80 токенов на схему плюс раунд согласования в чате. Поэтому пол должен различать типы скоупов (product против инфраструктуры) и масштаб задачи, а не требовать полный набор всегда. Каждый новый обязательный рунг требует механической проверки, иначе он повторит судьбу нынешних четырёх непроверяемых рунгов лесенки модуля.
