# Research: ленивая/поэтапная загрузка инструкций в LLM-агентах

<!--SECTION:STATUS-->

<!--SECTION:PROBLEM-->

## Problem

Директивы SDD v2 — монолитные промпты на 10–16k токенов, собираемые из партиалов (`ai/kit/contract/**/*.xml`, `ai/kit/axiom/**/*.xml`) через Handlebars-шаблоны (`ai/kit/templates/sdd-v2/*.directive.hbs`, например `module.directive.hbs`, `scope.directive.hbs`) и загружаемые агентом целиком на старте как self-contained «мир» — весь процесс, все шаги, все форматы сразу. Точечное чтение уже существует, но только для артефактов-документов: `gennady sdd-extract <file> <SECTION_NAME>` вытаскивает одну секцию тикета/спеки по якорю `<!--SECTION:NAME-->` (`specs/cli/sdd-extract/sdd-extract.spec.md`), а не секцию самой директивы.

Гипотеза оператора: проблема не в итоговом размере, а в том, что всё грузится **сразу и одним куском**, хотя большая часть содержимого директивы релевантна только на одном конкретном шаге процесса. Идеал: 4–8k токенов на входе (скелет + то, что нужно всегда), остальное шаг подгружает сам по мере входа в него — по аналогии с уже существующим механизмом `sdd-extract`, но применённым к самой директиве, а не только к тикету.

Открытые вопросы, на которые должен ответить ресёрч:

1. Как индустрия и Anthropic формально описывают progressive disclosure для агентных инструкций — есть ли нормативные пороги размера.
2. Есть ли документированный опыт JIT-подгрузки шага «по входу» и её подводных камней (забыл подгрузить, устаревшая копия, лишние обороты чтения).
3. Skeleton+details (скелет виден целиком, детали шага — лениво) против полностью ленивого дерева — и можно ли грузить лениво сквозные инварианты (аксиомы), которые должны действовать всё время.
4. Есть ли измеримые данные о качестве: сфокусированный контекст шага против полного мануала целиком.
5. Какие анти-паттерны документированы — когда ленивость ломает агента.

## Options

### Академия

**MemGPT: Towards LLMs as Operating Systems** (Packer, Wooders, Lin, Fang, Patil, Gonzalez; arXiv:2310.08560, 2023). Виртуальное управление контекстом по аналогии с ОС: main context (аналог RAM, ограничен) и external context (аналог диска, неограничен); агент сам вызывает функции переноса данных между уровнями (`archival_memory_search`, `core_memory_append`), interrupt-механизм передаёт ему управление на каждое сообщение пользователя или по таймеру. Первый систематический прецедент «агент сам решает, что подгрузить», а не диспетчер извне.

**Voyager: An Open-Ended Embodied Agent with Large Language Models** (Wang et al., NVIDIA/Caltech/Stanford/UT Austin/UW Madison; arXiv:2305.16291, ICLR 2024). Постоянно растущая библиотека навыков — исполняемый код, который хранится и извлекается по запросу, а не держится в промпте целиком; авторы утверждают, что это ослабляет catastrophic forgetting и делает навыки компонуемыми. Прецедент «навык как отдельно адресуемая единица», а не абзац внутри одного огромного промпта — концептуальный предок SKILL.md.

**Lost in the Middle: How Language Models Use Long Contexts** (Liu, Lin, Hewitt, Paranjape, Bevilacqua, Petroni, Liang; TACL, том 12, стр. 157–173, 2024; ACL Anthology 2024.tacl-1.9). Эмпирика на multi-document QA и key-value retrieval: точность максимальна, когда релевантная информация в начале или конце контекста, и заметно падает, когда она в середине длинного контекста — модели не умеют равномерно использовать длинный контекст. Это теоретическое основание тезиса «меньше, но релевантное, лучше, чем больше, но размытое».

**Diagnosing and Mitigating Context Rot in Long-horizon Search** (Xia, Wang, Huang, Liu; arXiv:2606.29718v2, 2026). Разбирает context rot именно в длинных пошаговых траекториях агента (не в одном большом документе): выделяет затухание влияния ранних шагов, узкое место внимания на длинной истории и накопление ошибок вдоль цепочки шагов, которые модель не может исправить задним числом. Предлагает windowing/суммаризацию и механизмы явного усиления доступа к ранним шагам. Прямое академическое подтверждение, что растягивание одного контекста через много последовательных шагов (как это фактически происходит, когда 10–16k директива прочитана один раз и держится «в фоне» на протяжении всего процесса) деградирует надёжность шаг-за-шагом.

**Agent Skills for Large Language Models: Architecture, Acquisition, Security, and the Path Forward** (Xu, Yan; arXiv:2602.12430v3 [cs.MA], 17 февраля 2026). Академический обзор именно формата SKILL.md: формализует трёхуровневую архитектуру progressive disclosure (метаданные при старте ~50–100 токенов → процедурные инструкции по триггеру → технические ресурсы по требованию) и отдельно поднимает риск, специфичный именно для ленивой загрузки: раз загруженный контент неявно доверяется без runtime-проверки — у 26.1% из 42 447 изученных community-скиллов найдены уязвимости, у скиллов со скриптами риск в 2.12× выше, чем у чисто текстовых. Это анти-паттерн другого рода (безопасность, не корректность), но прямое следствие модели «лениво загруженное = автоматически доверенное».

**Побочная находка, не относится к теме напрямую (флаг для читателя):** _Skeleton-of-Thought: Prompting LLMs for Efficient Parallel Generation_ (arXiv:2307.15337) — по названию совпадает со словом «skeleton» из гипотезы оператора, но решает не подгрузку инструкций, а латентность генерации (модель сначала выдаёт скелет ответа, потом параллельно раскрывает пункты). Смысл термина «skeleton» здесь другой; не подтверждает и не опровергает гипотезу skeleton+details для директив.

### Лидеры рынка

**Anthropic — Agent Skills, официальный блог «Equipping agents for the real world with Agent Skills»** (anthropic.com/engineering, 16 октября 2025). Трёхуровневый progressive disclosure: (1) метаданные `name`/`description` всех скиллов предзагружены в системный промпт при старте; (2) полное тело SKILL.md подгружается, когда Claude решает, что скилл релевантен; (3) файлы уровня 3+ (`references/`, `scripts/`, `assets/`) Claude сам открывает по необходимости. Из-за этого «объём контекста, который можно упаковать в скилл, практически неограничен» — цена не в объёме файла на диске, а в том, что реально прочитано.

**Anthropic — «Effective context engineering for AI agents»** (anthropic.com/engineering, 29 сентября 2025; авторы — Applied AI team: Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield). Даёт термин context rot как эмпирический факт («по мере роста токенов в контексте точность вспоминания информации из него падает») и называет четыре рычага одновременно: just-in-time retrieval (держать лёгкие ссылки — пути, запросы — и подгружать по инструменту, а не тащить данные заранее), compaction (сжатие истории с сохранением решений при потере шума), структурированные заметки вне окна контекста, суб-агентная изоляция. Явно формулирует trade-off JIT против предзагрузки: runtime-исследование медленнее и требует «продуманной инженерии», чтобы агент не тратил контекст на тупиковые попытки; гибрид (часть данных заранее, часть исследуется сам) на практике часто лучше любой крайности. Даёт формулу «правильной высоты» системного промпта — между жёстко закодированной хрупкой логикой и расплывчатыми инструкциями, предполагающими общий контекст, которого у модели нет.

**Anthropic — «Advanced Tool Use» / Tool Search Tool** (anthropic.com/engineering, 24 ноября 2025). Единственная найденная **измеренная** цифра качества именно от смены схемы загрузки на ту же задачу: на внутренних MCP-эвалах Anthropic точность Opus 4 выросла с 49% до 74%, Opus 4.5 — с 79.5% до 88.1% при включённом Tool Search (`defer_loading: true` на большинстве тулов + отдельный тул-поиск, который Claude вызывает сам). Токены на туже библиотеку тулов упали на 85% (≈77k → ≈8.7k). Явная рекомендация: 3–5 самых используемых тулов держать всегда загруженными, остальное — лениво. Это прямое подтверждение формы «маленькое эагерное ядро + длинный ленивый хвост», а не «всё лениво» или «всё сразу».

**Claude Code — sub-agents** (code.claude.com/docs/en/sub-agents). Готовый ответ на вопрос «можно ли лениво грузить инварианты»: каждый не-fork саб-агент стартует с изолированным контекстом, куда безусловно попадают файлы CLAUDE.md со всех уровней иерархии (кроме двух специальных встроенных агентов Explore/Plan, которые их пропускают ради скорости) — но НЕ попадают история разговора, уже использованные скиллы, полный системный промпт родителя. То есть в реальной работающей системе сквозные правила (аналог аксиом SDD) закладываются эагерно в любую изолированную единицу работы, а всё остальное — по обстоятельствам этой единицы.

**Manus — «Context Engineering for AI Agents: Lessons from Building Manus»** (Yichao "Peak" Ji, manus.im/blog, 2025). Аргумент против «полностью ленивого дерева», который меняет состав контекста на ходу: KV-cache стабильность требует, чтобы контекст был append-only — динамическое добавление/удаление определений тулов или инструкций посреди задачи (а) инвалидирует кэш от точки изменения и дальше и (б) путает модель, когда более ранние шаги ссылаются на определения, которых больше нет в контексте, что без constrained decoding часто приводит к нарушению схемы вызова. Решение Manus — маскировать доступность через логиты при декодировании, а не физически убирать определения. Второй тезис — держать файловую систему как внешнюю память (неограниченная, персистентная, читается агентом напрямую) и делать любое сжатие контекста restorable (сохранять пути/URL, даже выбрасывая содержимое). Третий — не прятать от модели её же ошибки: «оставлять неверные повороты в контексте» помогает агенту неявно скорректировать поведение и не повторять их.

**Cognition (Devin)**. Формулирует context engineering как «фактически задачу #1 инженера, строящего агентов» — управление полным жизненным циклом токена: что положить в контекст, что убрать, когда сжать растущую историю, какие документы подгружать just-in-time, как маршрутизировать подзадачи в изолированные саб-агенты, что вынести в персистентные заметки за пределы окна. Подтверждает те же два доминирующих рычага, что у Anthropic (JIT + суб-агентная изоляция), с добавлением явного упоминания, что длинные горизонты (сотни ходов) ломаются иначе, чем плохо написанные инструкции — это отдельный класс отказа, не решаемый просто более качественным текстом промпта.

**OpenAI — «A practical guide to building agents»** (openai.com/business/guides-and-resources). Более консервативная позиция: инструкции агента должны быть явными и разбиты на дискретные шаги заранее, а не архитектурно ленивыми; управление контекстом — оборонительное (суммаризировать последние N сообщений перед роутингом, передавать в следующего агента только то, что ему нужно), а не построение дерева lazy-load. Масштабирование к multi-agent рекомендуется только когда единый, хорошо ограниченный промпт перестаёт быть поддерживаемым. Рыночный контрпример: не все ведущие игроки формулируют решение как «одна директива с ленивыми секциями» — часть индустрии решает тот же бюджет контекста декомпозицией на много маленьких эагерных промптов с передачей хода (что ближе к уже существующей в gennady модели «один воркер на фазу» в `sdd-execute`, чем к ленивому дереву внутри одной директивы).

**Cursor — `.cursor/rules`** (cursor.com/docs/rules; практика описана в независимых разборах dev.to/DataCamp/techsy). Прямой IDE-агентный аналог «аксиомы против содержимого шага»: правило может быть always-apply (в каждом промпте), glob-scoped (только при работе с подходящими файлами), agent-requested (агент сам решает по описанию) или manual (только по явному упоминанию). Задокументированный именно-числовой анти-паттерн: держать alwaysApply у 10+ правил «сжигает» контекст ещё до начала разговора, и модель «одновременно удовлетворяет всем и выдаёт усреднённый результат, частично нарушающий большинство из них» — практическая рекомендация ограничивать always-apply 1–2 правилами. Это довод в пользу того, что список сквозных инвариантов должен быть маленьким по построению, а не просто «помечен как важный».

### Готовые инструменты

**agentskills.io — открытая спецификация Agent Skills.** Формат вышел из Anthropic в декабре 2025 и по данным вторичных обзоров (daily.dev, firecrawl.dev — не проверено на первоисточнике каждого вендора) был подхвачен OpenAI, Google, GitHub Copilot и Cursor в течение недель. Спецификация даёт точные числа: метаданные (`name`+`description`) ≈100 токенов на скилл, загружаются при старте для всех скиллов; тело SKILL.md — рекомендованный потолок **менее 5000 токенов** при активации; практический потолок — **500 строк** тела файла; ссылки на файлы уровня 3 — «на один уровень от SKILL.md», без глубоких цепочек, потому что при вложенных ссылках агент может частично прочитать файл через `head -100` и незаметно потерять хвост. Есть валидатор `skills-ref validate ./my-skill`.

**Anthropic Platform Docs — Skill authoring best practices** (platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices). Прямая проверка чек-листом: SKILL.md < 500 строк; «concise is key» с явным расчётом токенов на примерах («хорошо» ≈50 токенов против «плохо» ≈150 на одну и ту же инструкцию); шкала degrees of freedom (высокая/средняя/низкая свобода формулировки в зависимости от хрупкости операции); правило «одна ступень вложенности ссылок»; таблица содержания обязательна для референс-файлов длиннее 100 строк — тоже мера против частичного чтения. Явно формулирует источник провала: агент видит своё же `description`, решает, что процедура уже понятна, и не читает тело SKILL.md вовсе — то есть богатое описание может _подавить_ чтение подробностей, а не просвещение к нему подвести.

**Anthropic Tool Search Tool (API-примитив)**. Готовый механизм: тул размечается `defer_loading: true`, определение не попадает в контекст, пока Claude не найдёт его через отдельный тул поиска. Цифры — см. выше в «Лидеры рынка»; это тот же паттерн, но упакованный как готовый параметр API, а не как архитектурное решение, которое нужно строить самому.

**MCP progressive disclosure — сторонние реализации.** «Meta-tool pattern» (Synaptic Labs, blog.synapticlabs.ai): вместо регистрации 33 тулов регистрируются два — один с полным индексом возможностей в описании, второй — универсальный исполнитель; экономия отчётов о падении токенов до 98.7% (150k → 2k) в кейсе Anthropic code-execution-with-MCP. Filesystem-подобная иерархия тулов (agentic-patterns.com/patterns/progressive-tool-discovery): агент листает директории тулов и подгружает полную схему только для выбранного; масштабируется до 1000+ тулов, снижает начальный контекст на 70–90% по практическим данным, но платит явную цену — дополнительные обороты на поиск, риск, что агент пропустит шаг поиска, и накопление устаревших схем в кэше, если организация каталога плохая. Клиентская реализация Hermes Agent даёт 85% сокращения токенов на определения тулов при оверхеде ≈22K токенов/ход на связке из 5 серверов/34 тулов (developersdigest.tech приводит менее оптимистичный пример: у одного MCP CLI лениво загрузка сэкономила только 47K → 40K токенов — то есть выигрыш пропорционален размеру каталога, а не гарантирован сам по себе).

**LangGraph — subagents/subgraphs** (docs.langchain.com/oss/python/langchain/multi-agent/subagents). Готовый фреймворковый примитив изоляции контекста: саб-агент получает полностью свежий контекст на каждый вызов. Задокументированный trade-off прямо противоположен «ленивой подгрузке по ходу дела»: раз саб-агент не видит родительский контекст вообще, супервизор обязан **заранее упаковать всё нужное** в сообщение делегирования — внутри саб-агента дозагрузить что-то из родителя посреди работы нельзя. Изоляция куплена ценой полной предварительной упаковки, а не ленью.

**CrewAI и OpenAI Agents SDK.** Оба не имеют встроенного примитива progressive disclosure на уровне промпта — агент описывается плоской строкой инструкций + тулы + handoffs; масштаб контекста решается не ленивой подгрузкой секций одного промпта, а декомпозицией на несколько маленьких промптов с передачей хода (handoff) между агентами. Другой инструмент для той же цели: не «умный ленивый файл», а «много маленьких файлов».

### Синтез относительно директив SDD (выводы агента, не решение оператора)

1. Числа сходятся на одном порядке величины, но не на том, что дал оператор: индустриальный потолок для «то, что грузится при триггере» — **< 5000 токенов на тело** (agentskills.io) плюс ~100 токенов метаданных на старте; цель оператора 4–8k на входе — того же порядка, возможно чуть выше верхней границы рынка для одного скилла, но директива SDD — не skill-файл, а весь процесс, так что скелет процесса шире одного skill-body.
2. Ни один источник не поддерживает «полностью ленивое дерево» без стабильного эагерного ядра. Anthropic Tool Search — 3–5 тулов всегда, остальное лениво. Cursor — 1–2 always-apply правила, остальное scoped. Claude Code subagents — CLAUDE.md всегда, всё остальное по обстоятельствам. Manus — контекст append-only, ядро не трогается, чтобы не сломать KV-cache. Общая форма — «маленькое эагерное ядро + длинный ленивый хвост», а не 50/50 и не «всё по требованию».
3. Аксиомы (аналог `ai/kit/axiom/**`) по прямому прецеденту (CLAUDE.md → каждый саб-агент) не должны грузиться лениво: инвариант, который не гарантированно попадёт в контекст каждого шага, перестаёт быть инвариантом. Одновременно Cursor-анти-паттерн предупреждает про противоположную ошибку: если «всегда загружаемых» правил становится много (10+), модель начинает нарушать все понемногу — значит, набор аксиом должен быть маленьким по построению, не просто помечен высоким приоритетом.
4. Единственная прямая измеренная цифра качества именно от смены схемы загрузки (не просто токено-экономии) — Anthropic Tool Search: точность на MCP-эвалах 49%→74% (Opus 4) и 79.5%→88.1% (Opus 4.5) при переходе от «всё сразу» к «эагерное ядро + ленивый поиск». Она про выбор тула, не про пошаговую директиву процесса — прямого переноса на директивы SDD в найденных источниках нет, это была бы экстраполяция.
5. Skeleton+details ближе к тому, что фактически описывают Agent Skills (SKILL.md как таблица содержания, тело шага — ссылка на один уровень вглубь) и к тому, что уже устроено в репозитории (партиалы + `sdd-extract` для точечного чтения секций тикета). Полностью ленивое дерево с глубокими цепочками ссылок прямо не рекомендуется официальной документацией Anthropic (частичное чтение через `head -100`, потеря хвоста файла) — глубина вложенности, а не сам факт лени, названа источником потерь.
6. Задокументированный «забыл подгрузить» — не гипотетический анти-паттерн, а наблюдаемый: описание skill может быть настолько информативным, что агент решает, будто процедура уже понятна, и не читает тело файла с реальной инструкцией вообще (wordman.dev; smartscope.blog — расширенный список из версии инструмента, отсутствующего файла, неверных ключевых слов в описании, конфликта нескольких похожих skill).
7. «Лишние обороты на чтение» — не риск, а измеренная и признанная цена ленивой схемы везде, где она встречается (agentic-patterns.com прямо перечисляет discovery overhead и «агент может пропустить шаг поиска» как компромисс, а не сбой); экономия токенов пропорциональна размеру того, что откладывается — на маленьком наборе (developersdigest.tech: 47K→40K) выигрыш скромный, оправдан только при достаточно большом объёме откладываемого.

## Decision

2026-08-22, решения оператора по итогам обсуждения:

- ПРИНЯТО: директива = скелет (Mission + HaltConditions + сквозные аксиомы + список шагов + контракт стиля вывода) + пакеты шагов; пакет шага выдаёт CLI-инструмент (прецедент sdd-task --phase), а не самостоятельное чтение агентом — закрывает задокументированный антипаттерн «забыл подгрузить».
- ПРИНЯТО: сквозные аксиомы-инварианты остаются эагерными (лениво их не грузит никто — прецедент CLAUDE.md в каждом сабагенте).
- ПРИНЯТО: бюджеты под CI-гейтом — скелет ≤6k токенов (цель), ≤8k жёсткий потолок; официальное правило «вывод инструмента не обрезается» — размер каждого пакета шага тоже под механическим гейтом; связка скелет↔пакеты↔вывод покрывается guard-тестами.
- ПРИНЯТО: перестраиваются все три тяжеловеса (audit, scaffold, phase-execution-protocol) сразу, в ДВУХ режимах сборки (монолит | ленивый скелет) с переключением флагом при сборке — сравнение только на полных прогонах флоу; первая сборка — ленивый режим, сделанный образцово.
- ПРИНЯТО: работа оформляется спекой через собственный SDD-флоу (dogfooding авторского контура).
- DEFERRED_DECISION: точный состав режимов/комбинаций флагов сборки — спроектировать в спеке, обсудить отдельно.

## Consequences

Независимо от того, какой вариант выберет оператор, миграция монолитных директив на любую ленивую схему платит минимум тремя ценами, которые видны во всех найденных источниках одинаково: (1) дополнительные обороты на чтение секции при входе в шаг — не устраняются, а признаются рынком неизбежным компромиссом; (2) риск «забыл подгрузить» или «описание подменило реальное чтение», требующий отдельной проверки (eval-набор до документации, по рецепту Anthropic, а не вера в дисциплину агента); (3) необходимость держать эагерное ядро маленьким по построению — расширение списка «всегда грузим» без пересмотра эквивалентно частичному откату к монолиту и рискует эффектом Cursor (много always-apply правил → среднее нарушение всех). Любое решение также требует явно зафиксировать, какая часть директивы — сквозной инвариант, а какая — материал шага, потому что без этого разделения механизм точечного чтения (`sdd-extract`-подобный) рискует унести аксиому в лениво читаемую секцию.
