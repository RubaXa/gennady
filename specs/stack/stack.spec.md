# stack: Scope Specification

## scope-type

library

## 1. Vision & Primary Goal

Плагинная система стеков: **слой per-stack и per-repo знаний для команд «Геннадия»**. Стек (node, golang, дальше — любой) — деталь реализации за общим интерфейсом `StackPlugin`; различия между репозиториями выражаются не разными командами, а конфигом ([config.spec.md](../config/config.spec.md)), который переопределяет и расширяет встроенные плагины.

Проблема: сегодня каждая команда, которая шеллится наружу, несёт захардкоженные знания об npm (`verify.sh` → `classify-scripts` → `npm run …`; `testcov` → vitest/jest; `resolve-verify-commands` → `package.json`). Каждый новый стек порождал бы новые команды (`go-verify`, `rust-verify`, …) — анти-паттерн «в разных репах разные команды Геннадия».

Вместо этого:

- **Единые глаголы.** Команды «Геннадия» не меняются от стека к стеку; плагин выбирается авто-детекцией или конфигом.
- **Возможности (capabilities): одна обязательная, остальные опциональные.** `StackPlugin` — набор фасетов; каждый фасет обслуживает одну команду CLI. Обязателен только `verify` — плагин, реализующий один `verify`, полноценен и usage-ready (это единственный фасет, от которого зависит цикл SDD execute→verify). Опциональные фасеты (`fix`, `testcov`, `dbc-lint`, `directives`) могут быть не реализованы, и их поддержка может различаться между плагинами. Классификация — §4.3.
- **Единый контракт verify.** RUN-ALL (все гейты выполняются, отказы накапливаются), SUPPRESS-ON-SUCCESS (успешные гейты молчат), коды выхода `0/1/4/5` — не зависят от стека.
- **Гейты никогда не мутируют** рабочее дерево. Мутирующие операции полезны (prettier --write, autofix, codegen) — но это **отдельная сущность** `Fixer` и отдельный глагол `gennady fix` (§4.4), никогда не смешиваемые с верификацией.
- **FAIL ≠ ENV_FAIL.** Отказ инструмента (паника линтера, недоступный module proxy) — не finding по коду; отчёт явно запрещает агенту «чинить» код в ответ.
- **Конфиг — точка расширения.** Репозиторий описывает свою инфраструктуру один раз в `gennady.yaml`; личные надстройки — deep-merge из `.gennadyrc` (config.spec §1.2).

Вне скоупа v1 (TODO, §12): внешние плагины для проприетарных стеков. Идея зафиксирована; дизайн отложен — в том числе вопрос формата подключения (ссылка — плохой id; вероятная форма: `use` как map `id → source`).

## 2. Definitions

_Каждый термин ниже используется всеми спеками scope. Термины «Геннадия», не определённые здесь, ссылаются на свои спеки._

| Term                    | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stack**               | Технологический стек репозитория, определяемый маркер-файлом в корне: `node` (`package.json`), `golang` (`go.mod`); `anystack` — заглушка без маркера, активна в любом репозитории (plugins/anystack). Репозиторий может принадлежать нескольким стекам одновременно.                                                                                                                                                                                                                                                                                                                                                                                                |
| **StackPlugin**         | Реализация интерфейса §4 для одного стека: детекция + фасет `verify` (обязательный) + опциональные фасеты. Встроенные: `anystack`, `golang`, `node`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Capability**          | Фасет плагина, обслуживающий одну команду CLI. Обязательный: `verify`. Опциональные: `fix`, `testcov`, `dbc-lint`, `directives` (§4.3); их поддержка может различаться между плагинами.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Gate**                | Одна верификационная команда с бинарным вердиктом: `argv` + `cwd` + `env` + `timeout` + контракт вывода. Гейт **наблюдает** — он не изменяет закоммиченное состояние и не оставляет новых не-ignored файлов; нарушение обнаруживается по `git status` заведомо чистого дерева и откатывается (D-STACK-017). Gitignored-пути — легальная рабочая зона (кэши сборки). Исполняется без shell. Квалифицированное имя: `<stack>:<id>` (например `golang:build`).                                                                                                                                                                                                          |
| **Clean-tree guard**    | Предусловие и механизм отката verify (D-STACK-017): прогон стартует только на чистом дереве (`git status --porcelain` пуст — tracked и untracked; ignored не учитываются), иначе `DIRTY_TREE`, exit 4, ни один гейт не исполняется. Гейты исполняются **в реальном дереве**; непустой status после гейта — точный список его мутаций, откат — `git reset --hard` + `git clean -fd` (без `-x`: ignored переживают) — доказуемо точный, потому что состояние до прогона и есть HEAD. Один lock-файл на репозиторий защищает от параллельных прогонов и служит крэш-маркером. Репозиторий без git/HEAD → гейты исполняются без guard'а + диагностика `UNSANDBOXED_RUN`. |
| **Drift-гейт**          | Гейт с `driftMeansFailure: true` («drift-гейт»): мутация **ожидаема** — вердикт = exit-код команды **и** порезультатный `git status` дерева: непустой → FAIL со списком файлов («drift»). После грязного статуса дерево сбрасывается к HEAD перед следующим гейтом.                                                                                                                                                                                                                                                                                                                                                                                                  |
| **VIOLATION**           | Гейт **без** `driftMeansFailure: true` оставил дерево грязным — нарушение контракта «гейт наблюдает» (D-STACK-005). Отдельный статус: не FAIL по коду и не ENV_FAIL; отчёт называет гейт и файлы и предлагает перенести мутацию в `fixer` гейта (исполняется `gennady fix`, §4.4). Дерево сбрасывается к HEAD перед следующим гейтом.                                                                                                                                                                                                                                                                                                                                |
| **Fixer**               | Мутирующая операция, **привязанная к своему гейту** полем `fixer` (§4.4): её мутация ожидаема и не откатывается. Исполняется только явным `gennady fix`; в verify-план не входит никогда.                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Gate plan**           | Упорядоченный список гейтов, построенный плагином для скоупа и доработанный конфигом (`overrideGates` → `skipGates` → `extraGates`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Scope**               | Подмножество репозитория, к которому применяется прогон: явные цели (`files`), изменения от базовой ветки (`changed`, default) или весь репозиторий (`all`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Detection**           | Результат распознавания репозитория плагином: сводка для `--plan`, диагностики окружения, приватные данные плагина. Алгоритм — §3.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Diagnostic**          | Проблема окружения, найденная до запуска гейтов: `code` + `message` + `fix`. Никогда не игнорируется молча.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **RUN-ALL**             | Контракт прогона: выполняются все гейты плана независимо от отказов предыдущих; отказы накапливаются в одном отчёте.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **SUPPRESS-ON-SUCCESS** | Контракт отчёта: прошедший гейт не даёт ни строки вывода; печатаются только отказы, скипы и диагностики.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **FAIL**                | Гейт отработал и нашёл проблему **в коде**. Агент правит код.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **ENV_FAIL**            | Инструмент гейта не смог отработать (паника, ошибка конфига инструмента, недоступный registry/proxy, version skew). Код не виноват; отчёт запрещает править исходники. Классифицируется предикатами гейта (§4.2).                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **TIMEOUT**             | Гейт превысил свой per-gate `timeout` и был убит. Отдельный статус, не FAIL.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Stack config**        | Секция `stack` конфига «Геннадия» — [config.spec.md](../config/config.spec.md).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

## 3. Detection Algorithm

Детекция определяет, какие плагины активны для репозитория. Алгоритм детерминирован и намеренно примитивен — **существования маркер-файла в корне достаточно**; для экзотических раскладок есть `stack.use`:

1. **Кандидаты.** Реестр встроенных плагинов, отсортированный по id: `[anystack, golang, node]` (plugins.spec D-SP-009).
2. **Ограничение `use`.** Если в конфиге задан `stack.use` — реестр сужается до перечисленных id. Неизвестный id → ошибка конфига (config.spec §4.1). CLI-флаг `--stack=<id>` действует как одноразовый `use`.
3. **Опрос.** У каждого кандидата вызывается `detect(root)`:
   - `anystack`: распознаёт любой репозиторий (маркера нет); собственных гейтов не имеет — все приходят из `extraGates`.
   - `node`: существует файл `<root>/package.json`. Содержимое на детекцию не влияет: сломанный агентом JSON не должен «раздетектить» плагин — битый файл всплывёт диагностикой на этапе планирования гейтов.
   - `golang`: существует файл `<root>/go.mod`. Поиска вглубь нет — overkill; для нестандартной раскладки оператор задаёт `use` и/или `--root`.
4. **Активные = все распознавшие.** Репозиторий может быть node и golang одновременно — оба плагина активны, их гейты объединяются в один прогон в порядке реестра.
5. **Ноль активных** → `NO_STACK_DETECTED`, exit 5, с перечнем известных маркеров и подсказкой (`--root`, `stack.use`). Поскольку `anystack` распознаёт всё, без `use`/`--stack` это состояние недостижимо: незаконфигурированный репозиторий получает `ZERO_GATES` (exit 1, §8.4), а exit 5 остаётся для явно названного стека, не распознавшего репозиторий.

Инварианты: `detect` не мутирует дерево; из процессов позволены только короткие probe-вызовы версий инструментов — это разрешение, а не требование: встроенные плагины на детекции процессов не запускают (golang проверяет наличие бинарей через fs, а version skew ловит envFail-правилом на прогоне). Дополнительные обходы (например поиск вложенных `go.mod` для диагностики `NESTED_MODULES`) — информационные и на решение о детекции не влияют.

## 4. StackPlugin Interface

### 4.1 Ядро

```ts
type StackPlugin = {
  /** Уникальный id плагина: 'node' | 'golang' | 'anystack'. */
  readonly id: StackId;

  /** Маркер-файл детекции (например `go.mod`) — все ростеры (help, ошибки) рендерятся из реестра. */
  readonly marker: string;

  /** Однострочное описание для help и ростеров. */
  readonly description: string;

  /**
   * Распознать репозиторий по маркер-файлу в корне (§3). null — не этот стек.
   * Инвариант: не мутирует дерево; процессы — только version-probe'ы.
   */
  detect(root: string): StackDetection | null;

  /**
   * ОБЯЗАТЕЛЬНЫЙ словарь: все id гейтов, которые плагин может выдать.
   * Строгая валидация конфига сверяется с ним без детекции (plugins.spec §5).
   */
  readonly gateIds: readonly string[];

  /** ОБЯЗАТЕЛЬНЫЙ фасет: плагин с одним verify полноценен (§4.3). */
  readonly verify: StackVerifyCapability;

  // Опциональные фасеты — post-v1, полей в v1-типе нет (§4.3; фасет fix отменён,
  // FR-STACK-14: мутации живут в поле гейта `fixer`, не в отдельном фасете):
  // readonly testcov?: StackTestcovCapability;     // planned, §4.3
  // readonly dbcLint?: StackDbcLintCapability;     // planned, §4.3
  // readonly directives?: StackDirectivesCapability; // planned, §12
};
```

**Почему `detect` возвращает `StackDetection`, а не boolean.** Решение «наш/не наш» действительно бинарно (§3), но по пути детекция собирает факты, которые нужны всем последующим шагам: строки сводки для `--plan`, диагностики окружения (version-skew ловится probe-вызовом уже здесь), распарсенные данные репозитория (для golang: вендоринг, путь конфига golangci, модуль) — они переиспользуются в `resolveScope`/`planGates` через `details`, чтобы каждый фасет не перечитывал диск заново. Boolean заставил бы делать ту же работу повторно в каждом фасете.

### 4.2 Фасет `verify`

```ts
type StackVerifyCapability = {
  /**
   * Сузить прогон. request.mode: 'files' (явные цели) | 'changed' (diff от
   * базовой ветки + staged + untracked; default) | 'all' (весь репозиторий).
   * Плагин, не умеющий сужаться (node: npm-скрипты репо-уровневые), возвращает
   * репо-уровневый scope с честным note.
   */
  resolveScope(detection: StackDetection, request: ScopeRequest): StackScope;

  /**
   * Построить упорядоченный план гейтов. Неисполнимый гейт представлен
   * skipped: <reason>, а не выброшен.
   */
  planGates(detection: StackDetection, scope: StackScope, options: GatePlanOptions): Gate[];
};

/**
 * Предикат классификации отказа: получает исход гейта (exit code, флаг таймаута,
 * stdout/stderr/combined в окне head+tail, §8.2), true = отказ вызван окружением
 * (ENV_FAIL), а не кодом. Библиотека даёт готовые комбинаторы; плагины и конфиг
 * составляют из них набор per-gate. `describe` обязателен — сработавшее правило
 * называется в отчёте и в `--plan --json`; опциональный `hint` — подсказка по
 * починке окружения, раннер дописывает её к выводу; `source` — файл конфига,
 * из которого правило пришло (личное правило видно в момент срабатывания).
 */
type EnvFailPredicate = ((outcome: GateOutcome) => boolean) & {
  readonly describe: string;
  readonly hint?: string;
  /**
   * Что инспектирует предикат. `exit` описывает exit-code-конвенцию ОДНОГО бинаря и
   * поэтому не наследуется при `overrideGates.<id>.argv` (обёртка возвращает свои коды);
   * `output` описывает окружение и наследуется всегда.
   */
  readonly kind?: 'exit' | 'output';
  readonly source?: string;
};

// Встроенные комбинаторы (services/stack/env-fail.ts):
//   exitCodeMatches(op, n|n[], hint?) — условие на exit code (golangci-lint: `> 1` = поломка)
//   outputMatches(re, hint?)          — combined-вывод содержит совпадение (например /^panic: /m)
//   streamMatches('stdout'|'stderr', re, hint?) — то же по одному потоку
//   allOf(parts, hint?)               — конъюнкция предикатов
// Сбой запуска процесса (ENOENT и т.п.) раннер классифицирует как ENV_FAIL сам —
// это environmental для любого стека, комбинатор не нужен.

type Gate = {
  /** Id гейта, уникален внутри плагина ('build', 'test', …). */
  id: string;
  /** Стек-владелец; квалифицированное имя в отчётах и CLI: `${stack}:${id}`. */
  stack: StackId;
  /** Короткая человекочитаемая подпись для отчётов. */
  label: string;
  /** Команда с аргументами; исполняется spawn'ом БЕЗ shell — без интерполяции и пайпов. */
  argv: readonly string[];
  /** Рабочая директория гейта (абсолютная). */
  cwd: string;
  /** Переменные окружения, мержатся поверх process.env; из конфига — GateSpec.env. */
  env?: Readonly<Record<string, string>>;
  /**
   * ОБЯЗАТЕЛЬНЫЙ per-gate таймаут (мс); превышение → статус TIMEOUT.
   * Глобального таймаута нет: верхняя граница прогона = сумма таймаутов плана —
   * гейтов и их `requires`-предусловий (D-STACK-007). Гейт, чей инструмент имеет
   * собственный флаг таймаута (go test -timeout), рендерит во флаг значение
   * ЧУТЬ НИЖЕ гейтового (90%, целые секунды) — инструмент завершается сам до
   * жёсткого kill'а и успевает напечатать диагноз (goroutine dump).
   */
  timeoutMs: number;
  /** Контракт `gofmt -l`: exit 0 + непустой stdout = FAIL. */
  outputMeansFailure: boolean;
  /**
   * Drift-гейт (см. §2 «Drift-гейт»): мутация ожидаема, непустой drift
   * дерева после команды — вердикт FAIL. Чистота дерева гарантирована
   * предусловием (D-STACK-017); без этого флага мутация — VIOLATION
   * (имя по образцу outputMeansFailure, D-STACK-014).
   */
  driftMeansFailure?: boolean;
  /** Предикаты ENV_FAIL; пусто/отсутствует — любой отказ трактуется как FAIL (код виноват). */
  envFail?: readonly EnvFailPredicate[];
  /**
   * Мутирующее лечение этого гейта (§4.4): та же команда, но в реальном дереве.
   * Исполняется только `gennady fix <stack>:<id>`, в verify-план не попадает.
   */
  fixer?: Cmd;
  /**
   * Предусловия окружения, исполняемые ДО команды гейта. Первое упавшее — ENV_FAIL
   * с его `hint`; команда гейта при этом не запускается (§4.7). Так «docker не поднят»
   * обнаруживается за миллисекунды вместо десятиминутного зависания на таймауте.
   */
  requires?: readonly Cmd[];
  /** Причина, по которой гейт не исполняется (репортится, не запускается); null — исполняемый. */
  skipped: string | null;
};
```

### 4.3 Классификация capabilities: mandatory vs optional

**Обязательные** — без них плагин не является валидным `StackPlugin`, а v1 не является usage-ready. Обязателен ровно один фасет:

| Capability | Команда CLI                                 | Почему обязателен                                                                                | Задачи v1                                                       |
| ---------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| `verify`   | `gennady verify` (+ skill-гейт `verify.sh`) | Единственный фасет, от которого зависит цикл SDD execute→verify — то, ради чего scope существует | TSK-95 (библиотека + оба плагина), TSK-96 (команда + делегация) |

Отдельная обязательная команда `gennady build` не вводится: сборка уже является гейтом verify (`golang:build`; для node — typecheck как ближайший аналог компиляции), и точечный запуск покрыт `gennady verify --only=build`. Выделенная команда дублировала бы контракт verify ради одного гейта; если появится сценарий, где build нужен вне верификации (артефакты, кросс-компиляция) — это будет отдельный фасет со своей спекой.

**Опциональные** — могут быть не реализованы; поддержка может различаться между плагинами (плагин без опционального фасета честно репортит «не поддерживается» в соответствующей команде). Реализуются отдельными задачами после v1:

| Capability        | Команда CLI                        | Что отдаёт плагин                                                                                                                                                                                                                                                                                                                | Статус                                                                  |
| ----------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `testcov`         | `gennady testcov`                  | Как запустить тесты с coverage и где искать отчёт (go: `go test -coverprofile` + `go tool cover`); сегодня testcov захардкожен на vitest/jest/node:test                                                                                                                                                                          | planned, post-v1                                                        |

### 4.4 Fixer'ы и drift-гейты — мутирующие операции

Мутирующие команды полезны, но несовместимы с верификацией — поэтому две связанные сущности:

- **Названный fixer исполняется по всему репозиторию.** `verify` печатает подсказку `gennady fix <stack>:<id>` без флагов скоупа, под которыми он сам работал; значит подсказка обязана работать как напечатана. Явное имя — явный запрос, поэтому скоуп для него `all`, а не `changed`.
- **`fixer` — поле гейта, а не отдельная секция.** Мутирующая операция всегда принадлежит конкретной проверке: «что чинит `golang:generate`» — вопрос без смысла в отрыве от гейта `generate`. Поэтому fixer объявляется прямо на гейте (`Cmd`, §4.5), а его квалифицированное имя — имя гейта: `gennady fix golang:generate`. Отдельной секции `fixers` и отдельного фасета `fix` у плагина нет: гейт и его лечение живут рядом и не могут разъехаться по id.
- **`gennady fix [id…]`** — строит **тот же план**, что `verify`, и исполняет `fixer` тех гейтов, которые его объявили: все или перечисленные адресно. Последовательно (мутируют одно дерево), отказ останавливает цепочку. Реальное дерево, без реплики — мутация здесь и есть цель.
- **Drift-гейт** (§2) — верификационная половина того же цикла: команда, существующая только в мутирующей форме (кодогенерация), исполняется в реплике дерева; непустой drift = FAIL со списком файлов. Кодогенерация — пререквизит `build`, поэтому такой гейт стоит в плане **до** `build` (FR-STACK-09).

**Цикл:** `verify` → `generate`-гейт FAIL «сгенерированный код разошёлся, файлы: …» → `gennady fix golang:generate` материализует результат в реальном дереве (явное действие агента/оператора) → агент коммитит → `verify` зелёный.

Семантика не зависит от того, закоммичен ли сгенерированный код:

- **закоммичен** — drift чистого дерева ловит рассинхрон с исходниками (локальный аналог `generate` + assert-no-diff из CI);
- **в gitignore** — drift-гейт проходит (ignored-пути в статус не попадают), а материализация перед сборкой выполняется тем же fixer'ом; сборочный отказ из-за отсутствующих сгенерированных файлов указывает на `gennady fix`.

Инструменты генерации: гейты исполняются в реальном дереве, поэтому работают и генераторы вне дерева (`go install`, GOBIN, `tool`-директивы go.mod), и repo-relative бинари в gitignored-каталогах (`bin/` — легальная рабочая зона, D-STACK-017). «executable file not found» в выводе `generate`-гейта по-прежнему классифицируется как ENV_FAIL с подсказкой по установке, а не как drift-FAIL.

v1 реализует команду `gennady fix` и fixer на гейте `golang:generate`; прочие — post-v1 (§4.3).

### 4.5 `Cmd` / `CmdSpec` — одна форма команды на три места употребления

Гейт, предусловие (`requires`) и fixer — это одна и та же сущность «команда»: argv без shell, рабочая директория, переменные окружения, таймаут. Поэтому форма ровно одна, и в конфиге это **один** тип:

```ts
type Cmd = {
  argv: readonly string[]; // без shell
  cwd: string; // абсолютная (в конфиге — относительно корня репо)
  env?: Readonly<Record<string, string>>;
  timeoutMs: number; // в конфиге — duration-строка `timeout`
  hint?: string; // для requires: что делать, если предусловие не выполнено
};
```

Отдельных `RequiresSpec`/`FixerSpec` нет: три места употребления различаются **семантикой вокруг** команды (вердикт гейта / предусловие / мутация), а не её формой. Одна схема означает один набор правил валидации, один способ описать `cwd`/`env`/`timeout` и отсутствие расхождений между местами.

### 4.6 Контракт паритета: конфиг-гейт — первоклассный гейт

Плагины покрывают типовую инфраструктуру; репозиторий, чья инфраструктура не совпала со встроенным гейтом, обязан получить **ровно те же возможности** через конфиг. Иначе §1 («репозитории отличаются конфигом, а не командами») выполняется только для тех, кому повезло с тулчейном, а остальные возвращаются к самописным скриптам — то есть к проблеме, ради которой существует эта система.

**Правило.** Каждое поле `Gate`, на которое реагирует раннер, объявляемо в `GateSpec` — и в `overrideGates` (наследуется, если не задано), и в `extraGates` (со своим дефолтом). Появление нового поля в `Gate` без строки в `GateSpec` — незакрытая задача, а не деталь реализации.

**Единственное исключение — «обёртка» гейта**, то есть то, что система навешивает вокруг команды и что конфиг не должен уметь подделывать:

| Поле      | Почему не объявляемо                                                                                                                      |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `stack`   | выводится из секции конфига, в которой гейт объявлен; ручное значение означало бы гейт, живущий не в своём стеке                          |
| `label`   | синтезируется вместе с провенансом (`… (from gennady.yaml)`, `… (overridden by .gennadyrc)`); рукописная подпись скрыла бы источник гейта |
| `skipped` | вычисляется планировщиком (скоуп, отсутствующий тулчейн) и `skipGates`; авторская форма уже есть — это и есть `skipGates`                 |

Всё остальное — команда и её семантика (`argv`, `cwd`, `env`, `timeout`, `outputMeansFailure`, `driftMeansFailure`, `envFail`, `requires`, `fixer`) — обязано быть доступно обоим уровням.

**Переименования допустимы, но не молча.** Где конфиг-форма осознанно отличается от рантайм-поля (`timeoutMs` ↔ duration-строка `timeout`, config.spec D-CFG-003), соответствие фиксируется явным alias-списком в тесте паритета.

**Механическая проверка.** Тест берёт **рантайм-объединение** ключей гейтов, запланированных обоими встроенными плагинами, вычитает список исключений и alias'ы и требует, чтобы остаток был подмножеством `GATE_SPEC_KEYS`. Список исключений проверяется в обратную сторону: ни одно из трёх полей не должно быть объявляемым. Поэтому контракт не зависит от дисциплины ревьюера: плагин, начавший эмитить новое поле, роняет тест до появления конфиг-ключа.

### 4.7 `requires` — предусловия окружения

Классификация отказа по факту (§4.2, `envFail`) не покрывает случай, когда окружение сломано так, что команда **зависает**: `docker compose up --wait` без демона ждёт до таймаута, и гейт получает `TIMEOUT` без указания причины. `requires` решает это структурно: перед командой гейта исполняются предусловия, и первое упавшее даёт `ENV_FAIL` со своим `hint` — за миллисекунды, не за таймаут.

- Предусловия исполняются **в том же контексте**, что и команда гейта (то же реальное дерево, тот же `cwd`).
- Первое упавшее предусловие → `env-fail`; вывод содержит его argv и `hint`; **команда гейта не запускается**.
- Все предусловия прошли → гейт исполняется обычным порядком (§8.2).
- `hint` у предусловия **обязателен**: предусловие без инструкции по починке сообщает агенту не больше, чем таймаут.
- Предусловия — не гейты: они не дают собственного вердикта, не попадают в `--only`/`--skip` и не считаются в `passed`/`total`.

## 8. Module Contracts (DbC)

### 8.1 StackPlugin

- **Runtime Backing:** `real-runtime` · **Verification Levels:** `unit`

- Preconditions: `detect(root)` получает абсолютный существующий путь.
- Postconditions: `detect` → null или `StackDetection` с непустым `summary`; `planGates` → детерминированный порядок; каждый исполняемый гейт имеет `timeoutMs > 0`; неисполнимый гейт — `skipped: <reason>`, не исключение.
- Invariants: плагин не мутирует дерево; процессы на `detect` — только version-probe'ы; плагин не знает о конфиге (overrides применяет `applyStackConfig` поверх плана).

### 8.2 Gate Runner

- **Runtime Backing:** `real-runtime` · **Verification Levels:** `unit`

- Preconditions: каждый исполняемый гейт имеет непустой `argv[0]` и `timeoutMs > 0`.
- **Окно вывода для предикатов.** Регекспы из конфига исполняются в процессе «Геннадии» против вывода, который может достигать десятков мегабайт, поэтому предикаты видят **то же окно head+tail**, что печатает отчёт: классифицируется ровно то, что показывается. При `^`-анкоренных `/m`-паттернах отбрасывание середины может только **потерять** совпадение, то есть отказ уходит в консервативную сторону — `fail`, а не ложный `env-fail`.
- **Атрибуция сработавшего правила.** Вывод `env-fail` называет сработавшее правило (`describe`) и **файл-источник**, если правило пришло из конфига. Машинно-глобальное правило из `$HOME/.gennadyrc` меняет классификацию во всех репозиториях на машине, поэтому «это личное правило, а не политика проекта» должно быть видно в момент срабатывания, а не только в `--plan`.
- Postconditions: RUN-ALL; SUPPRESS-ON-SUCCESS; `requires` исполняются до команды гейта, первое упавшее предусловие → `env-fail` с его `hint`, команда гейта не запускается (§4.7) — **на обоих путях**: и под guard'ом, и без него (fixers, репозиторий без git), иначе предусловие защищает ровно тот путь, где оно и так безопасно; `outputMeansFailure: true` + exit 0 + непустой stdout → `fail`; **clean-tree guard** (§2, D-STACK-017): guard берётся лениво перед первым исполняемым гейтом каждого git-toplevel'а (lock + проверка `git status --porcelain`); грязный toplevel → `env-fail` для его гейтов с причиной DIRTY_TREE (корневой toplevel отвергается ещё до прогона, exit 4); гейты исполняются в реальном дереве с оригинальными argv/cwd, никакого маппинга путей нет; `driftMeansFailure: true` + непустой drift-статус после команды → `fail` со списком файлов; гейт **без** `driftMeansFailure` + непустой статус → `violation` со списком файлов; после любого грязного статуса дерево сбрасывается к HEAD (`git reset --hard` + `git clean -fd`, без `-x` — ignored переживают) до следующего гейта — сброс доказуемо точен, состояние до прогона и есть HEAD; репозиторий без git/HEAD → гейты исполняются без guard'а + диагностика `UNSANDBOXED_RUN`, а `driftMeansFailure: true`-гейт при этом → `env-fail`; lock снимается на успехе/исключении/SIGINT/SIGTERM; lock, оставшийся от упавшего прогона, при живом процессе → отказ, при мёртвом с флагом «дерево было чистым» → автоматический `reset --hard` + `clean -fd` с уведомлением, без флага → lock снимается и чистота перепроверяется как обычно; переполнение буфера захвата (`ENOBUFS`) → **не** `env-fail`: инструмент отработал, кода выхода нет, вердикт доходит до конца лестницы и становится `fail` с пометкой об обрезанном выводе (назвать это средой значит сказать «код не трогай» про гейт, который мог упасть по делу); предусловие с несуществующим `cwd` → `env-fail` со своим `hint`, а не падение раннера; превышение `timeoutMs` → `timeout`, причём процесс снимается **SIGKILL**, а не SIGTERM: гейт, игнорирующий SIGTERM, иначе доживает до конца (измерено: 4s против таймаута 600ms) и классифицируется как `SIGPIPE`, а не как таймаут; любой сработавший `envFail`-предикат → `env-fail` + запрет менять код в отчёте, `hint` сработавшего предиката дописывается к выводу; `ok === true` ⇔ все исполненные гейты `pass` **и хотя бы один исполнен** — то же выражение, что у кода выхода: иначе прогон, не исполнивший ничего, печатал в `--json` «all green» и выходил с 1.
- Invariants: `spawnSync(argv)` без shell; `gate.env` мержится поверх `process.env`; вывод отказа усечён с маркером и командой воспроизведения.

#### 8.2.1 Порядок вердиктов

**Порядок вердиктов** — фиксированный и проверяемый: `skipped` → сбой запуска (`env-fail`) → **сработавший `envFail`-предикат** (`env-fail`) → `timeout` → `violation` → drift-вердикт drift-гейта (`fail`) → stdout-контракт → exit-код. Предикаты консультируются **до** таймаута, violation и stdout-контракта: правило описывает окружение, и знание «почему» полезнее знания «чем кончилось» (D-STACK-015). Побочные свойства: на таймауте могут сработать только output-правила (exit-условия не матчат `null` по построению), а при `env-fail` поверх грязного дерева список файлов всё равно печатается.

### 8.3 Stack Config

- Контракты схемы, merge и строгой валидации — [config.spec.md](../config/config.spec.md) §4.1.

### 8.4 Verify Command

- **Runtime Backing:** `real-runtime` · **Verification Levels:** `unit`, `e2e`

- Postconditions: exit `0` — все гейты прошли **и хотя бы один исполнен**; `1` — есть отказ, **или ни один гейт не исполнен** (`ZERO_GATES`: прогон, который ничего не проверил, не является успехом); `4` — неверный вызов, **невалидный конфиг** (FR-STACK-12) **или грязное дерево** (`DIRTY_TREE`, FR-STACK-17); во всех случаях ни один гейт не исполнен; `5` — ни один плагин не распознал репозиторий (достижимо через `stack.use`: `anystack` определяется везде, поэтому без `use` активный набор непуст и незаконфигурированный репозиторий получает `ZERO_GATES` с подсказкой вместо кода 5). `--plan` не исполняет ни одного гейта и показывает per-key провенанс конфига. `--json` — машиночитаемые `runs` + `results`; вывод отказавших гейтов усечён (head+tail) как и в человеческом отчёте, `--full-output` отключает усечение. **Контракт для оркестраторов:** `results[].status === "env-fail"` и агрегат `envFailed` — стабильные поля; env-fail означает поломку окружения, править код в ответ нельзя. `results[].status === "violation"` — тоже стабильный статус: гейт мутировал реплику; лечится переносом мутации в `fixer` гейта (`gennady fix`, §4.4), не правкой кода. Прогон без единого исполненного гейта несёт `diagnostics[].code === "ZERO_GATES"` — стабильный маркер «ничего не проверено» и в `--json`. Оркестратор может ветвиться по любому из трёх согласованных сигналов: exit-код `1`, `ok: false` и этот диагноз. `ok` в `--json` считается тем же выражением, что и код выхода (все исполненные гейты `pass` **и хотя бы один исполнен**), поэтому «вакуумно true на пустом прогоне» больше не бывает — раньше именно это говорило парсеру «all green» про прогон, который вышел с 1; диагноз при этом остаётся единственным, кто называет **причину**. Отдельного exit-кода для env-fail нет (оркестратор читает JSON), коды остаются `0/1/4/5`.
- Invariants: **стек, не запланировавший ни одного гейта, не является частью прогона** — его нет ни в списке `stacks:`, ни в блоке `summary`/`scope`, ни в строке вердикта, ни в `runs` у `--json`: описывать стек, который ничего не проверял, читателю нечего. Плюс: явные позиционные цели → `files`; `--all` → `all`; иначе `changed`. `--only`/`--skip` принимают `stack:gate` и короткое `gate`.

### D-STACK-003 — Гейт — данные, раннер — один

- **Status:** active
- **Why:** Пока гейт — это `argv + cwd + env + timeout + контракт`, RUN-ALL/SUPPRESS-ON-SUCCESS/усечение/таймаут/классификация написаны один раз и не могут разъехаться между стеками. Плагины остаются чистыми планировщиками — тестируются без запуска процессов.

### D-STACK-004 — env-fail-классификация: предикаты на гейте, не знания в раннере

- **Status:** active
- **Recorded:** spec review round 2, PR #5 — форма изменена с деклараций на предикаты
- **Why:** «Паника golangci-lint», «exit > 1 у линтера», «Forbidden от module proxy» — знания Go-стека. Гейт несёт набор функций-предикатов `(outcome: GateOutcome) => boolean`, собранных из библиотечных комбинаторов (`exitCodeMatches`, `outputMatches`, `streamMatches`, `allOf`); сбой запуска процесса раннер классифицирует сам, отдельный комбинатор не нужен. Ни одного стек-специфичного регекспа в общем коде; предикаты выразительнее статических деклараций (композиция, отрицания).

### D-STACK-005 — Мутирующие команды запрещены как гейты; для мутаций — Fixer'ы

- **Status:** active
- **Recorded:** spec review round 2, PR #5 — добавлена сущность Fixer
- **Why:** `go fmt` / `prettier --write` / `go mod tidy` переписывают дерево — гейт никогда не падает и молча дописывает диф агента посреди фазы. Проверочные формы: `gofmt -l` (+ `outputMeansFailure`), `prettier --check`, `go mod tidy -diff`. Мутирующие операции нужны — поэтому отдельная сущность `Fixer` и глагол `gennady fix` (§4.4): явный вызов оператором, никогда не в verify-плане.

### D-STACK-006 — node-плагин игнорирует позиционные цели

- **Status:** active
- **Why:** npm-скрипты — репо-уровневые команды; сузить `npm run test` до файла нельзя без знаний о раннере (забота будущего фасета `testcov`). Честное поведение: node-гейты всегда репо-уровневые, `scope.note` это фиксирует.

### D-STACK-007 — Per-gate timeout обязателен; глобального таймаута нет

- **Status:** active
- **Recorded:** spec review round 2, PR #5 — добавлен рендер во флаг инструмента, убран конфиг-ключ testTimeout
- **Why:** Два источника таймаута — кластер багов «timeout inconsistency». Один источник истины: каждый гейт несёт `timeoutMs`; дефолты — у плагина per-gate (golang: build/vet/lint 5m, fmt 1m, test 10m; node: 10m); конфиг переопределяет per-gate. Верхняя граница прогона = сумма таймаутов плана, таймауты видны в `--plan`. Инструмент с собственным флагом (go test -timeout) получает то же значение — самозавершается раньше жёсткого kill'а и успевает напечатать goroutine dump.
- **Rejected alternatives:** глобальный `--timeout` (v1-прототип; убран), конфиг-ключ `testTimeout` (дубль per-gate таймаута; убран).

### D-STACK-008 — Capability-фасеты: verify обязателен, остальные опциональны

- **Status:** active
- **Recorded:** spec review round 2, PR #5 — добавлена явная классификация mandatory/optional
- **Why:** Per-stack параметризация нужна не только verify (§4.3), но usage-ready v1 определяется единственным фасетом, от которого зависит SDD-цикл — verify. Опциональные фасеты добавляются опциональными полями, их поддержка легально различается между плагинами; плагин без фасета честно репортит «не поддерживается».

### D-STACK-009 — Никаких плагин-специфичных ключей конфига в v1

- **Status:** active
- **Recorded:** spec review round 2, PR #5
- **Why:** Прежние ключи избыточны: `testTimeout` — дубль обязательного per-gate `timeout` (гейт сам рендерит его в `go test -timeout`); `lintConfig` — покрывается авто-поиском + `overrideGates.lint.argv`; `tidy` — убран из встроенных гейтов, drift-проверка объявляется одной строкой в `extraGates` (пример в config.spec §2). Если реальная нужда появится — ключи пойдут в выделенный объект `stack.<plugin>.config` с отдельной спекой плагина и строгой валидацией; всё вне известной схемы — ошибка конфига.
- **Rejected alternatives:** placeholder-подстановки `${VAR}` в argv (интерполяция в argv — новый класс ошибок; вернёмся, если появится кейс, не покрываемый env+override).

### D-STACK-010 — Мультипроектные репозитории: один root на прогон (v1), multi-root — отложено

- **Status:** active
- **Recorded:** review, mobile-spike feedback (PR #5)
- **Why:** Канонический мобильный монорепозиторий держит проекты в `ios/` и `android/` без маркеров в корне: `detect(root)` зовётся с одним root, `--root` принимает одно значение, `use` не форсит активацию — такой корень честно даёт `NO_STACK_DETECTED`. v1-воркфлоу: прогон на каждый проект (`--root=ios`, `--root=android`) + диагностика вложенных манифестов, как у golang с nested modules. Дизайн multi-root (кандидаты root'ов от плагина либо несколько `--root` у прогона) — отдельная итерация до Android-плагина; фиксируем направление, не реализацию.

### D-STACK-011 — Кодогенерация: drift-гейт до build + fixer, а не «остаётся в CI»

- **Status:** active
- **Recorded:** review discussion, PR #5 — supersedes формулировку «drift кодогена остаётся за CI» из round 5
- **Why:** Кодогенерация — пререквизит `build`, первого гейта: выносить её проверку в CI значит верифицировать потенциально устаревшее дерево локально. Мутирующий генератор исполняется в эфемерной реплике рабочего дерева (git worktree + незакоммиченные изменения, забейзлайненные локальным коммитом реплики — drift ловится по содержимому, включая файлы с правками агента); реальное дерево нетронуто, D-STACK-005 сохраняется без исключений. Материализация — явным `gennady fix golang:generate`.
- **Rejected alternatives:** запуск генератора в реальном дереве с откатом (откат tracked-файлов небезопасен при незакоммиченных правках агента в тех же файлах — тихая потеря работы); «дрейф ловит только CI» (round 5; отвергнуто ревью — см. Why).

### D-STACK-012 — Реплика не копирует ignored-файлы; отсутствующий генератор — ENV_FAIL с подсказкой

- **Status:** superseded by D-STACK-017 — реплики больше нет; ignored-пути объявлены легальной рабочей зоной гейтов. ENV_FAIL-классификация «executable file not found» на `generate`-гейте остаётся (FR-STACK-09)
- **Recorded:** интеграционный отчёт с внутреннего Go-монорепозитория (PR #5): генераторы жили в gitignored `bin/`, sandboxed `go generate` падал с «easyjson: executable file not found»
- **Why:** Реплика воспроизводит «fresh clone + незакоммиченные правки» — тот же мир, что видят CI и новый участник; генератор, существующий только как ignored-локальный артефакт, — именно та невоспроизводимость, которую этот взгляд должен вскрывать. `PATH` наследуется, так что `go install` / `tool`-директивы go.mod работают без настройки; копирование ignored-путей не ограничено по стоимости (кэши, node_modules) и прятало бы проблему. Отказ «executable file not found» — сломанное окружение, не drift кода: предикат ENV_FAIL на `generate`-гейте с подсказкой по установке (§8.4 запрещает агенту «чинить» код в ответ).
- **Rejected alternatives:** копировать ignored-файлы в реплику (неограниченная стоимость, легализует невоспроизводимое состояние); ключ `sandboxInclude` в GateSpec (эскейп-хэтч против принятой практики — onboarding-шаг `go install` решает то же за секунды; вернёмся, только если практика не приживётся).

### D-STACK-013 — Все гейты исполняются в одной реплике на прогон: контракт D-STACK-005 принудителен

- **Status:** superseded by D-STACK-017 — физическое предотвращение заменено предусловием чистого дерева + детект-и-откат (см. D-STACK-017); мотивация (D-STACK-005 принудителен, а не дисциплинарен) сохранена новым механизмом
- **Recorded:** review discussion, PR #5 — «no modifications» без исполнения остаётся строкой в спеке, worktree — реальное принуждение
- **Why:** «Гейт не мутирует дерево» до сих пор соблюдался только дисциплиной планирования (gofmt -l, скрининг npm-скриптов) — конфиговый или встроенный гейт мог молча мутировать. Одна реплика на прогон делает контракт физическим свойством по измеренной цене: на монорепозитории 566MB / 20k файлов — создание ~3.9s + baseline 0.3s + teardown 1.4s **однократно** и ~0.2s `git status` на гейт (против ~6s × N при реплике на гейт). Мутация гейта без `driftMeansFailure: true` — отдельный статус `violation` (не FAIL по коду, не ENV_FAIL) со сбросом реплики к baseline, чтобы следующие гейты видели чистое дерево. Кэши инструментов content-addressed (GOCACHE, golangci-lint) — компиляция не оплачивается дважды. **Ссылки расширяются из конфига.** Дефолты плагина держатся минимальными и только на read-only входы (`node_modules`, `bin`); всё остальное — общий кэш, тестовый профиль, вендор в сабмодуле — объявляется в `stack.<id>.sandboxLinks`. Причина: `anystack` — главный кейс уникальных репозиториев — не объявляет ссылок вовсе, и без конфигового ключа кастомный гейт из `extraGates` не мог дотянуться до нужного ему пути. Каждая ссылка — осознанная дырка в observe-only, поэтому путь обязан быть репо-относительным и не выходить за границу репозитория (абсолютный путь или `..` — фатальная ошибка конфига). Конфиговые записи поддерживают `*` внутри сегмента (генерируемый вывод масштаба Xcode/Tuist — это сотни ignored-путей, литеральный список стареет на каждом новом модуле); запись, не совпавшая ни с чем, — диагноз `UNRESOLVED_SANDBOX_LINK`, не молчаливый пропуск (иначе опечатка всплывает фантомным FAIL «про код») и не фатальная ошибка (на свежем клоне сгенерированного пути легитимно нет).

**Известное ограничение: сабмодули в реплике не материализуются.** `worktree add` идёт без `--recurse-submodules`, а `git diff`/`ls-files --others` содержимое сабмодуля не покрывают — это gitlink, а не untracked-файлы. Репозиторий, где исходники или вендор лежат в сабмодуле, получит в реплике пустой каталог и **ложный FAIL**. Обходится тем же ключом (`sandboxLinks: ['vendor']` — read-only ссылка); полноценный `--recurse-submodules` дороже и отложен.

Среда исполнения стека, живущая в ignored-путях (node: `node_modules`), symlink'уется по декларации плагина `sandboxLinks` — это среда, не состояние дерева, D-STACK-012 не ослабляется (node: `node_modules`, golang: `bin`, anystack: ничего). Пути реплики в выводе гейтов переписываются на реальные — иначе агент правит файлы в испаряющейся директории. Побочный выигрыш: `driftMeansFailure` в GateSpec становится тривиальным — реплика уже есть, флаг лишь выбирает семантику drift-вердикта (паттерн «быстрый скоуп-дефолт + канонический прогон адресно через skipGates + --only»).

- **Rejected alternatives:** реплика на каждый гейт (стоимость × число гейтов — измерено); доверять спеке без принуждения (нарушение обнаруживается только по факту порчи дерева); авто-symlink всех ignored-директорий (отменяет fresh-clone семантику D-STACK-012 для drift-гейтов); off-switch в конфиге (опциональное принуждение — не принуждение; fallback без git/HEAD покрывает честно застрявших).

### D-STACK-014 — `sandbox` → `driftMeansFailure`: флаг выбирает семантику вердикта, а не место запуска

- **Status:** active
- **Recorded:** review PR #5 — «Whole verify run is sandboxed now, do we still need this field?»
- **Why:** До D-STACK-013 флаг означал «исполнить этот гейт в реплике» — место запуска. После того как в реплике исполняются **все** гейты, это значение исчезло, а поле осталось нужным по другой причине: оно решает, чем является непустой drift реплики — **вердиктом гейта** (`fail` со списком файлов, кодогенерация) или **нарушением контракта** (`violation`). Имя врало о назначении, поэтому переименовано в `driftMeansFailure` — по образцу уже существующего `outputMeansFailure`, который так же описывает трактовку сигнала, а не место исполнения. Термин §2 «Sandboxed gate» стал «Drift-гейт» по той же причине: песочница теперь универсальна и в названии частного случая не участвует.
- **Rejected alternatives:** удалить поле (тогда мутирующая кодогенерация неотличима от гейта, нарушающего контракт — теряется и `gennady fix`-подсказка, и статус `violation`); оставить имя `sandbox` (описывает то, что стало общим для всех гейтов, и читается как «а остальные не в песочнице»).

### D-STACK-015 — Сработавшее `envFail`-правило старше таймаута, violation и stdout-контракта

- **Status:** active
- **Recorded:** review PR #5 + панель ревью: «лестница вердиктов делает `envFail` недостижимым в трёх из четырёх реальных форм отказа»
- **Why:** Предикаты консультировались последними, поэтому не срабатывали ровно там, где нужнее всего. Сломанное окружение чаще всего проявляется **зависанием** (`TIMEOUT` без причины и без запрета править код), **мусором в дереве** (`VIOLATION`, обвиняющий гейт) или **exit 0 с диагностикой** (stdout-контракт), а не аккуратным ненулевым кодом. Теперь `envFail` идёт сразу после сбоя запуска: если правило объяснило причину, вердикт — `env-fail` с `hint`, потому что «почему сломано» полезнее, чем «чем кончилось». Ослабление D-STACK-013 принято осознанно: мусор в дереве при сломанном окружении — симптом, а не нарушение контракта, поэтому файлы печатаются в выводе `env-fail`, а сама реплика по-прежнему сбрасывается к baseline. Без совпавшего правила приоритет прежний, и `VIOLATION` остаётся.
- **Rejected alternatives:** оставить `envFail` последним (три формы отказа неклассифицируемы, и агент получает `TIMEOUT` без единого указания, что делать); отдать приоритет `VIOLATION` над `env-fail` (формально строже, но агент получает «твой гейт мутировал дерево» вместо «подними docker» — обвинение вместо инструкции).

### D-STACK-016 — снимать группу процессов, а не только прямого ребёнка (open)

- **Status:** open
- **Problem:** таймаут снимает **прямого** ребёнка (`spawnSync` + `killSignal: 'SIGKILL'`). Внуки живут дальше: измерено — после возврата раннера два `sleep` из `sh -c 'sleep … & wait'` продолжали работать. Вердикт от этого не страдает (гейт классифицирован верно и вовремя), но осиротевший процесс может держать `GOCACHE`-локи и писать в каталог реплики, который раннер уже снёс.
- **Design:** асинхронный `spawn` с `detached: true`, затем на таймауте `process.kill(-pid, 'SIGTERM')`, grace-период, `process.kill(-pid, 'SIGKILL')`; вывод копится в ring buffer, из-за чего заодно исчезает лимит захвата (см. `ENOBUFS` в §8.2).
- **Why deferred:** ревью исходило из того, что вызывающие уже асинхронные. Это не так: `runVerify` и `runFix` — синхронные экспортируемые функции, их сигнатуры стоят в Entity Inventory (§7) и вызываются из `verify.cmd`/`fix.cmd` и десятков тестов. Переход на async — смена публичного контракта scope'а, а не правка раннера, и её место — отдельная задача с миграцией потребителей. Дешёвая часть (надёжное убийство и корректная классификация) уже сделана: SIGKILL не перехватывается, `error.code` остаётся `ETIMEDOUT`.
- **Acceptance:** после таймаута гейта, породившего фоновый процесс, в системе не остаётся ни одного его потомка.

### D-STACK-017 — verify исполняется в реальном дереве на чистом HEAD; реплика удалена

- **Status:** active · заменяет D-STACK-012 и D-STACK-013 (механику реплики; сам контракт D-STACK-005 «гейт наблюдает» остаётся в силе)
- **Recorded:** интеграция на мобильных репозиториях (PR #5): у реплики новый абсолютный путь и свежие mtime на каждый прогон — путезависимые кэши (Xcode, часто Gradle) холодные, verify ×30 медленнее ручной сборки (cloud-ios: 30 мин против ~1 мин warm); плюс 218 строк ручных `sandboxLinks`
- **Why:** одно предусловие заменяет всю машинерию. `verify` стартует только на чистом дереве (`git status --porcelain` пуст; ignored не учитываются) — иначе `DIRTY_TREE`, exit 4. Дальше всё следствия:
  - Гейты исполняются **в реальном дереве**: абсолютные пути и mtime стабильны — инкрементальные кэши живут; маппинг путей и перезапись вывода не нужны.
  - **Gitignored-пути — легальная рабочая зона гейтов.** Они локальны по определению (не попадают ни на какую другую машину, включая CI-раннеры) и являются ровно теми кэшами, ради которых прогон тёплый. Ключ `sandboxLinks` удалён — нечего линковать.
  - Вердикт: непустой `git status` после гейта — точный список мутаций → прежняя лестница (VIOLATION / drift-FAIL).
  - Откат: `git reset --hard` + `git clean -fd` (без `-x`). Доказуемо точен — состояние до прогона и есть HEAD; нет ни одного corner-case'а снапшота (каталоги, симлинки, mode-биты, бинарники, память): git делает всё сам.
  - Крэш-безопасность: lock-файл на репозиторий с флагом «дерево было чистым»; после падения авто-восстановление доказуемо безопасно.
  - Вердикт привязывается к commit SHA — verify проверяет закоммиченное состояние, то же, что чекаутит CI; отдельный CI-режим не нужен (свежий раннер чист по построению).
  - Цена, принятая осознанно: цикл «edit → wip-commit → verify → fixup» вместо «edit → verify → commit». Прежний инвариант «verify никогда не зелёный на непроверенном коде» сохранён отказом вместо реплики; `gennady commit` и `git stash` закрывают механику.
- **Rejected alternatives:** режимы изоляции `none|snapshot|worktree` (конфиг-матрица и три пути исполнения ради дефекта одного механизма); снапшот-restore по содержимому файлов (порт wisever: каталоги, симлинки, лимит памяти — хвост corner-case'ов); снапшот через git plumbing (временный индекс + `write-tree`: робастно, но git-internals и защищает ровно то незакоммиченное состояние, которое дешевле закоммитить); персистентная реплика со стабильным путём (лечит эфемерность и пути, но оставляет вторую копию дерева, холодный первый прогон, TTL/staleness/lock-машинерию — та же цена ради того же незакоммиченного состояния).
