# Use Cases agent-inbox (диаграммы переходов + неочевидные детали)

> Каждый кейс: диаграмма состояний/экранов/реакций + пояснение. UC-1…8 системные
> (каноника mermaid — [корневая спека §2](../agent-inbox.spec.md), здесь — читаемый
> рендер); UC-9…15 — уровень UI (владеет [inbox-dashboard](inbox-dashboard.spec.md)).

## Системные

### UC-1. Запуск и синхронизация (S1)

```
[off] → connect ──✗──┐
          │✓         │
          ▼          │
        poll ──✗─────┤
          │✓         ├──▶ [failed: ❌ причина + retry — с той же фазы, не с начала]
          ▼          │
       reconcile ──✗─┤
          │✓         │
          ▼          │
        restore ──✗──┘
          │✓
          ▼
       [ready] ──▶ авто-редирект на доску
```

**Неочевидное:** HTTP-слушатель поднимается ДО `connect` — иначе фазы невидимы по HTTP ·
«Открыть сейчас» пускает в read-only доску до ready · worktree — НЕ фаза (лениво, фоном,
иначе загрузка 60+ секунд как в v1) · падение фазы видимо, с retry именно этой фазы.

### UC-2. Авто-подхват роли (S2)

```
poll-снимок MR ── myRole (факт из GitLab)
   ├─ author/reviewer ─▶ очередь есть? ─нет→ enqueue пайплайн → 🔧 в ленте
   │                          │да
   │                          └→ продолжить (идемпотентно)
   └─ mentioned ─▶ «😴 Ждут других» (очереди нет)
        └ ручной override → assignedRole в реестре → очередь как у author/reviewer
```

**Неочевидное:** роль — не ручной акт, а вычисление; «без роли» существует только для
mentioned · ручное назначение — редкий override, не основной поток · повторный sync не
плодит дубли очереди (dedup по MR).

### UC-3. Ревью-пайплайн (S3)

```
prepare_env ─▶ plan ──▶ PLAN.md (минимальный, детерминированный — гарантирован даже при падении enrich)
                 │
                 ▼ enrich (flash; падение → слой 3 пропускается, пайплайн жив)
            fan-out (параллельно; линзы — волнами: 🧪 завершается → 🏛 стартует)
              ├─ track: файлы + чеклист (скрупулёзные баги)
              ├─ track: security (zero trust)
              ├─ triggered: deps-vuln / secrets / specs / миграции
              └─ линзы: 🏛 🎯 📜 🧪 🔐 ⚡ 🧾
                 ▼
            gate_coverage: чеклист × tool-trace ──недочит──▶ continue ТОЙ ЖЕ сессии (≤2) → эскалация
                 ▼
            synthesize (pro, read-тулы, указатели — не инлайн)
                 ▼
            gate_verdict ──fail──▶ synthesize с причинами (≤2) → эскалация оператору
                 ▼
            хвост: 👤 fetch_threads→verify→propose_replies · 👁 dedup→post→approve
```

**Неочевидное:** слои 1–2 обязательны к завершению, слой 3 advisory · coverage по
tool-trace (агент не может «сказать что прочитал») · enrich — украшение, не носитель
гарантий · линзы mandatory по умолчанию, крах линзы = эскалация, не тихий skip.

### UC-4. Новые коммиты → верификация (S4)

```
sync активных (~1/мин): sha ≠ lastReviewedHeadSha
   ▼ enqueue verify_fix (я автор) / delta_review (я ревьюер)
     · supersede только ОЖИДАЮЩЕЙ одноимённой задачи
     · идущие дорожки НЕ убиваются (доработают на старом SHA, дельта закроет разрыв)
   ▼
🦊-виджет «+N коммитов → задача #N»  ─▶ верификация ✔ ─▶ 💬-виджет с предложенными ответами на исправленные треды
```

**Неочевидное:** ~1/мин — только для МР с активной работой, не для всего inbox ·
дельта = отдельный мини-DAG (prepare→delta-changeset→затронутые дорожки→synthesize_delta→verdict).

### UC-5. Новые треды → триаж (S5)

```
sync: новые discussions ─▶ thread_triage ─▶ 🔧 фикс / 💬 ответ / 👍 согласие
                             │ + фактчек (детерминированная выгрузка тредов — не промпт-фантазия)
                             ▼
              💬-виджет «ждут мой ответ» + готовые реакции:
              [👍] [👍+резолв — только свои/бота] [💬 текст]
              [📋 репорт dev-агенту — только после фактчека и только мои дискуссии]
```

**Неочевидное:** резолв чужого треда запрещён детерминированно (disabled+причина) ·
предложение ответа появляется только ПОСЛЕ фактчека — не раньше.

### UC-6. Чат с якорями (S6)

```
выделение текста ─▶ мета-якорь {widgetId, artifactPath, fragment{start,end}, quote}
   ▼
Маршрут:  вопрос по артефакту ─▶ operator-сессия (персистентная, read-only)
          углубить ───────────▶ та же таск-сессия (жива? TTL-паркинг)
          фактчек / вширь ────▶ новая свежая сессия (adversarial)
          изменить артефакт ──▶ mutate-задача (очередь, CAS+снапшот)
   ▼
ответ в треде со ссылкой на якорь · мутация → отчёт в чат + 📄-событие в ленту
```

**Неочевидное:** якорь переживает мутацию (re-anchor по quote; офсеты — лишь подсказка;
quote потерян → stale, тред не теряется) · operator-сессия физически не может писать ·
история чата = журнал MR → переживает рестарт сервера и opencode.

### UC-7. Действия в GitLab — эффекты (S7)

```
decision accept ─▶ effect-задача (exclusiveWith: строго последовательно per MR)
   ▼ маркер идемпотентности пишется ПОСЛЕ подтверждения GitLab
   ├─✓─▶ ⚡ одноразовый виджет (resolved → тонет)
   ├─✗ сеть ─▶ failed + видимая причина; retry безопасен (маркера нет — дубля не будет)
   └─ повтор той же задачи ─▶ маркер найден → done без второго постинга
```

**Неочевидное:** dry-run подавляет эффект полностью, но оставляет `dryrun`-след в
журнале и SSE · гонка «уже резолвнут руками в GitLab» → no-op + журнал, не ошибка.

### UC-8. Градуированная автономия (S8)

```
capability = proposal ─▶ предложение ─▶ решение оператора
                                          ├─ accept ─┐
                                          ├─ edit ───┼─▶ журнал решений (датасет)
                                          └─ reject ─┘        ▼
                                   accept-rate ≥ 90% при n ≥ 20 (per capability)
                                          ▼
                                   capability = auto ─▶ автодействие + 🤖-бейдж + undo
```

**Неочевидное:** порог — на КАЖДУЮ capability отдельно (react может быть auto, approve —
ещё proposal) · edit с diff — самый ценный сигнал датасета · undo автодействия =
компенсирующий эффект где VCS позволяет (unapprove/unresolve/delete-note), иначе —
видимая пометка · reject тоже данные, не провал.

## Уровень UI (владелец: inbox-dashboard)

### UC-9. Навигация по экранам

```
#/boot ──ready──▶ #/ (доска) ⇄ #/mr/:ref (лента)
   └─ «Открыть сейчас» ─▶ #/ read-only (до ready)
неизвестный маршрут ─▶ #/
```

**Неочевидное:** чат-колонка не размонтируется при переходах (контекст меняется с
маршрута) · degraded sync — индикатор в шапке доски, не молчание · переход между двумя
MR не сбрасывает непрочитанное другого.

### UC-10. Жизненный цикл виджета

```
циклический (Находки/Треды/План):
  новое содержимое ─▶ bump вверх ленты ─▶ видно ТОЛЬКО новое/необработанное
      └─ обработанное ─▶ история виджета (сворачиваемая, не удаляется)
одноразовый (Действие):
  created ─▶ resolved ✔ ─▶ тонет навсегда
  повторное событие ─▶ НОВЫЙ инстанс (старый не воскресает)
```

**Неочевидное:** bump только при НОВОМ содержимом (не при любом lastActivity) ·
«запощенные находки» не исчезают из данных — они в истории виджета, доступны.

### UC-11. Оптимистичное действие и его неудача

```
клик ─▶ локально «⏳ #N» (<100 мс) ─▶ POST /task ─▶ {taskId}
          │                                       │
          │                            подтверждение: SSE task_update / батч
          ▼
     ошибка ─▶ «❌ + retry» в самом виджете (НЕ откат в пустое состояние)
```

**Неочевидное:** taskId приходит синхронно — виджет следит за СВОЕЙ задачей ·
двойной клик не плодит задачи (дедуп на сервере по dedupKey) · скелетон — только
когда данных нет вообще, не при каждом обновлении.

### UC-12. Решение по предложению (decision flow)

```
⚡ виджет решения (шапка/лента)
   ├─ [accept] ─▶ POST /decision ─▶ {taskId} ─▶ ⏳ ─▶ effect в очередь
   ├─ [edit]   ─▶ правка payload ─▶ {taskId} ─▶ ⏳ (decision=edit + diff в журнал)
   └─ [reject] ─▶ 204 (decision=reject в журнал; задачи нет)
```

**Неочевидное:** reject — полезные данные для accept-rate, не «отмена без следа» ·
edit-diff хранится целиком — это обучающий сигнал · после accept виджет следит за
эффектом по taskId до ⚡-поста.

### UC-13. Разрыв транспорта

```
SSE ✗ ─▶ батч /api/state каждые 3–5с ─▶ экспоненциальный backoff до 30с
          + баннер «соединение потеряно» (честно, не тихий протухший UI)
SSE ✓ ─▶ батч выключается, стрим — основной канал
```

**Неочевидное:** батч — реконсиляция, а не основной канал · доска продолжает свой
медленный poll 10–15с независимо от MR-стрима.

### UC-14. Непрочитанное

```
новые записи журнала ─▶ 📬+N на карточке доски
открытие MR ─▶ GET /feed ─▶ сервер lastReadAt=now ─▶ 📬=0 + разделитель «новое с прошлого визита»
```

**Неочевидное:** курсор — серверный (реестр), поэтому счётчик доски и разделитель ленты
не могут разъехаться · «новое» = от прошлого визита, а не за интервал времени.

### UC-15. Краш сервера глазами оператора

```
краш ─▶ рестарт ─▶ restore из журналов ─▶ доска идентична (карточки/очереди/лента)
```

**Неочевидное:** running-задачи → queued (перезапуск), но применённые эффекты НЕ
дублируются (маркер в журнале) · оператор в идеале не замечает краша, кроме паузы ·
это контрольный сценарий приёмки (crash_recovery в inbox-eval).
