# ADR: связи файлов и семантическое владение в SDD v2

- **Статус:** принят
- **Дата:** 2026-09-20
- **Решение:** D-40
- **Приёмка:** A17
- **Задача плана:** FO-1

## Контекст

В устаревшей шапке исходного файла хранится дополняемый список `@tasks`. Этот список смешивает
текущее владение, запланированную работу, завершённую работу и историческое происхождение.
Толкование каждого исторического тикета как текущего владельца файла может направить новую находку
в закрытый тикет и переоткрыть его без актуального доказательства.

SDD v2 отделяет стабильного семантического владельца от связей жизненного цикла задач. Исходный
файл один раз называет владельца; инструменты выводят рабочие связи из версионируемых спецификаций,
тикетов, квитанций и Git. Вычисленное представление доступно только для чтения и может кэшироваться
лишь как пересобираемая проекция, а не как второй источник истины.

Этот ADR задаёт контракт для FO-2—FO-6. Он не реализует resolver, не меняет вывод CLI, не
переписывает шапки и не мигрирует данные репозитория.

## Решение

### Каноническая шапка V2

Новый или мигрированный исходный файл V2 содержит следующие поля владения:

```text
@file: <назначение>
@spec: <canonical-spec-id>
@consumers: <список потребителей>
```

`@spec` хранит canonical spec ID ровно одного текущего семантического владельца. Канонический
registry/resolver однозначно разрешает ID в путь спецификации, например
`SPEC: CLI-ORIENT -> specs/cli/orient/orient.spec.md`. Путь является вычисленным результатом, а не
значением `@spec` и не вторым источником истины. Требование точного пути относительно корня
репозитория относится к сопоставлению `Target Files`/`Deleted Files`, а не к значению `@spec`.
Шапка не копирует историю тикетов. Новый исходный файл V2 не добавляет `@tasks`.

Устаревшее V1-поле `@tasks` остаётся допустимым, побайтово сохраняемым входом миграции. В V1 оно
может давать кандидатов доказательств для миграции. В V2 оно не является ни семантическим владельцем, ни
источником маршрутизации, а историческая запись `@tasks` сама по себе не может переоткрыть
завершённый тикет. В смешанном репозитории правило определяется для каждой области: нетронутый
V1-сосед сохраняет устаревшее поведение, а мигрированная область V2 использует контракт `@spec`.

### Постановка `AX_FILE_HEADER_TASK_TRACEABILITY`

В V2 каждая шапка исходного файла имеет canonical spec ID ровно одного разрешимого семантического
владельца `@spec`.
Связи тикетов `planned`, `active`, `blocked` и `history` выводятся из версионируемых артефактов и
никогда не копируются в шапку как источник владения. Устаревшее `@tasks` служит только evidence для
миграции и само по себе не может маршрутизировать или переоткрывать работу V2. FO-5 отвечает за
активацию этой постановки в действующей аксиоме, шаблонах и потребителях рабочего процесса; FO-1 фиксирует
нормативное утверждение, не меняя этих потребителей.

### Модель связей

Для нормализованного пути к файлу относительно корня репозитория resolver предоставляет пять
раздельных связей:

| Связь            | Смысл                                                                                                                          | Источник истины                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| `semantic-owner` | Canonical spec ID из `@spec`, однозначно разрешённый в спецификацию; текущий источник истины о предназначенном поведении.      | Один `@spec` + canonical spec registry/resolver |
| `planned`        | Открытый тикет или фаза объявляет точный target, но работа ещё не начата.                                                      | Открытый тикет и состояние фазы                 |
| `active`         | Фаза, объявляющая точный target, реально находится в `IN_PROGRESS`; она не заменяет семантического владельца.                  | Статус тикета и состояние фазы                  |
| `blocked`        | Незавершённая работа для точного target остановлена; связь остаётся отдельной от плановой работы и завершённой истории.        | Состояние тикета и blocker state                |
| `history`        | Закрытый тикет когда-либо объявлял, проверял или доказанно менял точный target; это происхождение, а не текущая маршрутизация. | Закрытые тикеты, квитанции и evidence Git       |

Механика учитывает status и phase state совместно. `TODO` с точным target даёт `planned` только
пока работа не начата. `active` возникает, только когда владеющая target фаза действительно
`IN_PROGRESS`; одного статуса тикета недостаточно. `blocked` выводится из состояния тикета и
blocker state, а не из упрощённого отображения одного status-token. `DONE` относится только к
`history`.

Семантический владелец и связи задач отвечают на разные вопросы. У файла может быть один
семантический владелец и несколько исторических тикетов. Отсутствие активного тикета нормально,
если `@spec` разрешается. Два активных автора одного точного пути создают блокирующую неоднозначность:
проверка FO-4 должна отказать закрытым образом (fail-closed), а не выбрать одного из них. Активный
автор, чьи `Spec References` не согласуются с `@spec`, также создаёт расхождение, а не становится
альтернативным владельцем.

### Таксономия evidence

Каждая связь результата resolver, включая `semantic-owner`, несёт ровно один из семи классов
evidence. Класс описывает то, что доказывает репозиторий, и не повышает намерение до наблюдавшейся
работы.

| Evidence               | Контракт                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `declared`             | Существует точная запись в `Target Files` или `Deleted Files`. Она доказывает только объявленную область.                                                              |
| `active`               | Точное объявление принадлежит фазе, реально находящейся в `IN_PROGRESS`. Оно доказывает текущую маршрутизацию работы, но не изменение файла.                           |
| `verified-target`      | Валидная квитанция, принадлежащая CLI, подтверждает работу в области точной объявленной цели. Без атрибуции Git это всё ещё не доказывает изменение файла.             |
| `git-attributed`       | Версионируемое доказательство Git связывает точный путь с текущей работой тикета. Это evidence наблюдавшегося изменения.                                               |
| `deleted`              | Версионируемое доказательство Git подтверждает удаление точного объявленного пути. Это evidence наблюдавшегося удаления.                                               |
| `declared-only-closed` | DONE-тикет объявлял путь, но не имеет более сильного наблюдаемого evidence. Он относится к `history` и не должен показываться как «файл изменён».                      |
| `unknown`              | Входы отсутствуют, конфликтуют, неоднозначны или не поддерживаются. Resolver сообщает неопределённость и никогда не повышает её до `active`, `verified` или `changed`. |

При наличии нескольких входов классификация использует самый сильный фактически присутствующий
факт и сохраняет указанное различие: атрибуция или удаление в Git наблюдаемы; квитанция подтверждает
область цели; статус и списки целей остаются объявленным доказательством жизненного цикла. `declared`,
`active`, `verified-target` и `declared-only-closed` никогда не должны выводиться как наблюдаемое
изменение файла.

Для `semantic-owner` разрешённый canonical ID получает `declared`: шапка объявляет владельца, а
registry/resolver подтверждает единственное разрешение ID в path. Отсутствующее или неоднозначное
разрешение получает `unknown` и соответствующий finding. Для `planned`, `active`, `blocked` и
`history` класс назначается по фактически доступным ticket/phase/receipt/Git данным.

### Стабильные finding codes

Ниже приведён закрытый реестр finding codes контракта FO-1. FO-4 реализует их без переименования;
новый класс ownership-дефекта требует отдельного изменения ADR.

| Код                                 | Условие                                                                                                                                                                                                          |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SDD_FILE_SPEC_OWNER_UNRESOLVED`    | V2 `@spec` отсутствует, имеет неверный формат или canonical spec ID не разрешается registry/resolver в существующую спецификацию; закрытый отказ.                                                                |
| `SDD_FILE_SPEC_OWNER_AMBIGUOUS`     | Canonical spec ID разрешается более чем в одну спецификацию; закрытый отказ без выбора кандидата.                                                                                                                |
| `SDD_FILE_ACTIVE_WRITERS_COLLISION` | Несколько фаз `IN_PROGRESS` объявляют один exact target без проверяемой serialization/dependency policy; блокирующая коллизия.                                                                                   |
| `SDD_FILE_ACTIVE_SPEC_MISMATCH`     | `Spec References` активного тикета не согласуются с canonical spec ID файла и нет явной typed cross-spec relation.                                                                                               |
| `SDD_FILE_TARGET_PATH_INVALID`      | Target имеет неверный формат или отвергается существующей repo-path/tombstone policy: absolute/`..`/glob/symlink escape либо другой запрещённый path. Само по себе отсутствие planned-файла не является finding. |
| `SDD_FILE_PROVENANCE_UNKNOWN`       | Provenance/evidence не поддерживается или неоднозначно; relation остаётся `unknown` и не повышается до `active`, `verified-target`, `git-attributed`/changed.                                                    |
| `SDD_FILE_V2_TASKS_FORBIDDEN`       | Новая или уже мигрированная V2-шапка содержит legacy `@tasks`; нетронутая V1-шапка это finding не получает.                                                                                                      |
| `SDD_FILE_ACTIVE_PLANNED_OVERLAP`   | `active` и `planned` объявляют один exact target; видимый coordination warning без назначения второго владельца.                                                                                                 |

### Инварианты resolver

FO-2 и каждый последующий потребитель должны сохранять следующие инварианты:

1. Нормализовать путь от корня репозитория и сравнивать пути точно. Сопоставление по basename,
   substring и glob запрещено.
2. Определять V1/V2 для каждой области до толкования шапок; не применять правило V2 к нетронутым
   V1-соседям.
3. Разрешать canonical spec ID из единственного `@spec` через registry/resolver независимо от
   статуса задачи. Отсутствующий или неоднозначный владелец V2 должен быть явным и приводить к
   закрытому отказу (fail-closed).
4. Выводить `planned`, `active`, `blocked` и `history` из канонического разбора тикетов, точных
   списков целей, квитанций и evidence Git. Не выводить их из памяти агента или сходства прозы.
5. Оставлять пути запросов доступными только для чтения. Вычисленный индекс — одноразовый кэш, а не
   второй вручную редактируемый реестр владения.
6. Использовать один чистый resolver для потребителей `orient`, `sdd-check`, reconcile, audit и
   migration. Потребители не должны изобретать собственное толкование владения.
7. Не добавлять «фазу владения». Владение — проекция существующих версионируемых артефактов.

## Матрица приёмки последующих задач

Эти случаи образуют общий контракт FO-2—FO-6. FO-1 фиксирует их, а последующие задачи добавляют
исполняемые фикстуры.

|   # | Случай                                                                     | Обязательный исход                                                         |
| --: | -------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
|   1 | Нетронутый V1-файл с множеством устаревших ID задач                        | Допустим и побайтово сохранён.                                             |
|   2 | Новый V2-файл                                                              | Один `@spec` с разрешимым canonical spec ID; нет `@tasks`.                 |
|   3 | Один IN_PROGRESS-тикет с точной целью                                      | Одна связь `active`.                                                       |
|   4 | Один TODO-тикет с точной целью                                             | `planned`, не активный владелец.                                           |
|   5 | Один DONE-тикет с точной целью                                             | `history`; reconcile не переоткрывает его автоматически.                   |
|   6 | Два активных тикета для одного пути                                        | Блокирующая коллизия; победитель не угадывается.                           |
|   7 | Активный тикет ссылается на другую спецификацию                            | Находка о расхождении спецификаций.                                        |
|   8 | Отсутствующий или неоднозначный V2 `@spec`                                 | Закрытый отказ с явной неоднозначностью владельца.                         |
|   9 | Смешанный репозиторий                                                      | V1-сосед остаётся устаревшим; мигрированная область становится строгой V2. |
|  10 | Цель совпадает только по basename, substring или glob                      | Связь отсутствует.                                                         |
|  11 | Квитанция подтверждает цель, но соответствующего evidence Git нет          | `verified-target`, но не `git-attributed`.                                 |
|  12 | DONE-тикет имеет только объявление                                         | `declared-only-closed`, а не «файл изменён».                               |
|  13 | Для удалённого или переименованного пути нет поддерживаемого сопоставления | Явный `unknown`/tombstone, а не выведенный владелец.                       |
|  14 | `orient --history`                                                         | Меняет только детализацию вывода, но не классификацию связей.              |
|  15 | `orient --json`                                                            | Детерминированная версионируемая схема.                                    |
|  16 | Повторное применение миграции шапки                                        | При втором применении ничего не меняется.                                  |

## Контракты модуля FO-2

FO-2 сознательно публикует детерминированный resolver до подключения CLI и проверок в FO-3/FO-4. Resolver не
вводит отдельный bypass для cross-spec работы: активная фаза обязана перечислить canonical spec ID
файла среди уже разрешённых `Spec References`, даже если вместе с ним перечислены другие
спецификации.

### `resolveFileRelations`

- **Contract:** Строит детерминированные `semantic-owner`, `planned`, `active`, `blocked`, `history`
  и findings из структурированного входа. Он не пишет файлы, не обходит корпус, не вызывает
  Git/process и не создаёт кэш; для нормализации и repo-path policy использует канонический
  read-only inspector `inspectRepoPath`.
- **Usage Waiver:** FO-2 намеренно поставляет единое ядро до его производственных
  потребителей; FO-3 подключает `orient`, FO-4 подключает `sdd-check`, после чего waiver должен быть
  снят, а не продлён молча.

### `fileRelationTicketFromContent`

- **Contract:** Адаптирует bytes одного тикета через действующие канонические parsers; registry,
  receipt validation, Git evidence и обход корпуса остаются обязанностью вызывающей стороны.
- **Usage Waiver:** FO-2 фиксирует общий parser-boundary заранее, чтобы FO-3/FO-4 не создали второй
  regex parser; первый производственный adapter в FO-3 или FO-4 обязан снять waiver.

## Последствия и владельцы следующих шагов

- **FO-2** реализует чистый resolver и исполняемые тесты связей/evidence.
- **FO-3/FO-3a** предоставляют общий результат через `orient` и принимают канонические ID задач.
- **FO-4** владеет fail-closed-проверками разрешения владельца, коллизий активных авторов,
  расхождения спецификаций и orphan-`@spec`.
- **FO-5** переводит потребителей создания и рабочего процесса, шаблоны шапки файла и действующие аксиомы с
  полномочий `@tasks` на этот контракт.
- **FO-6** мигрирует устаревшие шапки только при однозначном сопоставлении и сообщает о неоднозначности,
  а не угадывает.
- **FO-7** явно отложена: проектирование кэша требует измерений и детерминированной инвалидации.
- **Самомиграция E-14** остаётся заблокированной до FO-6; этот ADR не меняет текущие продуктовые
  данные V1.

## Отклонённые альтернативы

1. **Сохранить дополняемый `@tasks` владельцем V2.** Отклонено, потому что история остаётся смешана
   с текущими полномочиями, а закрытый тикет может получить маршрутизацию текущей работы.
2. **Хранить `@spec` вместе с вручную поддерживаемым индексом связей.** Отклонено, потому что это
   создаёт второй источник истины, который может разойтись с тикетами, квитанциями и Git.
3. **Выводить владение из совпадения по basename, substring или glob.** Отклонено, потому что
   неоднозначность превращается в молчаливую ошибочную маршрутизацию.
4. **Считать квитанции доказательством изменения файла.** Отклонено, потому что scope верификации и
   атрибуция Git доказывают разные факты.
5. **Переписать существующие шапки V1 в FO-1.** Отклонено, потому что совместимость обеспечивается
   изолированной миграцией; текущие данные V1 остаются нетронутыми до E-14.
